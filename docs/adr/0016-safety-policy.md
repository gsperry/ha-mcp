# 0016. Safety policy: blocking system actions on every route the server can cause

Date: 2026-10-22
Status: Accepted

## Context

### Problem

This server lets a language model call any Home Assistant service, trigger an automation, and write an automation. Home Assistant itself runs whatever it is asked to run as an administrator. A mistaken or manipulated model can therefore cause a system action: restart or stop Home Assistant, purge the history, create or restore a backup, start, stop or reboot an add-on or the host, or run a shell command or a Python script. Nothing in the original design stops it. Before this record's change, `call_service` passed every domain and service straight through, `upsert_automation` stored any actions, and `trigger_automation` ran an automation without looking at what it does.

The owner decided on 2026-10-22 that system actions are dangerous and must be blocked on the server, deterministically, with no way for the model to override the block in chat. Overwrites (saving over an existing automation or dashboard) and security devices (locks, alarm panels, covers) are not treated as dangerous. The same rules apply to the actions inside automations that the server writes or triggers. Deleting an automation is handled by a separate confirmation step and is not part of this record.

A check on the service name alone is not enough, because Home Assistant offers many ways to cause the same effect indirectly:

- A script, scene or automation can contain the blocked service, nested at any depth. The model reaches it with `script.turn_on`, `script.toggle`, the per-script service `script.<key>`, `automation.trigger`, `trigger_automation`, `scene.turn_on`, or `homeassistant.turn_on` and `toggle` forwarding to any of them.
- The target of such a call can be a floor, area, device, label, a group (old-style, or a new-style group, which forwards the call to its members when it runs) or `entity_id: all`, each of which Home Assistant expands to entities on its own or hands on. A scene member or an entity named inside service data can be a group too, and `group.set` and `scene.create` change what a group or scene holds while a script runs.
- A blueprint instance stores `use_blueprint`, its inputs and any keys of its own. Home Assistant merges the instance's own keys over the blueprint's, so an instance can carry its own actions and triggers next to the blueprint's, and inputs can themselves be actions.
- Some entities run configured actions or commands on an ordinary `turn_on`, `turn_off` or `press`: template switches, lights and buttons, `command_line` switches, covers and sensors, `universal` media players, Wake-on-LAN switches and Panasonic Viera players. Some stop the machine that runs Home Assistant: Supervisor add-on switches, Portainer containers, Proxmox virtual machines. A legacy `notify.<name>` service backed by `command_line` runs a shell command and has no entity at all.
- Some services act on a host, a container or the Home Assistant process and take a device id, or nothing at all, in their data instead of an entity target: `synology_dsm.reboot` and `synology_dsm.shutdown`, `portainer.recreate_container` and `system_bridge.power_command`. A scan of the data for entities finds nothing in such a call, so a check that only looks at entities lets it through.
- Home Assistant renders step data when the step runs. A whole `data` or `data_template` string, even one with no template marker, is turned into a mapping, and mapping keys are rendered, so a step can name an entity that the stored config never spells out. Other plain strings nested in the data are not parsed and reach the service as text.
- Home Assistant also lets trigger fields sit under an `options` key and moves them up before use, so a check that reads only the top level of a trigger misses them, and `options` can even replace the trigger's kind (`platform`).
- `conversation.process` hands a text request to Assist, which can run scripts and entities. `google_assistant_sdk.send_text_command` and `alexa_devices.send_text_command` hand free text to an outside assistant that can act on the entities exposed to it.
- Several services pass a media-player field (which accepts `all`) on to `media_player.play_media`, where a `universal` player runs its configured commands: `tts.speak`, the legacy `tts` say services, `camera.play_stream` and `google_assistant_sdk.send_text_command`. `media_extractor.play_media` forwards its whole data, area, device, floor and label targets included, to `media_player.play_media`.
- Home Assistant announces every service call, with its full data, as a `call_service` event. An automation written through this server could capture such an event and copy secrets from it (the confirmation code of the delete step is the case this protects) into a helper that a read tool then returns.

The owner accepted on 2026-10-22 that the policy is a list of known routes plus a platform denylist, not a proof. Other integrations, especially custom ones, that run configured actions behind ordinary services remain a declared residual (see Residual risks).

This record decides the policy module, every list in it, the walker that decides what a request would run, the Worker settings, the bounds that keep the walk inside the Cloudflare Workers free plan, where each check runs relative to the first call that changes the house, and what happens when the WebSocket or Home Assistant cannot be reached. The server keeps no state between requests, so the policy stores nothing and every decision is made inside one tool call.

### Behaviour of the last release

There is no release. Before this server was built, the repository had no tool: the original design note (`plan.md` as first written, before its dated correction note) only described them, and line 57 of the current `plan.md` still describes `call_service` as "Call any service (turn on, set temp, run script)". Line 63 describes `trigger_automation` as firing an automation with no mention of inspecting it, and the note has no safety policy at all. This record therefore departs from that design by the owner's decision of 2026-10-22. Every residual below is marked "no release existed".

## Options considered

1. **Block by service name only.** Rejected: a script, scene, blueprint or automation reaches the same service, as does a `command_line` switch through `switch.turn_on`. A name check passes all of them.
2. **Refuse every service call that can run something indirectly (all scripts, scenes, automations, and every entity of any platform).** Rejected: it removes the main use of the server, which is to turn lights on and run the owner's scripts.
3. **Walk what a request would run and refuse the dangerous parts (chosen), plus a platform denylist.** The cost is one WebSocket round of reads before the acting call.
4. **Platform allowlist instead of a denylist.** Rejected by the owner on 2026-10-22: new devices would be blocked until a maintainer lists their platform.
5. **Resolve targets in the Worker from the registries.** Rejected: floors, areas, devices, labels, groups and `primary_entities_only` are Home Assistant's rules and change between releases. `extract_from_target` with `expand_group: true` returns what a service call would reach, in one command, with the same defaults for config entities.
6. **Read scripts through REST (`/api/config/script/config/<key>`).** Rejected for entity targets: it needs the key, returns a blueprint script as bare `use_blueprint`, and cannot read YAML-package scripts. `script/config` by entity id returns the substituted config of any loaded script. REST by key is used only for the `script.<key>` service route, where the key is all that is known.
7. **Expand blueprint scripts with `blueprint/substitute`.** Rejected for stored scripts and automations: their `raw_config` is already substituted. It is used only for an automation being written, which is not stored yet.
8. **Read an automation's config through REST.** Rejected: it needs the config id from a state read, returns blueprint instances unexpanded and cannot read package automations. `automation/config` by entity id costs no extra subrequest.
9. **One WebSocket connection per walk level.** Rejected: a nesting depth of five would cost eleven connections. A check that appends commands to the live list keeps the walk on one connection, and the helper already works that way.
10. **Extend the helper with a callback-driven session API.** Rejected: a second public contract for one caller. Appending to the list the helper already reads is smaller and is covered by a test.
11. **Fail open when the WebSocket is down.** Rejected by the owner on 2026-10-22: classification needs it, so the server refuses every call that names an entity while it is down and accepts being read-only in effect until the first real run shows whether that matters.
12. **A REST-only degraded mode with an owner allowlist of entities.** Rejected by the owner on 2026-10-22 for now; revisit if the WebSocket proves unusable in production.
13. **A tool argument or chat message that overrides the block.** Rejected by the owner: the block has to hold against the model.
14. **Retry a failed policy read.** Rejected: each retry is another login, and a failed login counts towards an address ban.
15. **Read a script by key over REST before opening the WebSocket.** Rejected: it puts a second 10 s limit in front of the first and lengthens the pre-write time of an upsert. Every REST read is made from inside a check on the connection that is already open, so one limit covers the whole walk.
16. **Parse nested data strings as Python literals, and refuse those that look like a literal and do not parse.** Rejected: Home Assistant does not parse a nested plain string (facts table), so the rule would refuse texts such as `[Door] open` that Home Assistant sends unchanged, for no gain. Only a whole `data` or `data_template` string is parsed, because Home Assistant parses it; the server reads it with a small parser that accepts a subset of Python and refuses a whole string it cannot read as a mapping, because scanning the text instead would have to decode every Python escape to be safe. The cost is rare and is in the owner confirmations.
17. **Judge a device action by its integration's own code.** Rejected: the server cannot see it. A table of the device domains that call a service of their own domain, and a refusal for everything else, is what the server can state.

## Decision

### D1. One policy module, called before the first acting call

A new directory `src/policy/` holds the whole policy:

- `lists.ts`: the data in D3, as constants.
- `settings.ts`: reads the two settings (D2) from `env`.
- `walker.ts`: pure code, no network. Given a list of steps it returns what they would do: service calls with their names, targets and data, script and automation runs, scene steps, device steps, event steps, triggers, and reasons it cannot tell.
- `resolve.ts`: drives the WebSocket and REST reads (D8, D11), applies the lists and returns a verdict.
- `python.ts`, `capture.ts` and `refusal.ts`: Python's `str.strip()`, the template test and the small parser of D6; the capture rule of D10; and the refusal type with its message builders.
- `index.ts`: three entry points, `checkServiceCall(env, call)`, `checkAutomationWrite(env, config)` and `checkAutomationTrigger(env, entityId)`. Each returns when the request may go on and throws `PolicyRefusal`, an `Error` whose message reaches the caller, when it may not.

The tools call these entry points and nothing else. No argument of any tool reaches the settings.

### D2. Worker settings

Both are plain Worker variables read from `env`, not secrets. They are independent of each other.

- `ALLOW_SYSTEM_ACTIONS`: absent by default. Only the exact text `true` turns the system-action block off; any other value, including empty, leaves it on, so a typo fails closed. With it off, the system-action checks (D3, D4 and D6 to D9, except the legacy-notify rule) are skipped: any call and any config passes them, and no entity map, target expansion, script, automation or scene is read. Two checks stay on. The capture rule (D10) stays on because it protects the delete confirmation and not a system action; with the block off it examines only the config being written (its own triggers and every `wait_for_trigger` step in it, at any depth) and, for a blueprint instance, the blueprint's expansion merged with the instance's own keys (D8), which costs one `blueprint/substitute` command on a WebSocket connection. Scripts and automations that the config merely calls are not read, so a script of the owner's that waits for `call_service` is not caught. The legacy-notify rule (D3) stays on because it is the separate setting below: turning off the block for restarts and shell commands does not also allow every shell-backed notify service.
- `ALLOWED_NOTIFY_SERVICES`: a comma-separated list of legacy notify services the model may call, written as `notify.<name>` or just `<name>`, compared in lower case. When set, even to an empty text, it is the whole list. When absent, the list is the value of the setting that names the notify service for delete confirmation codes (added with the delete confirmation step, and not present yet), so that the owner's phone service keeps working. With neither set, no legacy notify service is allowed. The server's own notify call for a delete code is not a model call and is not checked. A notify group (a legacy service that fans out to others, `ha:homeassistant/components/group/notify.py:59-93`) on the list lets the model reach every member of the group, so only a group whose members the owner trusts belongs there.

`Env` in `src/index.ts` gains two optional string members, `ALLOW_SYSTEM_ACTIONS` and `ALLOWED_NOTIFY_SERVICES`. The repository's `wrangler.toml` gets a comment that documents them and no value; the owner sets them under `[vars]` of their own configuration or in the dashboard. The test Wrangler config is unchanged, and the shared test bindings in `vitest.config.ts` leave both unset, so every full-path test exercises the defaults. A test that needs a setting builds the server with its own `env` instead of going through the shared bindings.

### D3. The lists

All entries are lower case and compared after trimming and lower-casing the request. **Trim** everywhere in this record means Python's `str.strip()`, because Home Assistant strips with it and JavaScript's `trim()` leaves some of its characters. The characters removed are: space, `\t`, `\n`, `\v` (U+000B), `\f`, `\r`, `\x1c`, `\x1d`, `\x1e`, `\x1f`, `\x85`, `\xa0`, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F and U+3000. The implementation names this set explicitly and does not rely on the language's own trim.

- **Blocked domains** (every service in them): `hassio`, `backup`, `shell_command`, `python_script`, `profiler`, `debugpy`. A whole domain is the unit because `shell_command` and `python_script` register one service per configured entry, because `profiler` has thirteen services, several of which can stall the Home Assistant process (`start` and `memory` take any number of seconds with no upper limit, `ha:homeassistant/components/profiler/services.py:272-290`), and none that an everyday request needs, because `debugpy` has one service, `start`, which opens a debugger port on the configured host (`ha:homeassistant/components/debugpy/__init__.py:74-77`), and because new services in these domains stay blocked.
- **Blocked services**: `homeassistant.restart`, `homeassistant.stop`, `homeassistant.set_location`, `recorder.purge`, `recorder.purge_entities`, `recorder.disable`, `update.install`, `cloud.remote_disconnect`, `synology_dsm.reboot`, `synology_dsm.shutdown`, `portainer.recreate_container`, `system_bridge.power_command`, `group.set`, `scene.create`, `sql.query`, `media_extractor.play_media`. `media_extractor.play_media` is blocked because it forwards area, device, floor and label targets to `media_player.play_media` (facts table), and the server's target checks, which keep only entities of the call's own domain (D7.3), would find none and allow it. The four services that name a device or nothing are blocked because the entity checks cannot see them (facts table); they are refused by name in a direct call and wherever the walker meets them, like the others. `group.set` and `scene.create` change what a group or a scene holds while a script runs, so a walk that classified the members at the time of the check could be undone by the next step. Every blocked service and domain is refused wherever the walker meets it, in a direct call and inside any config it walks, and belongs to the system-action checks that `ALLOW_SYSTEM_ACTIONS` switches off.
- **Dispatch services** (hand a request to Assist, an agent or an outside assistant): `conversation.process`, `google_assistant_sdk.send_text_command`, `alexa_devices.send_text_command`. Each is refused by name, in a direct call and wherever the walker meets it, before any Home Assistant request; the Alexa service names only a device, so the rule for calls with no entity (D12) does not apply to it. Other candidates were read and are allowed (D4).
- **Platform denylist** (entities that run configured actions or commands, or that stop the host that runs Home Assistant): `template`, `command_line`, `universal`, `wake_on_lan`, `panasonic_viera`, `hassio`, `portainer`, `proxmoxve`. Any service call that acts on an entity of one of these platforms is refused, including calls that are harmless in themselves (the volume of a Panasonic Viera player, `turn_on` of a Wake-on-LAN switch): the platform is the unit. Sensors and other entities of these platforms that nothing acts on are not judged.
- **Inline-entity services** (carry entities in their data). `scene.apply` and `media_player.join` carry them throughout their data, so a templated value anywhere in the data is refused and the members are read strictly (D6, whole-data rule). The services below each carry media players in one field only, so only that field is read strictly and refused when templated; their other fields follow the ordinary-field rule of D6:
  - `tts.speak`, field `media_player_entity_id`;
  - every legacy `tts` say service, meaning every service of the `tts` domain other than `speak` and `clear_cache` (the name is configurable), field `entity_id`;
  - `camera.play_stream`, field `media_player`;
  - `google_assistant_sdk.send_text_command`, field `media_player` (also refused by name above while the block is on; it is listed too, so that the list of media-player fields is complete).

  These four fields are read strictly as media-player member fields (D6): `all` means every `media_player` entity in the entity map, each one classified; a templated value in the field is refused; `none` acts on nothing. Their other fields, for example the `message` of `tts.speak`, which Home Assistant carries inside the media source id that it gives to the player the classified field names, and never reads as an entity reference (`ha:homeassistant/components/tts/entity.py:146-155`), are ordinary data fields: a templated value there is allowed. A templated mapping key is refused everywhere, in these services too.
- **Legacy notify services**: every service of the `notify` domain other than `send_message` is refused unless it is on the allowlist (D2). `notify.send_message` is an entity service and is classified like any other (D7). This rule holds with `ALLOW_SYSTEM_ACTIONS` on or off.
- **Reserved event types**: any event type starting with `homeassistant_`. **Capture event types** (D10): `call_service` and `*`.
- **Device domains with a known service** (D4, device steps): the toggle domains `light`, `switch`, `fan`, `humidifier`, `remote` (`turn_on`, `turn_off`, `toggle`), `button` (`press`), and the own-domain domains `alarm_control_panel`, `climate`, `cover`, `lock`, `number`, `select`, `text`, `vacuum`, `water_heater`.

### D5. The walker: what it reads and how steps are classified

The walker takes the actions of an automation (`actions` or `action`, both read when both are present), a script (`sequence`), or a stored config read back, and produces a list of findings. It never changes its input and never calls the network. Trigger lists are read under `triggers` and `trigger` in the same way.

1. **Step type.** A step must be a mapping; anything else is refused as unreadable. Its type is the first key of `ACTIONS_MAP` that it contains, in Home Assistant's own order (the first row of the facts table). A step with no such key is refused.
2. **Over-approximation.** The type decides what a step means, but the walker also checks every key that can carry a call or a nested list, whatever the winning type is: `action`, `service` and `service_template` are all read as calls, and `sequence`, `choose`, `if`, `repeat`, `parallel` and `default` keys are all walked. A step cannot hide a call behind an earlier key. Home Assistant's strict step schemas reject such a step on save, so no valid config is refused for this.
3. **Nesting.** Walked recursively, with a single item accepted wherever a list is: `choose` (each option's `sequence`, and `default`), `if` (`then` and `else`), `repeat` (`sequence`), `parallel` (each entry is either a step, which may be a `sequence` step, or a list of steps), `sequence`. `wait_for_trigger` is not an action list; its triggers go to the capture rule (D10). Conditions hold no calls and are not walked. `enabled`, `continue_on_error` and `alias` are ignored: a disabled step is still walked.
4. **Calls.** For each service-call key the walker normalises the name (trim, lower case, must match `domain.service` with letters, digits and underscores) and collects the targets (D6). A name that does not parse, or is templated, is refused.
5. **Other step types.** `scene` is a scene run (D8). `device_id` is a device step, classified by its `domain` and `type` (D4). `event` is checked as in D4. `wait_for_trigger` goes to D10. `delay`, `wait_template`, `condition`, `and`, `or`, `not`, `variables`, `stop` and `set_conversation_response` hold no calls.
6. **Blueprint instances.** A config with `use_blueprint` is never walked as is, and never as the blueprint alone. Home Assistant builds the instance from the blueprint with the inputs substituted and then lays the instance's own keys over it, dropping `use_blueprint` and `blueprint` (facts table). The walker is given exactly that: `{...substituted, ...instance}` without those two keys, so an `actions`, `sequence`, `triggers` or `trigger` of the instance's own replaces the blueprint's. This applies to a config being written (D8) and to a script read by key over REST (D8); a loaded script or automation read by entity id already comes back merged. A stored config that still contains `use_blueprint` after being read back (the blueprint failed to load) is refused: its actions are unknown.
7. **Structure bounds.** Nesting within one config deeper than 20 levels, or more than 1000 steps in one walk, is refused (D11).

### D6. Names and targets

- **Templates.** A string that contains `{{`, `{%` or `{#` is a template. A templated service name, a templated `target` (the whole value), a templated `data` or `data_template` (the whole value), a templated value in any target key (`entity_id`, `device_id`, `area_id`, `floor_id`, `label_id`) and a templated mapping key anywhere in `data`, `data_template` or `target` are refused: Home Assistant decides them at run time, and it renders keys as well as values (facts table). In `scene.apply` and `media_player.join` (D3), which carry entities throughout their data, every value in the data is checked and a templated one anywhere, at any depth, is refused. In `tts.speak`, the legacy `tts` say services, `camera.play_stream` and `google_assistant_sdk.send_text_command` only the media-player field is refused when it is templated (member fields below); their other fields, such as `message`, are ordinary data fields, and a templated mapping key is refused in them as everywhere. A template inside an ordinary data field of any other service, such as a brightness, is ignored; the narrow case it leaves is a residual.
- **Whole data strings.** A whole `data` or `data_template` value that is a string with a template marker is refused (above). A whole `data` or `data_template` value that is a string without one is the only data that Home Assistant parses without a marker (facts table), so the server parses it as well, and the resulting mapping is treated as the data, so its `entity_id` counts as a target. Home Assistant strips the whole string with `str.strip()` before it parses it (facts table), so it would drop any leading or trailing character of the trim set (D3). The small parser skips only space, tab, newline, carriage return and form feed, so a string that starts or ends with any other character of that set (`\v`, `\x1c` to `\x1f`, `\x85`, `\xa0`, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F, U+3000) is not read as a mapping and is refused. That is a rare, safe over-refusal: Home Assistant would have used the mapping, and the server sends nothing. A string whose first non-whitespace character is `#` or `\` is refused without being parsed: Python skips comment lines and backslash-newline continuations before a literal, which the small parser does not, and refusing is the one rule that cannot be fooled by mixing them (a comment line, then a continuation, then the dict). A string that does not become a mapping is refused: Home Assistant raises "Result is not a Dictionary" for any other result (`ha:homeassistant/helpers/service.py:326-332`), so a working config never has one, and the rule leaves no way to hide a mapping behind syntax the small parser does not read. The parser accepts exactly: dictionaries at the top level, and inside them dictionaries, sets, lists and tuples (in parentheses; trailing commas allowed), strings in single or double quotes whose only backslash escapes are `\\`, `\'`, `\"`, `\n` and `\t`, whole and decimal numbers, `True`, `False`, `None`, and whitespace. Nothing else: no operators, string prefixes, triple quotes, joined neighbouring strings, comments or names. A mapping with the same key twice, at any depth, is refused: Python keeps the last value, and a reader that kept the first would see a different entity from the one Home Assistant uses. A string inside the result is not parsed again, because Home Assistant does not render it again. The cost is rare and is stated plainly: a whole data string that works in Home Assistant but is refused, because it holds a negative number, a comment after its first token, a string prefix or other syntax outside this list, or starts with `#` or a backslash. Every other string in step data, nested at any depth, is plain text for Home Assistant, so the server does not parse it and a text such as `[Door] open` or `#1 priority` is not refused. This applies to walked step data only; the data of a direct `call_service` is JSON and Home Assistant does not parse its strings.
- **Normal form.** An `entity_id` value, and every member field below, is a list, a tuple (from a parsed whole data string) or comma-separated text; it is split on commas, each piece trimmed and lower-cased. `none` is no target. `all` means every entity of the call's domain (D7). The other four keys are lists of text.
- **A direct call's `target`.** The data of a direct `call_service` may carry a `target` mapping; it is read like a step's target, so its keys are not ignored (Home Assistant would reject the key for an entity service, and a service that accepts it receives it as data).
- **Where entities come from.** Entity references are the values of the five target keys at the top level of the data, in a `target` mapping, and as a step-level `entity_id`, and every other string in the data (including those inside a parsed whole data string), as a value or as a mapping key at any depth, that after trimming and lower-casing (or after splitting on commas) is exactly an entity id and is known to `entity/source`. A nested string is scanned as text and never parsed. Home Assistant lower-cases entity ids as it validates them (`scene.apply` lower-cases its keys), so `Switch.Shell` is `switch.shell`.
- **Member fields, read strictly.** Home Assistant checks some fields with `cv.entity_ids` or `cv.entity_id`: the target keys, `scene.apply`'s `entities` keys and `media_player.join`'s `group_members`. In these every piece, in the normal form above, must be a known entity id, otherwise the call is refused as unknown, and each member is classified whatever its domain (D7.3).
- **Media-player member fields.** The services of the inline-entity list (D3) that carry media players read these fields as member fields, with the same strictness: `tts.speak` `media_player_entity_id`, every legacy `tts` say service `entity_id`, `camera.play_stream` `media_player` and `google_assistant_sdk.send_text_command` `media_player`. Pieces are split on commas, trimmed with the trim of D3 and lower-cased; `all` means every `media_player` entity in the entity map, each one classified (and each forwarding media-player group read, D7.2); `none` acts on nothing; a templated value in the field, at any depth inside it, is refused; an unknown piece is refused. Only this field is refused when templated: the other fields of these services (a `message`, for example) follow the ordinary-field rule above. For a legacy `tts` say service the `entity_id` is this field and is not read as a target of the `tts` domain, wherever it stands: in `target`, as a step-level `entity_id`, and in `data` or `data_template`. Home Assistant merges the target into the data of such a service, and the step-level `entity_id` overrides the target's (facts table), so `target: {entity_id: all}`, a step-level `entity_id: all` and `data: {entity_id: all}` are the same field with the same value, and each reads as every media player. The generic scan still runs over the rest of the data. Everywhere else a string that merely looks like an entity id and is not known is ignored; if the WebSocket is down such a string makes the call need it (D12).
- **Registry ids.** A target given as an entity registry id, not an entity id, is resolved by Home Assistant (facts table) but is not an entity id the server can look up, so it is not in the entity map and is refused as unknown (D7). Only a device step's entity may be a registry id (D8).

### D7. Resolving targets and classifying entities

1. **One map.** The first command of every walk that needs classification is `entity/source`. It returns every entity's platform under the key `domain`; the walker keeps it as a map from entity id to platform. Classification always uses that value, never the entity's own domain.
2. **Target expansion, groups included.** An entity is a group when its id starts with `group.` or its platform in the map is `group`. A target that holds only entity ids, none of them a group, is resolved locally. Any other target (floor, area, device or label ids, or any group) goes to `extract_from_target` with `expand_group: true` and `primary_entities_only` left at its default true, which is what a service call does (facts table). One command per distinct target. That command expands old-style groups and the lock group only. Every other entity of platform `group` that it returns unexpanded, or that the caller named, is a forwarding group (switch, light, button, fan, cover, valve, media_player, notify entity) when its own domain is one of those. Sensor, binary_sensor and event groups forward no service and are never read. Forwarding groups are read only for entities that are acted on after the domain filter of D7.3, so an area or label call such as `light.turn_on` reads only light groups, never the switch, sensor or other groups the area also holds; a group the caller named, and a group that is a scene member or a key of `scene.apply`, is always acted on. For each group that is read, the walker reads its `entity_id` state attribute with REST `GET /api/states/<entity_id>`, treats each member as a named entity, recurses (a member may itself be a group), and classifies every member under the same service whatever its domain, because the group forwards the service to each member. A group whose attribute is missing, not a list of entity ids, or unreadable (404, error, timeout) is refused as unreadable. The same applies to every group that is a scene member, a scanned entity (D6) or a key of `scene.apply`: the group is sent as an `entity_id` target and its members replace it. Group levels count against the depth bound of D9 and each group read is a node. The group entity itself is classified as well, but platform `group` is not denied. A group that is not in the map is refused as unknown.
3. **Which entities are acted on.** For a call whose domain is `D` other than `homeassistant`, the acted-on entities are the resolved entities whose own domain is `D`, because an entity service acts only on its own domain; `entity_id: all` is every entity of domain `D` in the map. Entities the caller named explicitly, every member of a group read by D7.2, and every entity found by the generic scan of the data (D6) are acted on and classified whatever their domain, because an entity found by the scan is one that the service may call into by its own route: `tts.speak` calls `media_player.play_media` on its `media_player_entity_id` (`ha:homeassistant/components/tts/entity.py:142-146`), and a `universal` player there runs its configured command in place of the call (`ha:homeassistant/components/universal/media_player.py:258-272`), so it is refused. For a call in the `homeassistant` domain (`turn_on`, `turn_off`, `toggle`, `update_entity`) every resolved entity is acted on, because Home Assistant forwards to each entity's own domain. `entity_id: all` on a `homeassistant` call is refused, as Home Assistant refuses it. For a scene run, `scene.apply` and `scene.create`, every member is acted on whatever its domain, because a scene applies each member's state to that member's own domain, and a group member is applied member by member. For `media_player.join` and every other member field (D6), the members are the strictly read entity ids and are classified whatever their domain. In a media-player member field (D6) `all` is every `media_player` entity in the map, so a legacy `tts` say service with `entity_id: all` (in the data, in `target` or at step level) classifies every media player and not the `tts` entities, and a house with a denied media player (a `universal` one) refuses it. `group.set` and `scene.create` are blocked (D3) and are never reached here.
4. **Classification.** Every acted-on entity must be in the map. An entity that is not has no source: it is refused as unknown (a typo, an entity that is disabled, a state with no entity behind it, or a registry id, D6). An entity whose platform is on the denylist (D3) is refused, and the message names the entity and the platform. This applies however the entity is reached: named, forwarded, expanded from an area, a floor, a device, a label or a group, listed as a scene member, or found in a script or automation.
5. **What the service does with the entity.** An acted-on entity of domain `script` is run when the effective service is `turn_on` or `toggle` (from `script.turn_on`, `script.toggle`, a forwarded `homeassistant.turn_on` or `toggle`, or a device step of those types); of domain `automation` when the call is `automation.trigger`; of domain `scene` when the effective service is `turn_on`; of domain `button` for every acted-on button, whatever the effective service, because D4 judges every acted-on button however it is reached (a `button.press`, a button device step, a label, a scene or a group). A forwarding group of buttons has no registry entry and no action of its own, so the rule is applied to its members and not to the group entity. `turn_off` and `reload` run nothing.

Reads happen on the one connection (D11). Each node (script, automation, scene) is read at most once per walk. A node that fails to read, for any reason, is refused as unreadable.

### D9. Depth, cycles and counts

- **Depth.** The request is level 0; a script, automation or scene it runs is level 1; what that runs is level 2, and so on. A node at level 6 or deeper is refused as too deep.
- **Cycles.** Each node is keyed by its entity id (or `key:<script key>` for the key route). A node already visited is not walked again, so a script that calls itself, or two that call each other, end the walk with the union of what they run and are not refused for being a cycle.
- **Counts.** At most 20 distinct nodes (script, automation, scene and forwarding group each count), at most 40 WebSocket commands including `entity/source` (target expansions, registry reads and blueprint expansions count), at most 10 REST reads (scene members, the script key route and every forwarding group read), at most 1000 steps. Past any of them the request is refused as too large to check, with the bound named. `entity_id: all` on scripts or automations is therefore refused in a house with more than 20 of them.
- **Time.** The whole walk, REST reads included, shares one limit of 10 s (D11). A walk that is not finished by then is refused.

### D10. The capture rule

An automation written through this server is refused when it could capture the `call_service` event, whose data includes the notify call that carries a delete code. Triggers are normalised the way Home Assistant normalises them before they are read:

1. A trigger list is flattened: an item that holds only `triggers` is replaced by that list.
2. The trigger's kind is its `trigger` key, or the older `platform` key. A trigger that has both at the top level is refused (Home Assistant rejects it as well).
3. `options` is merged in. If the trigger has an `options` key that is a mapping, the trigger is read as the rest of the trigger with the `options` entries laid over it (`ha:homeassistant/helpers/automation.py:104-134`). If `options` is present and is not a mapping, the trigger is refused as unreadable. If `options` holds a `platform` or a `trigger` key, the trigger is refused: Home Assistant lets that entry replace the trigger's kind, so a trigger written as `state` can attach as an `event` trigger (`ha:homeassistant/helpers/trigger/__init__.py:685-709`). For the both-places rule `trigger` and `platform` are the same key. If any other key appears both at the top level and in `options`, the merge is ambiguous and the trigger is refused. A capture type therefore cannot hide on either side, and the kind is never read from a place that another place can override.

A normalised trigger of kind `event` is refused when its `event_type`, which Home Assistant treats as a list of templates, is, or contains, any of: `call_service` (compared without regard to case and spaces), `*`, a templated value, or a value that is not text. The same normalisation and test is applied to each trigger of a `wait_for_trigger` step (Home Assistant validates both with the same function). The rule is applied to:

- the automation's own `triggers` or `trigger` (both are read when both are present);
- every `wait_for_trigger` step at any nesting depth, including steps inside blueprint expansions, inside `parallel` entries, and, with the system-action block on, inside the scripts and automations read for the walk on every route (a script of the owner's that waits for `call_service` cannot be run through the server while the block is on);
- every trigger of a blueprint automation after its expansion and merge with the instance's own keys, so a trigger that the instance adds or overrides is examined as well as the blueprint's.

The rule applies with `ALLOW_SYSTEM_ACTIONS` on or off, to the config being written; only the scripts and automations the config calls are skipped when the block is off (D2). It examines configs written through the server; an automation that already exists and was written by the owner is not changed (Residual risks). A trigger of another kind that reads the same events, an MQTT trigger on a topic that `mqtt_eventstream` publishes to, is not examined: `mqtt_eventstream` republishes every event including `call_service`, and it is declared as a residual.

### D11. One connection, and the helper

The walk runs on one WebSocket connection through `haWsCommands`. The first command is `entity/source` whenever anything needs classifying, and on the key route (`script.<key>`) the connection is opened even when nothing else needs it, so that the read of the key is made on it and not before it. The walk then continues from inside each command's `check`: the check reads the result, extends the walk, and appends the next commands to the array the helper was given. The helper already reads the array lazily (`src/ha/ws.ts`, lines 150-155 and 188), so this needs no change in behaviour; the implementation adds a sentence to the helper's comment, a test that a check can append commands, and a dated amendment to the record on the WebSocket helper. REST reads (scene members, the script key route) are made from inside a check with `haFetch`, never before the first command; they share the helper's 10 s limit, which is therefore the limit of the whole walk. A command that Home Assistant answers with `not_found` is allowed (`allowErrorCodes`) so that the refusal can name the node; `blueprint/substitute` also allows `unknown_error` and `invalid_format`, because a blueprint that is missing or whose inputs do not fit is answered with `unknown_error` (`ha:homeassistant/components/blueprint/websocket_api.py:262-270`) and the refusal should name the blueprint. Any other error rejects the walk. The count bounds of D9 are enforced in the check, before a command is appended. A parse of the entity map or of a registry list is done once per walk, and the walk keeps only the fields it needs.

### D12. Failure: the WebSocket, Home Assistant, and the limits

- A request that needs nothing from Home Assistant to be judged is decided locally and never opens the WebSocket: a blocked, dispatch or notify refusal, a call with no entity reference and no script, automation or scene route (for example `homeassistant.reload_all`, `persistent_notification.create`, or an allowlisted `notify.<name>`), and an automation config whose actions are all of that kind. The server is therefore read-only in effect, not read-only exactly, while the WebSocket is down.
- A request that needs a read and cannot get it is refused with the likely cause: the WebSocket upgrade failed or timed out, the login was rejected (the existing hint about a revoked token, a user that is not an administrator or a local-only user is reused), a command was refused as unauthorised, the socket closed, or a REST read failed. The refusal says the check could not run and that nothing was sent to change anything. Nothing is retried, and nothing is retried after a login failure.
- Because every read comes before the first acting call (D13), a failure at any point of the walk, including Home Assistant becoming unreachable half way or a timeout, leaves the house unchanged. Running out of a count or time bound is a refusal too.
- The 10 s helper limit covers the whole walk. A walk that does not finish in time is refused.
- CPU is different from the other limits. A Worker that runs out of CPU is stopped without an answer, and the CPU of the walk (parsing the entity map, a registry list, a script) adds to what the rest of the request needs. In a `call_service` or `trigger_automation` the walk comes before the acting call, so running out of CPU there changes nothing. In `upsert_automation` the steps after the write (the re-read, and up to six polls that each parse the whole states list) come after it, so a walk that has used much of the CPU can leave too little for them: the write has landed and the result with `previous_config` is lost (the residual of the write record, made likelier). The bound is the free plan's 10 ms of CPU for the whole request, unmeasured; the remedy is the paid plan, whose CPU limit is far higher (platform), or a house small enough that the walk is cheap. The implementation keeps the walk's parsing to one pass of each large answer and does the heavy part (the entity map) first and only when needed, so an upsert whose actions need no classification does none of it. A real-environment measurement decides whether more is needed.

### D13. Where each check runs, and the time budget

- **`call_service`:** after the domain and service are validated and before the POST. A refusal is raised before any Home Assistant request except the walk's own reads. Worst case with Home Assistant stalling at every step: the walk 10 s plus the POST's own limit of 10 s, 20 s.
- **`upsert_automation`:** after the shape of the config and the id are checked locally and before every Home Assistant request of the existing flow (the previous-config read, the registry read, the state reads and the save). A refused config costs no write and no later read. The walk counts inside the time before the write, as follows. ADR 0012 gives the call 55 s from its start, reserves 20 s for the POST and 5 s for the confirmation re-read after it, and so leaves the steps before the POST 30 s. Immediately before the POST the tool refuses, with nothing written, if more than 30 s have passed since the call began. Without the walk the steps before the POST (10 s each for the previous-config read, the registry read and the states read) end by 30 s at the latest, so the check never fires; with the walk, which comes first and can take 10 s, they can end by 40 s, and the check turns that extra time into a refusal instead of a write whose result the client has stopped waiting for. Worst cases with Home Assistant stalling at every step: an update has no registry or states read, so 10 (walk) + 10 (config read) + 20 (POST) + 10 (re-read) = 50 s, where ADR 0012 gave 40 s; a create is refused at about 40 s with nothing written, and one that is just fast enough to pass the check (30 s before the POST) is acknowledged by 50 s and ends by about 56 s, as ADR 0012 states. Every case ends inside the SDK client's 60 s request timeout (`fw:src/shared/protocol.ts:106`). ADR 0012 carries a dated amendment with these figures.
- **`trigger_automation`:** after the existing state read that refuses an unavailable automation, and before the POST of `automation.trigger`. Worst case with every step stalled: state read 10 s, walk 10 s, POST 10 s, state read 10 s, 40 s, inside 60 s with no further check.
- **Not affected:** every read tool (`list_services`, `list_entities`, `get_entity`, `get_history`, registry search, `list_automations`, `get_automation`, `check_config`, dashboard reads), `delete_automation` and `save_dashboard`. A dashboard card's tap action runs only when a person taps it (Residual risks).

### D14. Messages, and no override

A refusal is a tool error that begins with "Refused by this server's safety policy" and says which rule applied, what was refused (the service, the entity and its platform, the node), that the server's configuration blocks it and not Home Assistant, that nothing was sent to change anything, and where the owner can see the policy (the README). A request that needs a bound named says which bound; one refused for time says the check ran out of time and that nothing was written. The refusal never includes a token or a config value other than the names it needs. No argument of any tool changes the policy, and a refusal is not retried by the server.

### Cost against the free plan

The WebSocket upgrade is one subrequest; messages over it are not subrequests. Existing counts are from `src/tools/automations.ts` and `src/tools/services.ts`: `call_service` makes 1; `trigger_automation` makes 3 (state, POST, state); `upsert_automation` makes 3 for an update and at most 11 for a new id (config read, registry, states, POST, config read, up to 6 state polls).

| Case | Policy cost | Total with the existing flow | CPU (estimate) |
|---|---|---|---|
| `light.turn_on` on one light | 1 connection: `entity/source` | 2 | One parse of the entity map, roughly 1 to 2 ms for a house of 3000 entities |
| `light.turn_off` with an area | 1 connection: `entity/source`, `extract_from_target` | 2 | As above, plus a small answer |
| `light.turn_on` on a new-style light group (any forwarding group) | 1 connection: `entity/source`, `extract_from_target`; 1 REST read of the group's state for each such group (a group of groups adds one each) | 3 | As above, plus a small state answer per group |
| `script.turn_on` of a script that sets lights and turns a scene on | 1 connection: `entity/source`, `script/config`, extraction commands; 1 REST read for the scene | 3 | Map parse plus a few small parses |
| A script that calls two scripts which call a third (level 3) | 1 connection, about 8 commands, no REST | 2 | As above |
| `script.<key>` | 1 connection: `entity/source`, then the REST read of the key from inside a check, and `blueprint/substitute` if it is a blueprint | 3 | As above |
| A script with a device step that names a registry id | 1 connection, plus `config/entity_registry/list`, which answers with every registry entry (several times the size of the entity map in a house of 3000 entities) | 2 | The map parse plus one parse of the registry list, the largest single parse of any case, unmeasured; an upsert for a new id with such a step reads the registry list twice, once for the policy and once for the write record's own guard |
| Blueprint automation upsert, new id, with action inputs that call a script | 1 connection: `entity/source`, `blueprint/substitute`, extraction, `script/config` | 12 | Map parse plus two small parses |
| `trigger_automation` of a blueprint automation | 1 connection: `entity/source`, `automation/config`, extraction | 4 | As above |
| Worst case inside the bounds (upsert, new id; 10 REST reads, scene, key or group reads in any mix) | 1 connection and 40 commands at most | 22 | Bounded by the step count; the map parse dominates |

Every case is far inside 50. Forwarding-group reads are REST reads under the same bound of 10 as scene and key reads, so the worst case stays at 22 (1 connection, 10 REST reads, and the 11 of an upsert for a new id) even if every REST read is a group; the nodes bound of 20 and the 10 s walk limit also stay as they were. Nothing in this revision adds a subrequest beyond that bound, and the time worst cases below are unchanged.

Time, with Home Assistant stalling at every step (D13): `call_service` 20 s; `trigger_automation` 40 s; an upsert of an existing automation 50 s (ADR 0012 gave 40 s); an upsert of a new id is refused before the write at about 40 s or, when fast enough to pass the check, ends by about 56 s. All are inside the SDK client's 60 s request timeout. A normal call takes a few seconds; the time for up to 40 sequential commands through a remote proxy is unmeasured, and the 10 s limit turns an overrun into a refusal.

CPU is the weak figure and is stated honestly. The figures above are estimates from payload size, not measurements. A walk that runs out of CPU before an acting call is a refusal and not an unsafe call, but CPU adds up across the whole request: in `upsert_automation` the steps after the write (the re-read and up to six polls, each parsing the whole states list) can be left without CPU by a heavy walk, and then the write has landed and its result and undo value are lost (D12). A very large house may need more than 10 ms for the map parse alone on the free plan.

### Owner confirmations

Before implementation starts the owner confirms each of these, one by one, or all of them in one step. The list is complete and numbered 1 to 22; each item states its cost and, where there is one, the alternative. Each is a behaviour a user sees or a list that goes beyond what was asked for.

1. **The residual table above** (including the open-ended lists, item 21), including that wrappers such as `switch_as_x`, `generic_thermostat` and `alert` are not denied, that automations on their own trigger (owner automations, the turn-on of TV players that use a `PluggableAction`, trigger-based template entities) run unexamined, and that every forwarding group that is acted on is read and its members judged (one REST read per group). Everyday costs of the group reads: a group that is unavailable has no `entity_id` attribute (`ha:homeassistant/helpers/entity.py:1124-1128`) and is refused, although Home Assistant would have skipped it; a group with a stale or disabled member is refused as unknown; a request that reaches more than 10 forwarding groups, or more than 10 groups and scenes together, is refused as too large.
2. **The blocked services beyond the named ones**: `homeassistant.set_location`, `recorder.disable`, `update.install`, `cloud.remote_disconnect`, `synology_dsm.reboot`, `synology_dsm.shutdown`, `portainer.recreate_container`, `group.set` and `scene.create` are blocked as well as `sql.query` (item 17), `media_extractor.play_media` (item 22) and the restart, stop, purge, backup, add-on, host, shell and Python services. Cost of the three device-addressed services (and of `system_bridge.power_command`, item 14): the model cannot reboot or shut down a NAS or recreate a container through the server; the Synology services are deprecated in favour of buttons, which stay usable when they are not config-category or restart-class buttons (D4). The alternative for them is to leave them allowed and declare them as residuals, which leaves a model able to restart Home Assistant when it runs on that NAS or in that container. Cost of `homeassistant.set_location`, `recorder.disable`, `update.install` and `cloud.remote_disconnect` (the D4 rows give the reasons): the model cannot move the house, switch recording off, install updates (core, Supervisor, operating system and add-on updates included) or disconnect remote access through the server; the owner does these in Home Assistant. Cost of `group.set` and `scene.create`: owner scripts and automations that change a group's members or create a scene cannot be run, triggered or written through the server. The alternative for those two is to leave both services allowed but read their `entities`, `add_entities` and `snapshot_entities` fields strictly, as `scene.apply` is read, with every member classified whatever its domain. That keeps owner snapshot-and-restore scripts usable. Its cost is more mechanism (a strict member field for `group.set` and for `scene.create`, with the time-of-check gap for members a later step changes still open) and more refusals when a member is unknown.
3. **The platform denylist**: `template`, `command_line`, `universal`, `wake_on_lan`, `panasonic_viera`, `hassio`, `portainer`, `proxmoxve`. Every service call that acts on an entity of these platforms is refused, harmless ones included: Wake-on-LAN switches and Panasonic Viera players cannot be controlled at all, add-ons cannot be started or stopped, `update.skip` and `clear_skipped` are refused for the core, operating system, Supervisor and add-on update entities (platform `hassio`), and Portainer and Proxmox controls are unavailable. The alternative for `wake_on_lan` and `panasonic_viera` is to list them as residuals and allow them.
4. **Legacy notify**: owner scripts and automations that call `notify.notify`, `notify.persistent_notification`, `notify.mobile_app_*` or any other legacy notify service not on the allowlist cannot be run or triggered through the server, and `notify.<name>` cannot be called directly. The allowlist defaults to the delete-confirmation notify service and is otherwise empty. It stays on when `ALLOW_SYSTEM_ACTIONS` is `true`; the alternative is to switch it off together with the block. A notify group on the allowlist reaches all its members.
5. **Whole data strings**: in scripts and automations the server walks, a whole `data` or `data_template` string is parsed as a mapping, and the request is refused if it is a template, does not become a mapping (a leading or trailing `\v` or `\x1c` is one case: Home Assistant strips it and the server refuses, item 20), holds a duplicate key, or starts with `#` or a backslash. The cost is small: Home Assistant rejects a whole string that is not a mapping at run time anyway, and a duplicate key or a leading `#` or backslash is unusual. A whole string that works in Home Assistant but uses a negative number, a comment after its first token, a string prefix or other syntax outside the small parser is refused too. Plain strings nested in data, such as "[Door] open" or "#1 priority", are not refused. The alternative is to scan the text of a whole data string for known entity ids instead, which needs a rule for every Python escape.
6. **Device steps**: only the device domains named in D3 are accepted; steps of `mobile_app`, `nut`, `rfxtrx`, `zha`, `zwave_js`, custom integrations and steps with no entity are refused. Cost: editor-built automations that use a device action of another integration, or no entity, cannot be triggered or rewritten through the server. The alternative is to allow the other device domains and declare them as a residual: a device action of such an integration is that integration's own code, which the server cannot see, so a model could then run whatever it does.
7. **The upsert time rule**: an `upsert_automation` for a new id is refused before the write when the earlier steps have taken more than 30 s, and an update can take up to 50 s in the worst case (D13).
8. **Free-plan CPU**: a heavy walk can leave `upsert_automation` without CPU after its write, losing the result and the undo value. Accept this until the real run measures it, or move to the paid plan.
9. **`entity_id: all`** on scripts or automations is refused in a house with more than 20 of them, and `entity_id: all` for a domain that holds a denied entity is refused.
10. **`script.<key>`** is refused for a package script (use `script.turn_on` with the entity id), and reads the stored file, which can differ from the loaded script until a reload.
11. **Read-only in effect while the WebSocket is down**, and the decision to wait for the first real run before a degraded mode.
12. **`mqtt_eventstream`** is declared as a way to capture the delete confirmation code; the owner agrees not to configure it, or to have MQTT triggers examined with the delete confirmation design.
13. **Time of check against time of use** (including scripts called after a delay or a wait), **owner automations that capture `call_service`**, and **automations that run later on their own trigger**, none of which the server can see.
14. **`system_bridge.power_command`** is blocked (every command: shutdown, restart, sleep, hibernate, lock, logout). It acts on the machine that runs System Bridge, which is the Home Assistant host only where Home Assistant runs on that machine. The alternative is to leave it allowed and declare it as a residual with the other System Bridge services; the cost is that a model can then shut down or restart that machine, which may be the host.
15. **The `profiler` domain** is blocked whole. Cost: none for everyday use; the owner uses the profiler from the Home Assistant interface. The alternative is to leave it in the borderline services that stay allowed: `profiler.start` and `profiler.memory` accept any number of seconds with no upper limit (`ha:homeassistant/components/profiler/services.py:272-290`), so a single call can keep the process busy for as long as the caller chooses, and the other services log or dump objects of the process; none of them changes anything that is stored.
16. **The `debugpy` domain** is blocked whole (its one service, `start`, opens a debugger port on the configured host, all addresses by default). Cost: none for everyday use. The alternative is to leave it allowed and declare it as a residual bounded to houses that have configured `debugpy`, whose owner then does not configure it.
17. **`sql.query`** is blocked. Cost: the model cannot run SQL queries through the server, including read-only queries against the recorder database. The alternative is to leave it allowed and declare it as a borderline service: only `sqlparse` SELECT statements run, the session is closed without a commit so a PostgreSQL data-modifying CTE is rolled back, and what is left is a SELECT-callable function with side effects on PostgreSQL (for example `pg_terminate_backend`) and a connection to an arbitrary SQLite path, which can create an empty file; the bound is houses where the `sql` integration is set up.
18. **Dispatch services**: `conversation.process`, `google_assistant_sdk.send_text_command` and `alexa_devices.send_text_command` are refused by name, directly and when walked. Cost: the model cannot send text commands to Assist, Google Assistant or Alexa. The alternative for the last two is to allow them and declare them as a residual, bounded to houses where `google_assistant_sdk` or `alexa_devices` is set up and the assistant is linked to Home Assistant with exposed entities (switches and scenes are exposed by default).
19. **Media-player fields read strictly**: `tts.speak` (`media_player_entity_id`), every legacy `tts` say service (`entity_id`, wherever it stands: data, `target` or step level), `camera.play_stream` (`media_player`) and `google_assistant_sdk.send_text_command` (`media_player`) are on the inline-entity list. This holds in these fields only. Their other fields follow the ordinary rule: a templated `message` is allowed, and a templated mapping key is refused. Cost: in a house with a denied media player (a `universal` one) `all` is refused, and a computed media-player field (a template in that field) cannot be used in these services; announcements with a templated message are not affected. The alternative is to declare the gap as a residual bounded to houses with a `universal` player that has a `play_media` command, which leaves a model able to run that player's configured command through `tts.speak` with `all`.
20. **Trim and whitespace**: every trim in the policy is Python's `str.strip()` set (D3), not JavaScript's. A whole data string that starts or ends with a character of that set that the small parser does not skip (`\v`, `\x1c` to `\x1f`, `\x85`, `\xa0`, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F, U+3000) is refused although Home Assistant would use it. Cost: rare and safe. The alternative is to teach the small parser to skip the whole set, which is a longer parser rule for no everyday gain.
21. **The lists are open-ended**: the service, platform and dispatch lists name the routes found in Home Assistant Core 2026.10.2; custom integrations and later Core versions were not searched. The owner accepted this residual on 2026-10-22: when a route is found it is added to the relevant list, and the lists are re-checked on each Home Assistant upgrade. Services added by a later Core release are the same residual.
22. **`media_extractor.play_media`** is blocked by name, directly and when walked. It forwards area, device, floor and label targets to `media_player.play_media`, so a `universal` player in a targeted room would run its configured command while the entity checks see nothing to judge. Cost: the model cannot play extracted media (a video or stream URL) on a media player through the server. The alternative is to allow it and declare it as a residual with the other services that act on other domains through area targets, bounded to houses where `media_extractor` is configured and a room holds a `universal` player.

## Consequences

- A request that would restart Home Assistant, purge history, touch backups, add-ons or the host, reboot or shut down a NAS, a container or a machine through a service that names a device, run a shell command or a Python script, profile the running process, open a debugger port, run SQL, play extracted media through area targets, or hand text to Assist, Google Assistant or Alexa is refused with a message that says the server blocks it and nothing was sent. This holds for the service named directly and for every route listed in the problem statement, in the automations the server writes and triggers as well.
- Everyday control (lights, climate, locks, covers, ordinary scripts and automations) keeps working. The costs are: calls that act on an entity of a denied platform (template, command-line, universal, Wake-on-LAN, Panasonic Viera, Supervisor, Portainer, Proxmox) are refused, including `entity_id: all` for a domain that contains one; scripts that use `group.set` or `scene.create`, scripts with computed targets or with notify services that are not allowlisted, config-category buttons, device steps outside the known domains, and registry ids as targets cannot be used through the server, and, rarely, a whole `data` string that works in Home Assistant but uses a negative number, a comment after its first token, a string prefix, a duplicate key, a leading `#` or backslash, or a leading or trailing whitespace character that only Python strips is refused; `all` in a media-player field of `tts.speak`, the legacy `tts` say services or `camera.play_stream` is refused in a house with a denied media player, and so is a templated value in that field (a templated `message` is allowed); extracted media cannot be played through `media_extractor.play_media`; a group that is unavailable, or that has a stale or disabled member, is refused (the first although Home Assistant would skip it), and a request that reaches more than 10 forwarding groups, or more than 10 groups and scenes together, is refused as too large; `entity_id: all` on scripts or automations is refused past 20; the server is read-only in effect while the WebSocket is down; an upsert of a new id can be refused when Home Assistant is slow.
- Every write or trigger that names an entity opens one WebSocket connection first, so it needs the same connection the registry tools need. If the WebSocket cannot be opened from the Worker in production, the guarded writes cannot be used and the owner decides on a degraded mode.
- Release note: "The server now refuses system actions (restart or stop Home Assistant, purge history, backups, add-ons, shell and Python commands, remote-access disconnect, installing updates, changing the home location, rebooting or shutting down a NAS or a machine and recreating a container through their device services, profiling the running process, opening a debugger port, running SQL queries, playing extracted media, handing text to Assist, Google Assistant or Alexa), including when they are reached through scripts, scenes, automations, blueprints, groups or entities that run configured actions. Set `ALLOW_SYSTEM_ACTIONS` to `true` to turn this block off. Set `ALLOWED_NOTIFY_SERVICES` to list legacy notify services the model may call (it applies with the block on or off)."

## Amendment, 2026-10-23: the server's own notify call is checked, and the capture rule gains a prefix

Two statements above are changed by the delete confirmation record (0017).

- D2 said: "The server's own notify call for a delete code is not a model call and is not checked." That no longer holds. The setting that names the notify service for delete confirmation codes now exists (`DELETE_CONFIRMATION_NOTIFY_SERVICE`). Every delete call checks that the service is a usable name and is on the same effective allowlist the policy applies to a model's call, by the same function (`allowedNotifyServices`), and refuses otherwise. When `ALLOWED_NOTIFY_SERVICES` is absent, the allowlist is that one service, but only when its name is valid and is not `send_message` or `persistent_notification`; a blank, invalid or unsupported value adds nothing. The rule that a set `ALLOWED_NOTIFY_SERVICES`, even an empty text, is the whole list is unchanged, and the test for absent versus empty can now tell the cases apart.
- D10's capture event types were `call_service` and `*`. The rule also refuses an event trigger or `wait_for_trigger` step whose type, after the same strip and lower-casing, starts with `mobile_app_notification` (the companion app's received, cleared and action events, and any later type with that prefix), because the app can put notification text in them. It applies wherever the capture rule applies. An automation written through the server therefore cannot listen for those events; automations written in Home Assistant itself are not examined. The prefix is `CAPTURE_EVENT_PREFIX` in `src/policy/lists.ts`.

## Amendment, 2026-10-23: an undo through this server is checked too

The policy checks every automation write, and an undo is a write. Saving a returned `previous_config` or `deleted_config` again is therefore refused when that config holds something the policy refuses, even though the change being undone was allowed. Examples are a legacy notify call that is not on the allowlist, a device step of an integration that is not on the accepted list, a trigger the capture rule refuses, and a blueprint instance while the WebSocket is down. The legacy-notify rule and the capture rule apply even with the system-action block off. In that case the owner restores the returned config in Home Assistant's own automation editor. This is an accepted residual of the decision above; the README section "What writes change" says the same to the person who needs it.
