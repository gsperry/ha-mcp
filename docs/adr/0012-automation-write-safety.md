# 0012. Automation write tools: how an automation save or delete is made safe

Date: 2026-10-22
Status: Accepted

## Context

### Problem

Two tools change the house's automations: `upsert_automation` creates or fully replaces one, and `delete_automation` removes one. Both act on data that the household owns and that Home Assistant does not version. A save replaces the whole stored automation, and the answer to a save or a delete is only `{"result":"ok"}`. Four things can go wrong silently:

- **Stripped keys.** The MCP SDK hands the tool handler the parsed output of its zod schema. A plain object schema removes every key it does not declare, at every depth, so a get-modify-save would permanently delete `variables`, `max`, `trace`, `trigger_variables`, `use_blueprint` and anything newer. Each later edit would start from the reduced config.
- **Wrong target.** A body `id` overrides the id in the URL, so the automation is stored under a different key than the caller thinks. An id that already belongs to an automation defined outside `automations.yaml` (a YAML package) is appended to the file as a duplicate, which Home Assistant answers with success and then ignores forever.
- **A confirmation that confirms nothing.** Home Assistant writes the file, answers, and only then reloads the automation in the background. An immediate read of `/api/states` can miss a new automation, and on an update the old entity is still there until the reload replaces it. A caller told "saved" may be told something false.
- **Losses beside the config.** A delete drops the entity's area, labels, categories and custom entity id from the entity registry, and the first write rewrites `automations.yaml` from a parsed copy, which drops hand-written comments.

This server is stateless. Every tool call runs in a fresh Worker request, keeps nothing between calls, and opens its own connections to Home Assistant. Whatever protects a write therefore has to happen inside one call, and the only undo that can exist is the previous config handed back in the result.

This ADR decides the automation config schema, how ids are chosen and guarded, what order the calls to Home Assistant are made in and where the point of no return is, how each failure is reported, what the results contain, and what happens when the WebSocket (needed for the entity registry) cannot be used. It also states what cannot be guaranteed.

### Behaviour of the last release

There is no release. Before this server was built, the repository had no write tool: the original design note (`plan.md` as first written, before its dated correction note) only described one. It said that `upsert_automation` would take "a JSON config (alias, description, triggers, conditions, actions, mode)" and generate an id if none was given (line 61), that `DELETE` "removes it and reloads" (line 80), that the id is "any string you choose" such as a timestamp (line 78), and that the zod `AutomationConfig` would have "alias required, triggers required, the rest optional" (line 143). It said nothing about ids that belong to non-file automations, the body `id`, confirmation, failure reporting, previous values, registry metadata or comments in `automations.yaml`. It told the implementer to fall back to REST-only tools if the WebSocket failed (line 163). So every residual below is marked "no tool existed".

This ADR departs from that note in these ways, each recorded under Decision: the schema is looser (single items, string conditions, blueprints, alias optional); a body `id` is dropped; a generated id carries six random digits after the timestamp; a new id is checked against the entity registry and `/api/states`; the tool reads before it writes and returns the previous config; a new automation is confirmed by polling; a delete reads the config first and reports what the registry loses; every failure says how far the call got; and a failing WebSocket gets a narrow fallback instead of disabling the tools.

## Options considered

1. **Narrow zod schema as in the original note (alias required, arrays of objects).** Rejected: it deletes every key it does not declare, rejects valid single-item and blueprint automations that `get_automation` just returned, and makes a model rewrite the owner's config to get it accepted.
2. **Validate the automation in the tool (trigger platforms, service names, entity ids).** Rejected: Home Assistant validates on save and its message is better; a copy of its rules would drift and would either strip keys or refuse valid configs.
3. **Use the body `id` as the target.** Rejected: it silently turns "edit automation A" into "write automation B" whenever the two differ. The body `id` is dropped and a warning says so.
4. **Pure millisecond timestamp for a generated id.** Rejected: Workers advance their clock only after I/O, so two parallel creates can read the same millisecond, both see 404, and the second silently replaces the first. Parallel calls make sharing a millisecond likely, so the suffix has to carry the uniqueness: six random digits make two such calls collide about one time in a million. Home Assistant treats the id as an opaque string.
5. **Always fail closed when the registry read fails.** Rejected by the owner: it ties the main use case, creating an automation, to a WebSocket path that is unproven from Workers.
6. **Always fall back to `/api/states` when the registry read fails.** Rejected by the owner: a caller-supplied id that belongs to a registry-disabled package automation has no state, so it would be appended as a duplicate that never loads.
7. **Skip the collision guard and let Home Assistant sort it out.** Rejected: Home Assistant answers 200 and ignores the duplicate entity; the file is left with a dead entry that no later call can detect.
8. **Confirm a new automation by one state read right after the write.** Rejected: the reload runs after the response, so the read usually misses it. A bounded poll costs wall time, not extra writes.
9. **Confirm an update by polling states.** Rejected: the old entity keeps the id until the reload replaces it, so the poll matches at once and proves nothing. The config re-read, which reads the file under the lock, is the confirmation for updates.
10. **Compare the sent config with the stored one and warn on a difference.** Rejected: Home Assistant imposes key order, adds the `id` key and may rename singular keys, so a correct write would almost always warn. Both values are returned and the caller sees them.
11. **Optimistic concurrency (an argument carrying the config the caller last read).** Rejected for now: Home Assistant offers no compare-and-set, so the tool would still read then write with a window, and it adds an argument to a tool whose contract is "full config in, previous and current out". It is the recommended follow-up if concurrent edits matter.
12. **Retry a write or a delete whose outcome is unknown.** Rejected: a repeated write can be applied twice and each repeated 401 is a failed login. The error tells the caller how to find out and how to repair.
13. **Poll after a delete to confirm the entity is gone.** Rejected: the delete answers only after the file is written under the lock, and the removal is a background step that adds no failure the caller could act on.
14. **A tool that asks Home Assistant for a restart or for `check_config` after each write.** Rejected: `check_config` does not see individual automations, and the write's own 400 is the real validation.

## Decision

Rules for `upsert_automation` and `delete_automation`, in the order they act.

**D1. The automation config schema is loose at every depth.**
`AutomationConfig` in `src/ha/schemas.ts` is `z.looseObject`. Declared keys:
- `alias` and `description`: optional; any scalar (HA's `cv.string` coerces numbers and booleans), so the tool does not insist on a string. Null is not a scalar here: Home Assistant's `cv.string` refuses it (`ha:homeassistant/helpers/config_validation.py:653-668`), so a null `alias` or `description` is refused by the tool's schema and nothing is sent.
- `mode`: optional, one of `single`, `restart`, `queued`, `parallel`.
- `triggers` and `trigger`: each null, a loose record or an array of loose records.
- `actions` and `action`: each null, a loose record or an array of loose records.
- `conditions` and `condition`: each null, a string (template shorthand), a loose record, or an array whose elements are strings or loose records.

Null is accepted for these list keys because `get_automation` can return a stored config that has it, and because `ensure_list` is expected to turn it into an empty list. That last step is outside the pinned source: `ensure_list` is `probatio.EnsureList()` (`ha:homeassistant/helpers/config_validation.py:314`), from a package that is not in the clone (`ha:requirements.txt:41`). If Home Assistant refuses a null list, it answers 400 and nothing is stored, so the worst case is a refusal that carries its own message. No declared key has a `.default()`, so the tool never adds a key the caller did not send.
- `use_blueprint`: an optional loose record.

At least one of `triggers` and `trigger` and at least one of `actions` and `action` must be present as a key (its value may be null) unless `use_blueprint` is present; that refusal is a tool error naming the requirement and sends nothing. Every other key (`variables`, `trigger_variables`, `max`, `max_exceeded`, `trace`, `initial_state`, `hide_entity` and anything added later) passes through unchanged, as does every key inside a trigger, condition or action record. No plain `z.object` appears anywhere between the tool argument and the request body. The tool does not check anything else: not the trigger platform, not the service, not whether both `trigger` and `triggers` are present (Home Assistant refuses that, `ha:homeassistant/helpers/config_validation.py:1024-1047`). Home Assistant also refuses a top-level key it does not know (`ha:homeassistant/helpers/script.py:298-318`); the tool sends it anyway and passes Home Assistant's 400 message back, and nothing is stored. The advertised input schema keeps `additionalProperties` open (`fw:src/server/zod-json-schema-compat.ts:33-36`).

**D2. Id handling.**
`upsert_automation` takes an optional `id` and a required `config`. `delete_automation` takes a required `id`.
- A body `id` (top level only; `id` keys inside triggers are trigger ids and are left alone) is removed before anything else. If it was present and, compared as strings (so a numeric body `id` equal to the argument matches), the `id` argument is absent or different, the result carries a warning `body_id_ignored` that says which id was used and that an existing automation is edited by passing its `id` argument.
- An `id` argument is any non-empty string. It goes into the URL through `pathSegment`, which refuses an empty value, `.` and `..` and encodes everything else. The tool adds no format rule of its own, because package automations use arbitrary ids and a new refusal would be a new hard error.
- With no `id` argument the tool generates one: the current time in milliseconds as a decimal string followed by six random decimal digits from the platform's random source, zero-padded (nineteen digits in all). The id is built by joining the two pieces as text and is never computed as a number, because nineteen digits exceed 2^53 and a number would lose precision. The tool text says "omit `id` to create a new automation". If the config read for a generated id answers 200, the id already exists: the call stops with an error and nothing is written, and a new call generates a new id.

**D3. The collision guard.**
It applies only when the config read for the id answers 404, that is, to a new id. An id whose config read answers 200 is an existing automation in `automations.yaml` and needs no registry check (an edit cannot create a collision). For a new id, before any write:
1. The entity registry read, over the WebSocket (`config/entity_registry/list`, one command). An entry counts when its `platform` is `automation`, its `entity_id` starts with `automation.` and its `unique_id` equals the id. This catches enabled package automations, registry-disabled ones (no state), and orphaned entries. A match refuses the call.
2. The `/api/states` read. An automation state whose `id` attribute equals the id refuses the call.
A refusal is an error that names the entity found and says that an automation from a YAML package or another file cannot be edited through this server, that an id is created by omitting `id`, and, always, that this can also be a leftover entry of a UI automation that was removed from `automations.yaml` by hand (a false positive for a caller-supplied id; the owner removes the entry in Home Assistant). The hint is always included because the registry check runs before any state is read, and because an enabled orphaned entry has a restored `unavailable` state carrying the `id` after a restart or reload (`ha:homeassistant/helpers/entity_registry.py:476-501`, `ha:homeassistant/helpers/entity_registry.py:2827-2837`), so a match cannot be classified as "package" or "leftover" from what the tool has read. A failure to read `/api/states` fails the call before any write, in every mode: there is no weaker guard than this one.

**D4. When the registry read fails: the narrow fallback.**
The owner decided on 2026-10-22: edits need no registry check; a new caller-supplied id fails closed; a generated id falls back to `/api/states` with a warning; a delete proceeds with a warning. This rule says exactly which failures count.

| What `haWsCommands` did | Class | New caller-supplied id | New generated id | Delete |
|---|---|---|---|---|
| Answered | normal | guard applies (D3) | guard applies | metadata reported |
| Rejected with code `auth_invalid` or `unauthorized` | credentials | fail closed, error naming token revoked, user not an administrator, user local-only; nothing written | same | same: no DELETE |
| Any other rejection: the upgrade `fetch` failed (network error), the upgrade gave no socket, the 10 s limit passed, the socket closed or reported an error before the answer, a send threw, a message was not valid JSON, an unexpected message arrived during authentication, Home Assistant answered with another error code, or the result was not a list | transport | `registry_check_unavailable` error, nothing written | continue with the `/api/states` check alone and a `registry_check_unavailable` warning | continue with `lost_registry_metadata: null` and the warning |

The rest of the reasoning: the registry read is a read, so a failure of the transport has changed nothing and the tool does not retry it (a retry could repeat a failed login). The REST config read always runs first with the same token, so a bad token has already failed there as a 401 with its own message (`ha:homeassistant/components/http/decorators.py:76-81`, `ha:homeassistant/helpers/http.py:99-100`); `auth_invalid` or `unauthorized` over the WebSocket after a successful REST call means the credentials changed between the calls or the WebSocket path rejects them, and the safe reaction is to stop. The fallback is sound for a generated id because the id is a nineteen-digit number that no package automation uses, so the check it skips (a registry-disabled package automation, which has no state) cannot match. The fallback is not sound for a caller-supplied id, which is why that case fails closed. The error for the caller-supplied case says: "omit `id` to create a new automation, or retry when the entity registry can be read". The text always includes the sentence about an earlier call whose outcome was unknown: the caller should first call `get_automation` with the id after waiting about 30 seconds (a rule of thumb, D7): if the config exists, the earlier write landed and edits of that id need no registry check; if it does not exist, the earlier write did not land and omitting `id` is safe. It is always present because the server is stateless and cannot know whether the id came from an earlier call with an unknown outcome. It is the same instruction as in D7. A failing fetch in the upgrade is not an `HaWsError`; the classifier treats every rejection that is not an `HaWsError` with one of the two credential codes as transport.

**D5. Order of calls for `upsert_automation`, and the point of no return.**
1. Validate the arguments (D1, D2). No network.
2. `GET /api/config/automation/config/<id>`: 200 means update and gives `previous_config`; 404 means create and `previous_config` is null; any other answer or failure stops the call.
3. Create only: the registry read (D3 step 1, D4).
4. Create only: the `/api/states` read (D3 step 2).
5. **Point of no return: `POST /api/config/automation/config/<id>`** with the config minus the body `id`. Nothing earlier changes Home Assistant. Every refusal in D1 to D4 happens before this call.
6. `GET /api/config/automation/config/<id>` again (the confirmation, D6).
7. Create only: the state poll (D6).
The tool keeps a stage variable: `before_write` until the POST is started, `write_in_flight` while it is outstanding, `write_acknowledged` once Home Assistant answered 2xx. No call is ever repeated.

**D6. Confirmation.**
- Both create and update are confirmed by the config re-read, which Home Assistant answers from the file, freshly read under the lock (`ha:homeassistant/components/config/view.py:89-91`, `ha:homeassistant/components/config/view.py:161-166`). The `config` in the result is what that read returned, not what was sent. The tool does not compare the two (Option 10).
- A **new id** is then polled: `/api/states` is read, the automation whose `id` attribute equals the id is looked for, and if absent the tool waits one second and reads again, up to six reads. No read starts more than 5 s after the first read started: the elapsed time is checked after each one-second wait, and a read that would start later is not made (the result is then `entity_not_found`, as after six reads), so slow but successful reads cut the poll short instead of stretching it. Each read is limited to the smaller of 4 s and the time left of the overall budget (D11). A match gives `entity_id` and `state`. State `unavailable` adds the warning `unavailable`: Home Assistant stored the automation but could not load it (for example a blueprint is missing); the reason is in its log. If no match appears the result has `entity_id: null`, `state: null`, the warning `entity_not_found` and a note: the automation may still be loading, Home Assistant may have ignored a duplicate id, a registry entry removed earlier may have been restored as disabled (`ha:homeassistant/helpers/entity_registry.py:1601-1633`, `ha:homeassistant/helpers/entity_platform.py:1177-1185`), a configuration error elsewhere may have stopped the reload (`ha:homeassistant/helpers/entity_component.py:351-375`), or the automations file may not be included by the Home Assistant configuration (a first deployment). A poll that ends with `state_unconfirmed` (D6, last bullet) also carries a note, which begins the same way and says the state could not be confirmed and `list_automations` shows whether it loaded. The `entity_not_found` note begins "The automation is stored; do not create it again", says to run `check_config` if it does not appear, and names the not-included file as a cause (the owner then adds the `automation` include for `automations.yaml`).
- An **update** is not polled, because the old entity keeps the id until the reload (`ha:homeassistant/components/automation/__init__.py:1209-1229`). Its result has `entity_id: null`, `state: null` and a note saying that Home Assistant reloads in the background and that `list_automations` shows the loaded state after a moment. The note adds that a configuration error elsewhere in Home Assistant can stop the reload, in which case the old automation keeps running with the old behaviour although the new config is stored; if the change does not take effect, run `check_config`, fix what it reports, and make the call again (an unchanged config reloads once the error is gone). The state cannot show this, because the old entity is still on or off (`ha:homeassistant/helpers/entity_component.py:351-375`).
- A failure during the poll is not a failure of the call: the write and the config re-read already succeeded. The poll stops, the result carries the warning `state_unconfirmed` with the message of what failed, and nothing is repeated. This includes Home Assistant going down, a 5xx from the proxy and a 401.

**D7. Failure reporting by stage.**
Every failure becomes a thrown error whose message says the stage, the id and what is known, because only the message reaches the caller (`fw:src/server/mcp.ts:271-278`, `fw:src/server/mcp.ts:290-299`). From `write_in_flight` onward the message contains the previous config (or says that there was none) as compact JSON.

| Failure | Stage | What the error says |
|---|---|---|
| Argument refusal, `pathSegment` refusal, missing triggers or actions | `before_write` | Nothing was sent. |
| Config read: 401 or 403, any other status, timeout, network failure, a corrupt `automations.yaml` (Home Assistant answers 500) | `before_write` | Nothing was changed. A 401 carries the credentials hint and a 403 the message about a banned address (0002); neither is repeated. |
| Generated id already exists; guard refusal; `registry_check_unavailable` for a caller-supplied id; credential failure on the WebSocket; failed `/api/states` read | `before_write` | Nothing was changed; the specific reason (D3, D4). |
| POST answered 400, 401, 403 or 404 | `write_in_flight`, refused | Home Assistant refused the write and nothing was stored: validation and the administrator check run before the file is touched (`ha:homeassistant/components/config/view.py:101-124`, `ha:homeassistant/components/http/decorators.py:76-81`). A 400 carries Home Assistant's own text. |
| POST answered 5xx (including a proxy 502 or 504), or no answer (timeout, connection dropped) | `write_in_flight`, outcome unknown | The write may not have happened, may have happened completely, or may have reached the file without the reload: Home Assistant cancels a handler when the client goes away, but the file write already running in the executor can finish, and the reload is created only after it (`ha:homeassistant/components/http/server.py:540-542`, `ha:homeassistant/components/config/view.py:128-139`). The error carries the id and the previous config and says: **ask the user to wait at least 30 seconds, or to confirm that nothing else is saving automations, before any further write, by this server or in the Home Assistant interface**, because an abandoned write can still be running and can overwrite a later change (D10). The 30 seconds is a rule of thumb, not a bound: `fsync` can block "a few seconds or longer" (`ha:homeassistant/util/file.py:25-29`), and a model has no timer, so in practice the human waits or confirms. Then read the automation with `get_automation`. If the stored config is the one you sent, call `upsert_automation` again with the same `id` and config, which is safe (it replaces the same automation and makes Home Assistant reload it). **Update:** if the stored config is still `previous_config`, the write did not land and the same call is safe. **Create:** if `get_automation` does not find it after the wait, the write did not land: create it again with the same `id` when the registry can be read (a call with an id that is not stored and not in the registry is idempotent), or without `id` when the call is refused with `registry_check_unavailable`. Do not omit `id` before waiting and looking, because a late write would then leave two copies. A failed file write is a 500 and does not store anything (`ha:homeassistant/util/file.py:34-43`), but the caller cannot tell it from the cases above, so it gets the same message. |
| POST answered 2xx, then the config re-read failed or answered 404 | `write_acknowledged` | Home Assistant acknowledged the write; only the confirmation failed, so the automation is probably stored. For a 404, another client may have deleted it, or it is stored under another key. The error carries the previous config. |
| Poll failure | after the write | Not an error: D6, warning `state_unconfirmed`. |

The tool never opens another connection to find out what happened and never repeats a call. If the Worker itself is stopped before it returns, none of this is reported (D13).

**D8. `delete_automation`.**
1. `GET` the config. A 404 is an error naming the id: it is not stored in `automations.yaml`, so it either does not exist or is defined elsewhere (see `list_automations`); no DELETE is sent. Other failures stop the call (stage `before_delete`).
2. Read the entity registry (one WebSocket command) and find the entry as in D3 step 1. The result is informational, not a guard. D4 gives the failure behaviour: credential failures stop the call with no DELETE; any other failure continues with `lost_registry_metadata: null` and a `registry_check_unavailable` warning. No matching entry gives `lost_registry_metadata: null` and a note that the automation has no registry entry.
3. **Point of no return: `DELETE /api/config/automation/config/<id>`.** Home Assistant writes the file under the lock and answers after the write (`ha:homeassistant/components/config/view.py:141-159`).
4. Return `{id, deleted_config, lost_registry_metadata, warnings, note}`. `lost_registry_metadata` is `{entity_id, area_id, labels, categories, name, icon, disabled_by, hidden_by, options, aliases}` from the registry entry (`options` holds, for example, voice-assistant exposure; `aliases` comes from the extended entry, which is not in the list, so it is reported only when the list carries it), which is what the registry removal drops (`ha:homeassistant/helpers/entity_registry.py:1746-1767`). The note says that the entity and registry entry are removed in the background after the answer. `deleted_config` is the config exactly as read in step 1, the undo.
Failures at the DELETE: a 400 means the entry was already gone (another client removed it between the read and the call), nothing was deleted by this call. A 401, 403 or 404 is reported as refused with nothing removed, as for the save (D7). A 5xx or no answer means the outcome is unknown, and the remedy differs from a save. The file entry may be gone while the hook never ran, because a cancelled handler does not create it (`ha:homeassistant/components/config/view.py:150-157`, `ha:homeassistant/components/config/automation.py:31-40`): the entity keeps running and its registry entry stays. Repeating the delete then fails with 404 ("defined elsewhere"), and restoring the same id is refused by the guard because the registry entry and state remain. The error carries the id, `deleted_config` and the registry metadata read in step 2 (so a restore without `id` can re-apply it), and says: **ask the user to wait at least 30 seconds, or to confirm that nothing else is saving automations, before any further write** (a rule of thumb, as in D7), then call `get_automation` with the id, and follow the first branch that fits:
- It returns the config with `editable: true`: the delete did not happen; repeat it if still wanted.
- It finds nothing (an error that no config and no state exists) and `list_automations` does not list the id: the delete completed (the handler ran, only the answer was lost) and nothing more is needed. Restoring `deleted_config` without `id` is only for undoing the delete; removing the registry entry is the cleanup when the delete was wanted, and none exists here.
- It returns the config with `editable: false`, or `list_automations` still lists the id: the file entry is gone and Home Assistant did not finish. Run `call_service` with `automation.reload` and `data: {"id": "<id>"}`, which stops only that automation and leaves every other one untouched (a reload without data removes and re-creates every automation, including hand-written ones that were given a random id by the first write, and restarts them; `ha:homeassistant/components/automation/__init__.py:1150-1194`, `ha:homeassistant/components/automation/__init__.py:1209-1229`). If that call answers an error, a configuration error elsewhere has stopped the reload (`ha:homeassistant/helpers/entity_component.py:351-375`; over REST it is a 400 with Home Assistant's text, `ha:homeassistant/components/api/__init__.py:442-467`): run `check_config`, fix what it reports, and reload again; until then the automation keeps firing. After a successful reload the id can stay listed as `unavailable` (the restored state of its enabled registry entry, `ha:homeassistant/helpers/entity.py:1455-1500`) until the registry entry is removed: that is expected and is not a reason to reload again. Then either remove the leftover registry entry in Home Assistant (Settings, Entities) if the delete was wanted, or undo the delete by calling `upsert_automation` with `deleted_config` and without `id`, which creates a copy under a new id, and re-apply the registry metadata from the error by hand. Restoring without `id` before the reload would leave two running copies, and a restore with the same `id` is refused by the guard while the registry entry remains.

The description of `delete_automation` says that the area, labels, categories, name, voice-assistant options, aliases and custom entity id are removed from the registry, that Home Assistant keeps the removed entry for 30 days and restores it if an automation with the same id is created again (`ha:homeassistant/helpers/entity_registry.py:1601-1633`, `ha:homeassistant/helpers/entity_registry.py:94`), that this server does not rely on or promise that, and that `lost_registry_metadata` is what to re-apply by hand.

**D9. What the results contain.**
`upsert_automation` returns compact JSON with keys in this order: `id`, `previous_config` (null for a create), `config`, `entity_id`, `state`, `warnings`, `note`. `entity_id` and `state` are null for an update and, with a note, when the poll found nothing. `warnings` is an array of `{code, message}`; the codes are:
- `unavailable` (D6);
- `entity_not_found` (D6);
- `state_unconfirmed` (D6);
- `registry_check_unavailable` (D4);
- `body_id_ignored` (D2);
- `automations_file_rewritten`, present on every successful write and delete: Home Assistant rewrites the whole of `automations.yaml` from a parsed copy, which drops hand-written comments and formatting, gives an entry that has no `id` a random one, and may write tags such as `!include` or `!secret` out differently (`ha:homeassistant/components/config/view.py:244-257`, `ha:homeassistant/components/config/automation.py:91-92`; the tag behaviour is unverified). The server is stateless and cannot know whether this is the first write, so every result carries it.
The undo for an update is calling `upsert_automation` with the same `id` and `previous_config` (its body `id` is dropped). The undo for a create is `delete_automation`. The undo for a delete is `upsert_automation` with the same `id` and `deleted_config` (after an interrupted delete, follow D8 instead); in the degraded mode that call is refused (D4), and the result says so (S27).

**D10. Concurrency with the Home Assistant UI: last write wins, and the tool says what it can.**
Home Assistant serialises the requests of this endpoint with one lock and each request re-reads the file inside it (`ha:homeassistant/components/config/view.py:51`, `ha:homeassistant/components/config/view.py:128-132`). While every handler runs to completion, a save of one automation cannot erase another automation's entry. That holds only until a handler is cancelled: a POST or DELETE whose client gave up leaves the lock while its file write can still be running, so a later save can read the old file and be overwritten when the abandoned write lands last (`ha:homeassistant/components/http/server.py:540-542`, `ha:homeassistant/core.py:871-882`). This is why the unknown-outcome errors say to wait before any further write, and why the write call has a longer timeout (D11). There is also no version and no compare-and-set on one automation. The tool does not claim to prevent a lost update. It guarantees: `previous_config` is what was stored when the first read ran, so an edit made after the caller's own earlier `get_automation` is in `previous_config` and can be merged back; and a change landing between the write and the confirmation read shows up in `config`. It cannot protect an edit made in the window between its first read and its POST (a few round trips), which is overwritten and appears in no result, or an editor left open in a browser that saves later. Three more windows are declared: a delete reads the config, another client saves a new version, and the DELETE removes that version, so `deleted_config` is the older one and the newer one is in no result; two concurrent creates with the same caller-supplied id are last-write-wins with no dead duplicate (the writer matches by id, `ha:homeassistant/components/config/automation.py:94-96`); and the early lock release above.

**D11. Budget per call.**
- Subrequests (the Workers free plan allows 50): create with a new id, at most 11: config read, registry (one WebSocket), states, POST, config re-read, up to six states reads in the poll. Update: 3. Delete: 3.
- CPU time per call (the free plan allows 10 ms): a create parses the full registry list once and up to seven full `/api/states` bodies (the guard's read and up to six poll reads); a delete parses the registry list once; an update parses only small bodies. The poll stops at the first match, which is normally the first or second read, so the usual cost is the registry list and two or three states parses. These sizes depend on the house and are unmeasured (S29).
- Timeouts: every helper call is limited to 10 s, except the POST and the DELETE, which get 20 s (a delegated choice). The write call is the one where giving up early is dangerous: a cancelled handler releases the lock while its write continues (D10), and the write uses `fsync`, which can take seconds on a busy disk (`ha:homeassistant/util/file.py:25-29`). A normal write takes milliseconds, so a longer limit costs nothing in the normal case and shrinks the window in which a slow write is abandoned. The poll makes at most six reads, starts none more than 5 s after the first read started, and limits each read to 4 s, so on its own it ends within about 10 s: the last read starts at most 5 s after the first and takes at most 4 s, and the window is checked after the following one-second wait, which then stops the poll. The overall budget below bounds it from outside.
- An overall deadline for the steps after an acknowledged write (a choice between shortening the tail and declaring a window; the tail is shortened, because a result that arrives is worth more than a residual that is explained). The MCP SDK's own client gives up on a request after 60 s by default (`fw:src/shared/protocol.ts:106`), and a client that gives up discards the previous config and the warnings with it. The steps before the POST are bounded by 10 + 10 + 10 s, and the POST by 20 s, so the write is acknowledged at 50 s at the latest. The steps after it share a budget of 55 s measured from the start of the call: the config re-read gets the smaller of 10 s and the time left (never less than 1 s), the poll starts no read with less than 1 s left and gives each read the smaller of 4 s and the time left, and a poll that runs out of budget ends as a success with the warning `state_unconfirmed`. The call therefore ends by about 56 s in the worst case, inside the 60 s default. A time source that only advances after I/O is enough here, because the check is made after each I/O step. The budget does not shorten any step before the POST (each of those fails closed on its own limit), and for an update it affects only the re-read.
- Wall time, worst case, when Home Assistant stalls at every step (each limit is per call, not per tool): an update 10 + 20 + 10 = 40 s (the re-read limit stays 10 s because the budget leaves more than that); a delete 10 + 10 + 20 = 40 s; a create, with the WebSocket working or failing, 10 + 10 + 10 + 20 = 50 s to the acknowledged write, then at most about 6 s more (a 5 s re-read, then no poll) because of the deadline, so about 56 s. A normal call takes a few seconds. The tool timeout of the MCP client is not known and is not set by this server; a client with a limit below these figures abandons the call while the Worker may still be mid-sequence, and the remote-access proxy may have a timeout of its own (verification plan).
- The 4 MiB request cap of the SDK bounds the automation size (S26).

**D12. Descriptions, annotations, logging, retries.**
Both tools are registered with `registerTool`, a description saying what they return and when to use them, and `destructiveHint: true` (`readOnlyHint: false`, `openWorldHint: false`). The `upsert_automation` description says that it replaces the whole automation (send the full config as `get_automation` returned it), that a blueprint automation is sent as `use_blueprint`, that `id` is for editing an existing automation from `automations.yaml` and is left out to create one, that automations from YAML packages cannot be edited, that the result has `previous_config` and how to undo, that an unknown outcome is resolved with `get_automation` and then the same call again with the same `id`, and that the caller should keep its own earlier copy until the write is confirmed. No config contents and no token are ever logged. Nothing is retried, and nothing is sent after a 401 or `auth_invalid` (D4, D7).

**D13. Protect the undo from the Worker and the client.**
After the POST, only the confirmation read, the poll and serialising the result remain. The tool serialises compact JSON with no indentation, puts `previous_config` (or `deleted_config`) before `config` so a cut-off result loses `config` first, and includes the previous config in every error from `write_in_flight` onward. If the Worker is stopped before it returns (the CPU limit or memory) or the client cuts the result off, nothing can be reported; this is a declared residual. Automation configs are small, so the CPU risk comes from the states and registry parses, not from the config.

## Consequences

- A save cannot strip keys, cannot be stored under a different id than the one reported, cannot be appended as a dead duplicate of a package automation while the registry is readable, and is confirmed by a read of the stored file. A new automation is confirmed by state, and a failure to load is reported.
- Every write returns the version it replaced, and every failure the tool can observe says how far the call got and carries that version. A delete returns the config and what the registry loses.
- With the WebSocket down, editing and creating with a generated id still work, and the result says the guard was reduced. New caller-supplied ids are refused until it works.
- Costs: a new automation takes up to eleven subrequests and one WebSocket connection instead of one request; a delete takes three; every result carries two copies of a small config and a standing warning about the rewrite of `automations.yaml`. A generated id is nineteen digits, not the thirteen the Home Assistant interface produces.
- Behaviour callers must know, and the tool text says: omit `id` to create; pass `id` to edit; package automations cannot be edited; last write wins; an unknown outcome is resolved with `get_automation` and the same call again.
- Release note: "Automations can be created, replaced and deleted. A replace returns the previous config so it can be undone; a delete returns the deleted config and the registry data that was lost. Automations that come from YAML packages are refused."

## Verification plan

Unit tests use the fetch spy of the test helpers (an unmocked call fails the test) and a fake WebSocket driven through the helper, recording every message. Each test fails against a plain `z.object` schema, an arrays-only schema or a naive implementation. No test touches the network or real credentials.

- D1: a config with `variables`, `max`, `trace`, `trigger_variables` and an unknown future key, with unknown keys inside a trigger, a condition and an action, sent through the full MCP request path, reaches the POST body deeply equal; a single-dict trigger and action and a string condition are accepted and reach the body unchanged; `condition` as a string, a record and an array of both; a blueprint config without triggers or actions is accepted; a config with neither triggers nor `use_blueprint` is refused with nothing sent; a bad `mode` is refused; the advertised input schema leaves `additionalProperties` open at every level.
- D2: a body `id` never reaches Home Assistant, and an `id` key inside a trigger does; `body_id_ignored` appears only when the body id was present and the argument absent or different; `.`, `..` and the empty string are refused with nothing sent; a generated id is thirteen digits of milliseconds plus six zero-padded digits (with a fixed clock and a random source that returns a small number, proving the padding); a 200 on the config read of a generated id stops the call with no POST.
- D3: a package id (state with the `id` attribute) is refused before any POST; a registry-disabled package id (registry entry, no state) is refused; an orphaned registry entry is refused with the false-positive text; an id in the registry under another platform is not a match; an id whose config read answers 200 makes no registry or states read; a failing states read stops the call before the POST.
- D4: one test per row and failure kind: upgrade `fetch` throws, no socket, timeout, close, error event, other error code, result not a list: edit succeeds, caller-supplied create refused with no POST and the "omit id" text, generated create succeeds with the warning, delete succeeds with the warning and `lost_registry_metadata` null; `auth_invalid` and `unauthorized`: all three flows stop with no POST and no DELETE and no retry; exactly one WebSocket connection per call.
- D5: the recorded order for create (config read, registry, states, POST, config read, poll), update (config read, POST, config read) and delete (config read, registry, DELETE); the POST is not sent before every check has passed; nothing is sent twice.
- D6: the re-read value, not the sent value, is returned; a poll that matches on the third read; state `unavailable` gives the warning; six reads and no match give `entity_not_found`; a failing poll read (network, 502, 401) gives `state_unconfirmed` and no further read; an update performs no states read; timers run at a fraction of their length in the tests, and the recorded delays prove the cadence and the 4 s read limit.
- D7: one test per row: refusal, config read 401, 400 with Home Assistant's text surfaced, 401 at the POST, 500, a timeout with the POST in flight (previous config and id in the message, repair text), a failing re-read after the POST (stage text and previous config), a 404 re-read; each asserts the stage text, that nothing is repeated and that the error message carries what the SDK will keep.
- D8: a missing id gives an error and no DELETE and no registry read; the result shape with a registry entry (all fields), with no entry (null and the note) and with the registry failing (null and the warning); a 400 at the DELETE; a timeout at the DELETE gives the unknown-outcome error with `deleted_config`; the description contains the registry warning and the 30-day text.
- D9, D13: result key order with `previous_config` first; compact JSON; the `automations_file_rewritten` warning on every success; the undo round trip (update, then the same call with `previous_config`, ends with the original stored); create then delete.
- D10: two saves of different ids in the fake server do not interact; a UI edit between the first read and the POST is overwritten in the fake and the test asserts what the tool returned (documenting the limit).
- D11: counts of subrequests per flow (11, 3, 3) with the poll at full length; after an acknowledged write that used 50 s of the budget the re-read asks for 5 s, and with 56 s used the re-read asks for 1 s and the poll sends no read and ends with `state_unconfirmed`.
- D12: annotations as registered (`destructiveHint: true`, `readOnlyHint: false`); the description of `upsert_automation` contains "omit `id` to create" and the replace-everything and undo text.
- D7 and D8 unknown outcomes: the message tells the caller to wait at least 30 seconds, or confirm, before any further write, and that this is a rule of thumb; the update text says a stored `previous_config` means the write did not land and the create text says to create again with the same `id`; the POST and DELETE calls use a 20 s limit and every other call 10 s (recorded timer delays); the delete message names `automation.reload` with `data: {"id": ...}`, the three branches (not done, completed, not finished), the reload-error branch with `check_config`, the leftover registry entry, restoring without `id` only as an undo, and carries the registry metadata; the `registry_check_unavailable` text for a caller id says to check `get_automation` first.
- D6 notes: the update note and the `entity_not_found` note contain "a configuration error elsewhere can stop the reload", "check_config", "stored; do not create it again" and the not-included-file cause (a test of the exact text).
- D1: null `triggers`, `conditions` and `actions`, and a numeric `alias`, are accepted and sent unchanged; no key is added to the body that the caller did not send; a numeric body `id` equal to the argument gives no `body_id_ignored` warning.
- D8: the report lists `options`, and `aliases` only when present; an interrupted delete in the fake leaves the entity listed, and the scenario's steps (reload, restore without `id`) succeed against the fake.
- S28: a fake HA that answers 500 to the POST and a `WriteError` text produces the unknown-outcome error with the previous config.

Only a run against the real environment can show:
- whether a client abort during a slow POST or DELETE reaches Home Assistant through the proxy and cancels the handler inside the lock (S35), how long its file write takes on the real disk, and whether a second save made during that time is lost;
- what an interrupted delete leaves behind and whether `automation.reload` and removing the registry entry clear it (S33);

## Amendment, 2026-10-22: time before the write

The safety policy (0016) adds a check of what an automation would run before the first request of `upsert_automation`. That check reads from Home Assistant on one WebSocket connection and has a limit of 10 s, so the steps before the POST can now take 10 + 10 + 10 + 10 s, and the POST 20 s: the write could be acknowledged at 60 s, which is not inside the 55 s budget above and leaves the client at its 60 s limit with the write already made and the previous config lost. The figures in D11 therefore change as follows. Immediately before the POST the tool refuses, with nothing written and a message that says so, when more than 30 s have passed since the call began: 30 s is the 55 s budget less 20 s for the POST and 5 s for the re-read. Without the policy check the steps before the POST end by 30 s at the latest, so the refusal never fired; with it they can end by 40 s. Worst cases with Home Assistant stalling at every step: a create is refused at about 40 s with nothing written, and a create that passes the check is acknowledged by 50 s and ends by about 56 s, as before; an update, which has no registry or states read, is 10 (policy check) + 10 (config read) + 20 (POST) + 10 (re-read) = 50 s instead of 40 s; a delete is unchanged at 40 s, because it is not checked. Every figure stays inside the SDK client's 60 s request timeout. The subrequest counts of D11 are unchanged by this record; the policy's own reads are counted in 0016.
