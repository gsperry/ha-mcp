# 0019. OAuth sign-in for the claude.ai connector, with the owner's password as the only way in

Date: 2026-10-23
Status: Proposed

## Context

### Problem

Until now one static bearer token protects `/mcp` (0005). The owner's claude.ai account is a Team account. On a Team plan an organization Owner adds a custom connector once, and it then appears for every member; with a header credential, "every member's requests carry the same key" and the credential is "the organization's credential, not a person's" (Anthropic, Authentication for connectors, Static credentials in request headers; Add a connector that isn't in the directory, On a Team or Enterprise plan). A header connector would therefore let every member of the organization drive the owner's house: read states, call services, write automations and dashboards.

The owner decided on 2026-10-23 that the server must require sign-in with a password that only the owner knows, so that other members who try to connect cannot pass on their own. The mechanism is OAuth served by the Worker itself, using Cloudflare's `@cloudflare/workers-oauth-provider` (MIT) and a Workers KV namespace. The authorize step is a page that asks for an owner password held in a new Worker secret. Claude Code keeps the existing static bearer header, next to OAuth.

This record decides the library surface, the routes and their answers, how `/mcp` accepts either credential, client registration, the sign-in page and its attempt limit, token lifetimes and revocation, the configuration, the owner's steps and the tests. It does not change the tools, the safety policy (0016) or delete confirmation (0017).

Who the design protects against: other members of the Team organization (they can click Connect and know the URL), the internet at large, and a thief of one access token. It does not protect against a holder of `MCP_BEARER_TOKEN` or `OWNER_PASSWORD`, against someone who can read the Worker's secrets (they also hold the Home Assistant token), or against Anthropic's own infrastructure, which holds the tokens it was issued. It also does not protect against the owner being persuaded to enter the password on a sign-in page that another member started: that member's own claude.ai may then receive the session (residual R15).

### Behaviour of the last release

The published `main` (commit 1dfbb57) has no OAuth. It answers 404 for every path but `/mcp`; 405 with `Allow: POST` for any other method on `/mcp`; 403 for a disallowed `Origin`; 401 with `WWW-Authenticate: Bearer` and an empty body for a missing or wrong bearer; then reads and parses the body once (`src/index.ts`, lines 103-134). It has two secrets that matter here, `MCP_BEARER_TOKEN` and `HA_TOKEN`, and no KV namespace. Every departure below is stated as a departure, and with the OAuth bindings absent the Worker is meant to behave exactly as that release does (D2, "OAuth switched off").

## Options considered

1. **Keep the header connector and rely on the bearer token.** Rejected: every member of the Team organization can use a header connector.
2. **`OAuthProvider` with `apiRoute: "/mcp"`, the static bearer through `resolveExternalToken`.** Rejected: the library would own `/mcp` for every method (`OPTIONS` gets 204 with CORS), the order "method before auth" of 0005 would have to be rebuilt in a wrapper around it, and the hook is proposed for deprecation.
3. **`OAuthAuthorizationServer` plus `OAuthResourceServer` hosting `/mcp`.** Rejected: the resource host answers `OPTIONS`, reflects `Origin` in CORS headers and fixes its challenge text, so a wrapper would still do the work. We want the static bearer checked first and without KV.
4. **Two Workers joined by a service binding (the library's recommended split).** Rejected: a second Worker, a binding and a second deploy for one resource and one user.
5. **Sign-in through an outside identity provider (GitHub or Google) with an allow list of the owner's account.** Rejected: an outside OAuth application with its own secrets and steps for one user; the owner chose a password page.
6. **OAuth written by hand.** Rejected: the two advisories above are exactly the mistakes a hand-written authorize endpoint makes.
7. **Dynamic client registration next to CIMD.** Rejected for now: anonymous callers could write KV (1,000 writes a day on the free plan), Claude registers a new client on every connection, and the registration callback cannot count without a KV write. Kept as the fallback if Claude's dialog cannot use its published identity (Owner confirmation 1).
8. **The library's consent handle for the sign-in page.** Rejected: `beginConsent` writes a KV record on every GET, and the page is reachable by anyone who can build a URL (D4).
9. **A persistent lockout after N failures, in KV.** Rejected: each failure is a write from an anonymous caller, and a lock the attacker can renew locks the owner out of new sign-ins as long as the attack lasts.
10. **A Durable Object counter.** Rejected: an exact global counter, but a new class, binding and migration for a guarantee the password's strength already provides.
11. **A password hash (PBKDF2 or scrypt) instead of a constant-time compare.** Rejected: the secret is already a random value the owner generates, a hash adds nothing against a leak of the secret store, and a meaningful iteration count does not fit the free plan's 10 ms of CPU.
12. **Revocation only by deleting KV keys.** Rejected as the only path: it needs Wrangler and a list of every key, and it acts after the 60 s read cache. The session tag in D5 gives an instant revoke-all by changing one secret.
13. **A cookie double-submit token or the library's handle for CSRF.** Rejected: the password in the form is itself a secret an attacker's page cannot supply; D4 adds an `Origin` rule and anti-framing headers.
14. **Remembered consent.** Rejected: sign-in happens about monthly.
15. **Accept any CIMD client id, checking only the redirect.** Rejected: both `/authorize` and `/oauth/token` would fetch any HTTPS URL an anonymous caller names, including the owner's Home Assistant address, which counts each credential-less request as a failed login. The Worker would be a free request proxy.
16. **`Referrer-Policy: no-referrer` on the sign-in page.** Rejected: under it browsers send `Origin: null` on a form post, which the same-origin rule would refuse every time (D4 uses `same-origin`).

## Decision

### D1. The library, its surface and how it is built

- `package.json` gains one runtime dependency, `@cloudflare/workers-oauth-provider`, pinned exactly to `1.2.4`. It has no dependencies of its own (`wop:package.json:1-51`, no `dependencies` key).
- `OAuthAuthorizationServer` is the library surface: its `fetch` for the metadata and token endpoints, `validateToken` for `/mcp`, and `getOAuthApi(env)` for `parseAuthRequest`, `completeAuthorization` and `authorizationErrorRedirect`. One `OAuthResourceServer` is built only to serve the protected-resource document (its `fetch` is called for that one path and no other, and answers it before it examines any token, `wop:dist/oauth-provider.js:1936-1951`). Its options set `requiredScopes: ["mcp"]`, which is what makes the document carry `scopes_supported` (`wop:dist/oauth-provider.js:1997-2009`); the deprecated `resourceMetadata.scopes_supported` is left unset, because setting both is refused (`wop:dist/oauth-provider.js:262-266`). The resource server's token validator and handler are stubs that nothing can reach, because `/mcp` is never routed to it, and a test proves that. Not used: `OAuthProvider`, `resolveExternalToken`, the consent and upstream helpers, token exchange, enterprise-managed authorization, `purgeExpiredData`, registration.
- A new module, `src/oauth.ts`, holds everything OAuth: the construction, the route handlers, the sign-in page, the session tag and the `/mcp` token check. `src/index.ts` keeps routing and the existing steps.
- The server object is built per request, as the MCP server is (0004), from the request URL and `env`: `issuer` is `url.origin`, `resources` is `[url.origin + "/mcp"]`. The Worker holds no OAuth state at module scope. Reason: the issuer and the resource must be exact, and the Worker does not otherwise know its own address; deriving them from the request means no new setting, and a request that reaches the Worker under another host gets documents and tokens for that host, so a token issued for one host is refused at another (the audience check fails closed). The library accepts only an `https` origin, or an `http` origin on a loopback host, and throws a `TypeError` for any other (`wop:dist/oauth-provider.js:959-964`, `wop:dist/oauth-provider.js:972-974`, `wop:dist/oauth-provider.js:1987`, `wop:dist/oauth-provider.js:2744-2746`). `src/oauth.ts` therefore checks the origin before it builds anything: `https`, or `http` with the host `localhost`, `127.x.x.x` or `[::1]` (what `wrangler dev` serves). For any other origin, and if the construction throws anyway, OAuth is treated as off for that request (D2): every OAuth path is 404 and `/mcp` takes the static bearer only. That answer is deterministic and fails closed, and a refused construction is logged as `{ event: "oauth_error", category: "configuration" }`. The construction is option validation only. If measured CPU per request makes it matter (verification plan), a one-entry memo keyed by origin is allowed without a new record.
- Options set: `scopesSupported: ["mcp", "offline_access"]`; `clientIdMetadataDocumentEnabled: true`; `accessTokenTTL: 3600`; `refreshTokenTTL: 2592000` (both written out, so a library default change moves nothing); `tokenExchangeCallback` (D5); `onError` that logs `{ event: "oauth_error", status, code, category, reason }` and nothing else, and returns nothing so the library's response stands. `onError` covers error responses only; the library's direct `console.warn` calls are outside it (see D4, Logging). Not set: `clientRegistrationEndpoint` (so no `registration_endpoint` is advertised), `allowTokenExchangeGrant`, `allowPrivateUseRedirectUris`, `refreshTokenIdleTTL`. The endpoints keep their defaults, `/authorize` and `/oauth/token` (`wop:docs/authorization-server.md:9`).

### D2. Routes, methods and the `/mcp` gate

**What exists.** When OAuth is on (below), exactly five paths exist; every other path, including `/`, `/mcp/`, `/register`, `/.well-known/oauth-protected-resource` (no suffix) and `/.well-known/openid-configuration`, answers 404 with an empty body, as now. The protected-resource document is served only at the path-suffixed URL that the 401 names, because a document for resource `https://.../mcp` served from the root URL would not match the URL it was fetched from (RFC 9728, section 3.3).

| Path | Methods and answers | Served by |
|---|---|---|
| `/mcp` | `POST` as today (D2 gate below). Any other method: 405 with `Allow: POST` and an empty body, before authentication, so a GET never draws a 401. | `src/index.ts` |
| `/.well-known/oauth-protected-resource/mcp` | `GET` and `HEAD`: 200, `application/json`, `{ resource, authorization_servers: [issuer], scopes_supported: ["mcp"], bearer_methods_supported: ["header"], resource_name: "ha-mcp" }`. `OPTIONS`: 204. Other methods: 405 with `Allow: GET, HEAD, OPTIONS`. The same answers as the authorization server document, from the library's own code, so the JSON is not hand-written and the library checks the spelling of the resource and the issuer. | the library (`OAuthResourceServer`, metadata path only) |
| `/.well-known/oauth-authorization-server` | `GET` and `HEAD`: 200 with the library's document; `OPTIONS`: 204; other methods: 405 with `Allow: GET, HEAD, OPTIONS` (`wop:dist/oauth-provider.js:2904-2916`). | the library |
| `/oauth/token` | `POST` with `application/x-www-form-urlencoded` only: the exchange, the refresh and revocation; any other method gets the library's 405 JSON error with `Allow: POST, OPTIONS`, any other content type its 400 (`wop:dist/oauth-provider.js:3085-3102`); `OPTIONS`: 204. A thrown library error becomes an OAuth-shaped 503 (`temporarily_unavailable`, `Retry-After: 30`). Before the library sees a form-encoded `POST`, the edge applies the client rule of D3: a missing, repeated or foreign `client_id`, a Basic `Authorization` header, or a `client_assertion` field is answered `invalid_client` (401) with no fetch. | `src/oauth.ts` (the client rule), then the library |
| `/authorize` | `GET`: the sign-in page. `POST`: the password submission. Any other method: 405 with `Allow: GET, POST`. | `src/oauth.ts` |

**Order of checks, amending 0005.** The order stays path, method, `Origin`, credential, body for `/mcp`; the other paths have their own, short orders:

1. Path: the five above, else 404.
2. `/mcp`: method (405), then `Origin` (403, the 0006 allow list), then the credential gate, then the body steps of 0005's second amendment (read once, parse once, refuse batches), then the transport. Unchanged except the gate.
3. The two discovery documents: the handlers' own method rules. The token endpoint: the library's method and content-type rules, then, for a form-encoded `POST`, the client rule of D3 at the edge, then the library. A body that does not parse as a form is handed to the library, which answers 400 before it looks at any client (`wop:dist/oauth-provider.js:3103-3114`). The 0006 allow list does not apply: the documents are public, and a token request is authenticated by its code and PKCE verifier, not by anything a browser carries on its own, so the list would add a way for Claude's sign-in to fail (which `Origin`, if any, Claude's servers send here is unverified) and protect nothing. The library answers a request that carries an `Origin` with CORS headers that reflect it (`wop:dist/oauth-provider.js:236-251`).
4. `/authorize`: method (405); for `POST`, the same-origin rule (D4); then the page logic. The 0006 allow list does not apply here, because the form is posted by the owner's browser from this Worker's own origin, which the list would refuse.

**The `/mcp` credential gate.** Let `presented` be the text after `Bearer ` in the `Authorization` header (the existing pattern, `^Bearer (.+)$`).

1. If `presented` equals `MCP_BEARER_TOKEN` by the existing constant-time compare (`bearerMatches`, `src/index.ts`, lines 38-49), the request is authenticated as the static caller. No KV is touched. This is checked first so that the Claude Code path costs nothing and cannot be affected by KV, and so a static token is never sent to the OAuth code.
2. Otherwise, if OAuth is on and `presented` matches `^owner:[A-Za-z0-9_-]{16}:[A-Za-z0-9_-]{32}$` (the shape the library issues for the one user id `owner`), call `validateToken(resource, presented, env)`. A token that does not match the shape never reaches KV. If the call throws (KV unavailable), answer 503 with an empty body and `Retry-After: 30`: a 503 is not a 401, so Claude does not start a refresh or a sign-in loop, and nothing is let through. If it returns nothing, or the props' session tag does not equal the current tag (D5), answer 401 as below. Otherwise the caller is authenticated as the OAuth caller.
3. Otherwise 401.

I chose "static first, then OAuth, by a library call from our own gate" over the library's `resolveExternalToken` hook and over wrapping a resource host, for the reasons under Options 2 and 3.

**The 401.** Empty body, as in 0005. With OAuth on, the header is `WWW-Authenticate: Bearer resource_metadata="<origin>/.well-known/oauth-protected-resource/mcp", scope="mcp"` when no token was presented, and the same with `error="invalid_token", ` first when a token was presented and was refused (Claude refreshes reactively on a 401). With OAuth off, the header is `Bearer`, exactly as now. The answer never says whether the token had the wrong shape, was expired, was revoked or matched nothing.

**OAuth off.** OAuth is on only when `OAUTH_KV`, `OWNER_PASSWORD` and `SIGN_IN_LIMITER` are all bound, `OWNER_PASSWORD` is non-empty, and the request's origin is one the library accepts (D1). When any one of them is missing, including only the limiter, the state is the same: only `/mcp` exists, the gate is step 1 alone, the 401 is `Bearer` without `resource_metadata`, and every other path, the two discovery documents, `/authorize` and `/oauth/token` included, is 404. The Worker then behaves as the last release. This is one all-or-nothing rule, so a deployment that forgot the limiter never serves a page that takes password guesses without a throttle, and there is no half-configured state to test. It is also the rollback (see Consequences). The only 503 on the sign-in page and token paths is a runtime failure of a KV or limiter call (D4, D5). A bound `OWNER_PASSWORD` shorter than 24 characters keeps OAuth on but makes `/authorize` refuse to serve the form (D4).

### D3. Client registration and redirect rules

- **CIMD only.** `clientIdMetadataDocumentEnabled: true`, and the `global_fetch_strictly_public` compatibility flag in both Wrangler configurations (0001 requires the two to match). Claude then sees `client_id_metadata_document_supported: true` and `none` in the metadata and chooses CIMD ("Use Claude's published identity"). No registration endpoint exists, so no anonymous caller can write a client record. CIMD documents are fetched by the library and cached in the Cache API, not KV.
- **A fixed allow list of client ids.** A `client_id` is accepted only if it starts with `https://claude.ai/` and parses to the origin `https://claude.ai`, so `https://claude.ai.example/x`, `https://claude.ai@example.test/x` and `http://claude.ai/x` all fail. `https://claude.com/` is not included: the one hosted callback the redirect rule accepts is on claude.ai, and nothing in the Anthropic pages read for this record names a client id on another host. The exact client ids that the hosted apps and Claude Code send are a real-environment check (verification plan); if one lies elsewhere, the allow list gains an entry by a new record. The list is a constant in `src/oauth.ts`, not configuration: a setting could widen what the Worker fetches by a typo, it changes only when Claude's published identity does, and that deserves a code review. Claude Code with the static bearer is not affected. If Claude Code is ever moved to OAuth it presents its own client document, which must also be under the prefix; if it is not, its sign-in fails with `invalid_client` and the header keeps working.
- **Why the list exists.** The library fetches the document named by any HTTPS `client_id` it is given, at `/authorize` and at `/oauth/token` alike, before it examines the grant type (`wop:dist/oauth-provider.js:3166-3188`, `wop:dist/oauth-provider.js:4696-4708`). Without a list an anonymous caller could point the Worker at the owner's Home Assistant address; every such request reaches Home Assistant without credentials, and Home Assistant counts each as a failed login: a notification every time and, if the owner has set a login-attempt threshold, a ban of the Cloudflare address the Worker's own calls use (`ha:homeassistant/helpers/http.py:62-79`, `ha:homeassistant/components/http/ban.py:89-90`, `ha:homeassistant/components/http/ban.py:111-170`; the default threshold is off, `ha:homeassistant/components/http/const.py:51`). The Worker would also be a free request proxy to any public host.
- **Where the list is enforced.**
  - At `/authorize`, first of the pre-checks below, before `parseAuthRequest` (which fetches).
  - At `/oauth/token`, in an edge pre-check that runs before the library for every form-encoded `POST`. It reads the form from `request.clone()`, so the library still receives the original body. The request is refused with `invalid_client` (401, JSON body, `Cache-Control: no-store`, no CORS headers) and no fetch when: there is no `client_id`, or more than one non-empty one; the one `client_id` is not on the list; an `Authorization: Basic` header is present (this server has no client that authenticates with a secret, and the library would refuse a CIMD client's Basic header anyway after fetching); or a `client_assertion` or `client_assertion_type` field is present (the library would take the client id from the assertion's issuer, `wop:dist/oauth-provider.js:3166`). A non-empty `client_secret` is left to the library: the client id is already on the list, and the library refuses the method after one fetch from claude.ai.
  - The rule covers every grant type and revocation: a refresh request carries `client_id` like any other, because the library has no other way to find the client (`wop:dist/oauth-provider.js:3166-3174`), and revocation is the same endpoint (`wop:dist/oauth-provider.js:3221`).
- **The page's other pre-checks, before any lookup.** After the list, and before `parseAuthRequest` runs, the page requires: `response_type=code`; a `code_challenge` (the library lets a confidential client omit it); and a `redirect_uri` that is exactly `https://claude.ai/api/mcp/auth_callback`, or an `http:` URL whose host is `localhost` or `127.0.0.1` (any port; the path is left to the client's document, which the library compares). Every failure of the list or of these checks is a local 400 page, never a redirect, because the redirect has not yet been checked against the client's document; none starts an outbound fetch. Reason: a code can then only be delivered to Claude's hosted callback or to a program on the owner's own computer, whichever client document an anonymous caller points at, and a request with a foreign client or redirect costs nothing. `[::1]` is not allowed because Anthropic's page says Claude Code declares the other two forms. The library then checks the redirect against the client's own document and requires S256 (`wop:dist/oauth-provider.js:5554-5558`, `wop:dist/oauth-provider.js:181-199`); its errors from there on, a `plain` challenge or a wrong `resource`, are redirects to the now verified callback.
- A `client_id` under the list still makes the Worker fetch that URL once per cache lifetime, from claude.ai's host (5 KB, 10 s, public addresses only), and the library follows a redirect from it (`wop:dist/oauth-provider.js:1455-1464`). That is residual R9.

### D4. The sign-in page

The flow uses `parseAuthRequest` and `completeAuthorization`, with no KV write before the password is right.

**GET `/authorize?...`**

1. If OAuth is off: 404. If `OWNER_PASSWORD` is shorter than 24 characters: 503 with a page saying sign-in is not set up.
2. The pre-checks of D3 (a failure is a local 400 page, with no redirect and no fetch), then `parseAuthRequest(request)`, then `describeConsent`. An `AuthorizationError` with a validated redirect becomes the library's error redirect to the client; one without becomes a local 400 page; a fetch failure of the client's document (`CimdFetchError`), or any other failure of the client lookup, becomes a local 502 page. Nothing from the error is shown beyond fixed text.
3. A 200 page showing: the name the app claims (escaped, labelled as claimed), the domain that publishes it (the host of the client id), where access will be sent (the redirect URI's host, which the MCP authorization specification requires), a warning for a loopback host ("this sends access to a program on your computer; continue only if you just started signing in from it"), a plain statement of what Allow grants ("every tool of this server: read and change your Home Assistant"), the line "Continue only if you clicked Connect yourself just now; never use a sign-in link someone sent you.", a visually hidden `username` field (`type=text`, `name="username"`, value `owner`, `autocomplete="username"`, off-screen rather than `type=hidden` or `display:none`, which password managers tend to skip), one password field (`type=password`, `autocomplete=current-password`, required, at most 256 characters) and two buttons, `decision=allow` and `decision=deny`. The form has no `action` attribute, so the browser posts to the page's own URL with its query string, and the POST re-runs `parseAuthRequest` on that query; no field carries anything the server trusts, and the server ignores `username`.

**POST `/authorize?...`**

1. The same-origin rule. If the `Origin` header is present and is not the text `null`, it must equal this Worker's own origin. If it is absent or `null`, the request is accepted only when `Sec-Fetch-Site` is `same-origin`. Anything else gets 403 with an empty body. The page is served with `Referrer-Policy: same-origin` (below), under which a browser's same-origin form post carries the real `Origin`; a browser that sends none or `null` on a same-origin post still sends `Sec-Fetch-Site: same-origin`, which a web page cannot set. This rule is a defence against cross-site posts only; the password is what stops everyone else.
2. The body is read with a 4 KiB limit; it must be `application/x-www-form-urlencoded` and carry `decision` equal to `allow` or `deny`; otherwise a local 400 page.
3. The pre-checks and `parseAuthRequest`, as for GET.
4. `deny`: 302 to the client with `access_denied` from `authorizationErrorRedirect`. No password and no limiter.
5. `allow`: the limiter, then the password, then the grant:
   - `SIGN_IN_LIMITER.limit({ key: "owner-sign-in" })`. When it refuses: 429 with `Retry-After: 60`, the password is not examined. When the call throws: 503 page, the password is not examined, nothing is granted.
   - The password is compared to `OWNER_PASSWORD` the way the bearer is: SHA-256 of both, `crypto.subtle.timingSafeEqual` on the digests, so the comparison takes the same time whatever the length or content. An empty field never matches.
   - Wrong: 401 with the page again and a fixed line, "That password was not accepted." No hint of length or position.
   - Right: `completeAuthorization({ request, userId: "owner", metadata: {}, scope: ["mcp"], props: { v: 1, gen } })` and a 302 to `redirectTo`. The granted scope is always `mcp`, whatever the client asked for; the token response reports it.
   - If the grant write throws (KV unavailable or its daily write cap reached): 503 page, nothing granted.

**The password.** The secret is `OWNER_PASSWORD`, a Worker secret. A value shorter than 24 characters is refused at request time (the form is not served, a POST is refused with 503), so a weak value cannot be set by accident. The owner generates it with `openssl rand -base64 24` (32 characters, 192 bits) and keeps it in a password manager; `autocomplete=current-password` and the hidden `username` field let a phone's or a computer's manager offer to save and fill it (whether they do is a real-environment check). Length is all the Worker can check; a long weak phrase is the owner's responsibility (Owner confirmation 2).

**Attempt limiting.** The limiter is Cloudflare's Rate Limiting binding `SIGN_IN_LIMITER`, 5 attempts per 60 seconds per Cloudflare location, one key for the whole Worker. It counts every password attempt, right or wrong, because the outcome is not known before the compare. What it gives and what it does not:

- It writes nothing to KV, so an attacker cannot spend the 1,000 daily writes that sign-ins and refreshes need.
- It is a throttle, not a lock. When an attacker stops, the owner can sign in within a minute; an attacker at the owner's location can slow the owner for as long as the attack lasts, no longer. The owner's other routes (Claude Code's header, sessions already issued) are unaffected.
- It is approximate and per location: the documentation says requests can exceed the threshold and that locations count separately. It is not the bound on brute force. The bound is the product of three things: the password's entropy; the free plan's 100,000 requests a day for the whole Worker, which caps guesses at 100,000 a day however many locations are used; and this throttle, which caps one location at 7,200 attempts a day. At 100,000 guesses a day, exhausting a space of 2^30 values takes about 29 years and 2^40 values about 30,000 years; a generated 32-character value is beyond reach. A paid plan has no daily request cap, and then only the throttle and the entropy bound the attacker.
- A missing binding turns OAuth off altogether (D2), so the limit is never skipped silently; if the limiter call throws at run time, the POST is 503 and the password is not examined. Whether the free plan includes the binding is not stated on its documentation page and the local test runtime's enforcement is unverified: a deploy that cannot bind it fails and says so, and the fallback is a KV counter with the costs under Options 9 (an ADR amendment).

**CSRF and framing.** There is no handle and no cookie. A cross-site form post cannot include the password, and a post without the password or without a passing same-origin rule does nothing. Every HTML answer carries `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; frame-ancestors 'none'; base-uri 'none'`, `X-Frame-Options: DENY`, `Cache-Control: no-store`, `Referrer-Policy: same-origin`, `X-Content-Type-Options: nosniff` and `X-Robots-Tag: noindex`. The referrer policy is `same-origin` and not `no-referrer` on purpose: under `no-referrer` a browser sends `Origin: null` on a form post, and the same-origin rule would refuse every sign-in. Under `same-origin` the post keeps its real `Origin`, and the redirect that follows it reaches the cross-origin callback with no `Referer`. There is deliberately no `form-action` directive: a browser applies it to the redirect that follows the post, and the redirect goes to the client's callback, which the library has validated. Everything that came from the client is HTML-escaped (`wop:docs/consent-page.md:15-17`).

**Logging.** One JSON line per attempt: `{ event: "sign_in", outcome: "granted" | "wrong_password" | "rate_limited" | "denied", clientDomain, redirectHost }`, where both values are host names parsed by `URL`. Never the password, the code, a token, `state` or the challenge. A failed attempt by another member is visible in `wrangler tail` or Workers Logs only; nothing is pushed to the owner's phone (residual R10). Some lines come from the library and are not under the Worker's control, because `onError` covers error responses only. A warning when a client document cannot be fetched prints the client id and the error text (`wop:dist/oauth-provider.js:4706`); every client id that reaches the library has passed the allow list (D3), so that line can only name a URL under `https://claude.ai/`, whose path and query an anonymous caller chooses, and it never fires for a foreign id. A warning when revoking a grant fails after a refused refresh prints the grant id and the error (`wop:dist/oauth-provider.js:3429`). A third appears once per Worker start if the compatibility flag is unset (`wop:dist/oauth-provider.js:2452`). None of them carries the password, a code, a token, `state` or the challenge.

### D5. Tokens, sessions and revocation

- **The user.** The single user id is `owner`. The id is visible in KV keys and in the token prefix and is not secret.
- **Props.** `{ v: 1, gen }`, where `gen` is the first 32 hexadecimal characters of `HMAC-SHA256(OWNER_PASSWORD, "ha-mcp oauth session v1")`. It is a one-way function of the password with a purpose label of its own; it is stored encrypted, and without the password it is worthless. Props carry nothing else: no HA value, no bearer, no password.
- **The check.** `/mcp` computes the current `gen` for each OAuth request (one HMAC) and refuses a token whose props differ, comparing in constant time. The `tokenExchangeCallback` does the same on refresh and throws `OAuthError("invalid_grant")` on a mismatch, which makes the library revoke that grant (`wop:dist/oauth-provider.js:3419-3433`) and tells Claude to send the owner to sign in (Anthropic, Token endpoint requirements). It returns nothing on a match.
- **Lifetimes.** Access token 3,600 s. Refresh token 30 days from sign-in, not sliding, so the owner signs in again about monthly. Each refresh rotates the refresh token (library behaviour).
- **Revoke everything.** Primary: change `OWNER_PASSWORD` (`wrangler secret put`). Every OAuth session then fails at the next `/mcp` call and the next refresh, immediately, without waiting for the KV read cache. The static bearer is untouched. Secondary, for a leaked KV namespace or to clear it: delete the keys with Wrangler (`npx wrangler kv key list --binding OAUTH_KV --prefix grant:` and `--prefix token:`, then `kv key delete` for each); a deleted token can still pass for up to 60 s at a location that has it cached. Last resort: delete the namespace, create a new one and put its id in `wrangler.toml`. Revoking one session is not a goal: there is one owner.
- **KV unavailable.** The `/mcp` OAuth path answers 503; the static path is unaffected; sign-in answers 503; the token endpoint answers an OAuth-shaped 503. Nothing is allowed because KV failed.
- **Cost per sign-in and per refresh**, in the free plan's units: a sign-in is about seven KV writes and deletes (the grant, the old grant's tokens and record deleted, then the grant and one access token written at the exchange) and a handful of reads; a refresh is two writes. A day of constant use, with one refresh an hour, is under 60 writes. The anonymous routes write nothing: no registration, no handle, no counter.

### D6. Interactions with what exists

- **Origin.** `/mcp` keeps the 0006 rule. `/authorize` uses the same-origin rule on its `POST`. The discovery and token paths have none. The two rules never apply to the same path.
- **Safety policy and delete confirmation.** Both act on tool calls, after the gate, and see no difference between the two credentials. The two credentials are not distinguishable to a tool: both are "the owner". 0017's key is `HMAC-SHA256(HA_TOKEN, "ha-mcp delete confirmation v1")`; the session tag uses `OWNER_PASSWORD` and another label. Neither secret feeds the other: rotating `HA_TOKEN` ends open delete challenges only; rotating `OWNER_PASSWORD` ends OAuth sessions only. The batch refusal still precedes the transport, so one request is one tool call whichever credential made it. 0017's guessing residual counts "a holder of the bearer token"; it now also counts a holder of an OAuth session, and its remedy "rotate the bearer token" gains "change `OWNER_PASSWORD`".
- **CPU.** An OAuth `/mcp` request adds a SHA-256 and a regular-expression test; for a well-formed token, one KV read, one AES-GCM unwrap and decrypt, one HMAC and the constant-time compares. Each is small next to the Home Assistant call a tool makes, and the free plan's 10 ms counts CPU, not the wait for KV. Not measured here: unverified, a first-run check. A static request adds nothing.
- **Subrequests and KV.** A KV read counts against KV's own 1,000 operations per invocation (footnote of the limits page), not the 50 subrequests that 0016's budget counts. An OAuth `/mcp` request reads KV once, and a request that fails the shape test reads nothing. Reads are not bounded by `/mcp` requests alone, though: an anonymous revocation `POST` to `/oauth/token` with an allowed client id and any three-part token string reads up to two keys (`wop:dist/oauth-provider.js:4248-4287`), so about 50,000 such requests a day would use the free plan's 100,000 reads (residual R16). A shape filter at the edge would not reduce this, because an attacker can send a well-formed token; refusing revocation at the edge would remove a standard client feature to save reads that the 100,000 requests a day cap already limits. The exposure is declared, not filtered. The static bearer makes no KV read and is unaffected.
- **Free-plan write budget.** Legitimate use stays far below 1,000 writes a day (D5). Anonymous callers cannot write at all, so the budget cannot be spent by someone who does not hold the password or a session. A refresh storm by the owner's own client is the only way to approach it, and it ends at midnight UTC.
- **Logs.** The `initialize` line of 0004 gains `auth: "static" | "oauth"` so the owner can see which credential a client used.

### D7. Configuration

`wrangler.toml` ships with the OAuth settings commented out, so the published default deploys exactly like the last release and `wrangler deploy --dry-run` needs no placeholder id:

```toml
# OAuth sign-in (optional). To turn it on, replace the compatibility_flags line above with
#   compatibility_flags = ["nodejs_compat", "global_fetch_strictly_public"]
# uncomment the two blocks below, paste your KV namespace id, and set the OWNER_PASSWORD secret.
# See the README. Without all three of the KV namespace, the rate-limit binding and the
# OWNER_PASSWORD secret, the Worker accepts only the bearer token on /mcp.
#
# [[kv_namespaces]]
# binding = "OAUTH_KV"
# id = "<your-kv-namespace-id>"
#
# [[ratelimits]]
# name = "SIGN_IN_LIMITER"
# namespace_id = "1001"
#   [ratelimits.simple]
#   limit = 5
#   period = 60
```

and a comment that `OWNER_PASSWORD` is a secret. A KV namespace id is not a secret and may be committed. `namespace_id` is any integer unique in the owner's Cloudflare account; the owner changes it if it collides. The `global_fetch_strictly_public` flag is part of the commented block and off by default: it changes how a fetch to an address in the Worker's own zone is routed, which the Home Assistant call is not expected to be affected by (unverified), so an owner who does not turn OAuth on takes no untested runtime change. With the flag unset the library prints one warning when the Worker starts and cannot fetch client documents; if the bindings are present and the flag is missing, the first sign-in fails closed at the client lookup (D4). The README says so in Troubleshooting. The build check bundles the shipped configuration, so the library's code is in the bundle either way.

`Env` gains `OAUTH_KV?: KVNamespace`, `OWNER_PASSWORD?: string` and `SIGN_IN_LIMITER?: RateLimit`, all optional because OAuth is off without them. `.dev.vars.example` gains `OWNER_PASSWORD`. The README's Secrets table, Deploy, Connecting Claude, Token rotation, Rolling back and Troubleshooting sections are rewritten for this record.

The test configuration follows 0001: `test/config/wrangler.toml` gets the compatibility flag, a KV namespace named `OAUTH_KV` and the rate-limit binding, all switched on, because the tests must exercise OAuth (the tests of the off state replace `env`); `vitest.config.ts` binds `OWNER_PASSWORD` to a fake value of at least 24 characters; `test/env.test.ts` adds `OWNER_PASSWORD`, `OAUTH_KV` and `SIGN_IN_LIMITER` to its exact key set.

### D8. The owner's steps

All are human steps. None is run by the agent.

1. `npx wrangler kv namespace create OAUTH_KV`; in `wrangler.toml`, follow the comment in the OAuth block: replace the `compatibility_flags` line, uncomment the two blocks, paste the printed id, and change `namespace_id` if it collides with another rate limit in the account.
2. `openssl rand -base64 24`; store the value in a password manager; `npx wrangler secret put OWNER_PASSWORD`.
3. `npx wrangler deploy`, then `npm run smoke` as before (it uses the static bearer).
4. In claude.ai, Organization settings, Connectors: remove the header connector. Add, Custom, the Worker's `/mcp` URL exactly as the metadata says it (no trailing slash), Authentication **Sign in now**, OAuth client **Use Claude's published identity**, no client secret. A header connector's authentication cannot be edited, so it is removed and a new one added.
5. As the owner: Customize, Connectors, the connector, Connect. The password page opens; enter the password. Do this once on a computer and once on a phone: the post must not be refused, and the password manager should offer to save the entry. Sign in only through a Connect you clicked yourself, never through a link someone sent you. If something was wrong and then fixed, wait about five minutes: Claude caches discovery documents.
6. Optional check: from another member's account, or a private window with a wrong password, confirm Connect cannot pass.
7. Claude Code is unchanged: `claude mcp add --transport http ha-mcp <url> --header "Authorization: Bearer <bearer-token>"`.
8. Optional: because the old bearer value sat in the organization's connector, rotate `MCP_BEARER_TOKEN` and re-add Claude Code's header (Owner confirmation 6).

## Owner confirmations

Each item changes what the owner sees or does, or goes beyond what was asked for. Each states its cost and its alternative.

1. **Client registration is CIMD only; there is no registration endpoint.** The owner picks "Use Claude's published identity". Cost: a client that cannot send a CIMD cannot connect; this depends on Anthropic's published behaviour and on the dialog offering that option on the owner's plan. Alternative: also enable dynamic registration with a callback that accepts only the two redirect forms of D3; cost: anonymous callers can write KV records (1,000 writes a day on the free plan, shared with sign-ins), Claude registers on every connection, and the 90-day records accumulate.
2. **The password is a new Worker secret, `OWNER_PASSWORD`, at least 24 characters (refused otherwise), generated by `openssl rand -base64 24`, pasted at about monthly sign-ins.** Cost: a secret to keep and rotate; only length is checked, not strength. Alternative: a memorable passphrase, which is weaker and leans on the throttle and the daily cap, or an outside identity provider (Options 5).
3. **Attempts are throttled with Cloudflare's Rate Limiting binding, 5 a minute per location, with no persistent lockout.** Cost: not a hard limit; the bound on brute force is the password's entropy and the daily cap; the free plan's access to the binding is unverified. Alternative: a KV lockout (spends the write budget, lets an attacker lock the owner out), or a Durable Object (exact, but a new class and migration).
4. **Access tokens last one hour; refresh tokens 30 days from sign-in, not sliding.** Cost: the owner signs in about monthly; a refresh costs two KV writes. Alternative: a sliding 30-day idle window (no re-sign-in while used weekly, but a stolen refresh token then lives as long as it is used), or 90 days.
5. **Changing `OWNER_PASSWORD` ends every OAuth session** (the session tag in D5). Cost: a password change forces a new sign-in everywhere, and a tag check on every `/mcp` call and refresh. Alternative: no tag, so changing the password revokes nothing and revocation is by deleting KV keys with Wrangler.
6. **The static bearer stays valid next to OAuth, for Claude Code.** Cost: anyone with `MCP_BEARER_TOKEN` skips the password page, and the token sat in the Team organization's header connector until the owner removes it. Alternative: rotate it once at the cutover (re-adding Claude Code's header), or move Claude Code to OAuth through its loopback sign-in (supported by D3, with the loopback warning on the page) and delete the secret.
7. **The header connector is removed from the organization and replaced by an OAuth connector.** Cost: authentication settings cannot be edited, so the connector is removed and re-added, and members see the new one only as "Connect". Alternative: none that keeps the server closed to members.
8. **The Worker gains an outbound fetch of the client's metadata document, limited to client ids under `https://claude.ai/` (the `global_fetch_strictly_public` flag, set only when OAuth is turned on).** Cost: R9, a fetch to claude.ai's own host; the flag changes how same-zone fetches are routed, which the Home Assistant call (a public address) is not expected to be affected by, unverified. Alternative: dynamic registration (Options 7) or pinned clients (not in 1.2.4).
9. **The OAuth bindings ship commented out in `wrangler.toml`; to turn OAuth on the owner uncomments them and writes a KV namespace id and a rate-limit namespace id.** Cost: the owner edits a tracked file, and OAuth is off until then. The ids are not secrets. Alternative: keep them in an untracked copy of the configuration.
10. **A new runtime dependency, `@cloudflare/workers-oauth-provider` 1.2.4, exactly pinned.** Cost: the project's first runtime dependency beyond the MCP SDK and zod; a library one month past 1.0 and one day past this release; bundle size and startup time (the limit is 64 MiB and one second; not measured here). Alternative: writing OAuth by hand (Options 6).
11. **The page grants the scope `mcp` whatever is asked, and shows what it means in one sentence.** Cost: no read-only sign-in. Alternative: two scopes enforced per tool, which would need a tool classification that does not exist.
12. **Only client ids under `https://claude.ai/` can start a sign-in or use the token endpoint; the list is a constant in code.** Cost: a client whose id lies elsewhere (Claude Code's own document, if it is not on claude.ai, or a claude.com address) cannot sign in until a new record adds it; the static header keeps working. Alternative: accept any client id, which makes the Worker fetch any public address an anonymous caller names, the owner's Home Assistant included (Options 15); or a setting in `wrangler.toml`, which makes the list easy to widen by mistake.

## Consequences

- A token can be obtained only by someone who enters the owner's password at the sign-in page. Another member's own Connect reaches that page and stops there. A member who gets the owner to enter the password on a page the member started can obtain a session for up to 30 days (R15).
- The server has one new runtime dependency, one KV namespace, one rate-limit namespace and one secret. The free plan's KV budgets are not touched by anonymous callers.
- The HTTP edge grows from one path to five when OAuth is on, and 0005, 0006, 0004 and 0017 get dated amendments. With any OAuth binding or the password absent, the edge is the last release's, and the shipped `wrangler.toml` has them commented out.
- Rolling back to a build from before this change leaves the OAuth connector failing with a 401 that has no `resource_metadata`; the owner must re-add a header connector, which again lets every member use it. Removing the KV binding, the rate-limit binding or the password secret has the same effect on OAuth and leaves the static bearer working. The KV namespace keeps its records until they expire.
- Release note: "The server now offers OAuth sign-in for the claude.ai connector, off by default. To turn it on, create a KV namespace, uncomment the OAuth block in `wrangler.toml` and set `OWNER_PASSWORD`, then replace the header connector with an OAuth one. Claude Code's header keeps working."
- The README's connector instructions change from "No sign-in with a header" to "Sign in now with Claude's published identity".
