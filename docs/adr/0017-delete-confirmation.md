# 0017. Delete confirmation: a one-time code on the owner's phone

Date: 2026-10-23
Status: Accepted
Revised: 2026-10-23 (design review: batched requests, app-fired notification events, look-alike text; second review: parse once at the edge, recorder read-back through `sql.query`; third review: a rule for templated service names, removed in the fourth review, edge answers for a bad body under a wrong `Accept`, a failed body stream, the setting changed during a challenge's life; fourth review: deletes are refused while the system-action block is off, which replaces the rules that tried to make the block-off path safe; fifth review: the stored-automation residual covers rollback and pre-deploy periods, and the stored-data-services example; sixth review: the review step says to delete what it finds, to cover every automation created or changed and the scripts those automations call, to include other refused or stored-data services and the optional re-save check, and the README rollback note is stated as an addition)

## Context

### Problem

`delete_automation` removes an automation, and Home Assistant answers only `{"result":"ok"}`. The delete also drops the automation's entity registry entry (area, labels, categories, name, custom entity id), and Home Assistant keeps no history of automations. The tool returns the deleted config, so a caller who kept it can re-create the automation; nothing else brings it back. At present a model that calls the tool once, by mistake or because of manipulated input, deletes the automation with no human involved.

The owner decided on 2026-10-22 that an automation delete needs a one-time code that Home Assistant sends to the owner's phone and that the owner reads back to the model in the chat. Overwrites (saving over an existing automation or dashboard) need no code. The server cannot pause a tool call to ask a person: it runs in JSON response mode with a new server and transport for every request and keeps no state between requests (0004). A confirmation therefore takes two calls.

The code is worth something only if the model cannot obtain it without the owner. The ways it could reach the model are the subject of most of this record:

- Home Assistant announces every service call, with the caller's data, as a `call_service` event, so the notify call that carries the code is visible to any automation that listens for that event. A model-written automation could copy the code into a helper that a read tool then returns.
- The code could sit in an entity state or history that the read tools return.
- A short numeric code can be guessed, and a server that stores nothing cannot count attempts. The MCP transport also accepts a JSON-RPC batch, which would put many guesses in one HTTP request.
- A challenge could be replayed, altered, or used for another automation.
- The text on the phone could be made to mislead the owner: an automation renamed beforehand, an alias that imitates the rest of the message, or a second message from the model through the same service.

## Options considered

1. **Keep the single-call delete.** Rejected: it is the problem.
2. **Ask through the MCP client (elicitation).** Rejected: it needs a server-initiated request on a stream, and this server is stateless with plain JSON responses (0004). Support in claude.ai is unverified. The confirmation also would not be the owner's own device.
3. **A confirmation phrase typed in the chat, or a flag argument such as `confirm: true`.** Rejected: the model can supply both without a human.
4. **A button on the notification (an actionable notification) that fires an event.** Rejected: it needs an owner automation and state on the Home Assistant side, and the model can fire an event of the same name with a model-written automation (plain event steps are allowed), so the approval is forgeable.
5. **Store the code, with its attempt count and use count, in Workers KV or a Durable Object.** Rejected for now: it adds a binding and an account resource to deploy, a second failure mode, and state that the stateless design (0004) avoids. It would give single use and a rate limit on codes. Its absence is accepted by the bound under D3 and is Owner confirmation 3.
6. **Store the code in Home Assistant (an `input_text` helper).** Rejected: the read tools return helper states, so the code would be one `get_entity` away.
7. **Put an unkeyed hash of the code in the challenge** (the server compares the hash of the supplied code). Rejected: the code space is 10^8 and a SHA-256 of every code takes seconds to compute, so anyone holding the challenge recovers the code offline.
8. **Derive the code from the key (the code is a keyed function of the id, expiry and a nonce; the challenge carries only the nonce and expiry).** Rejected: a caller could make up challenges of its own and try codes against them, and no notification would ever reach the phone. Guessing would cost one request per try with no visible event and no lifetime. With the tag of D3 only the server can produce a challenge that verifies, so every attempt needs a code the owner was told about.
9. **Sign challenges with the bearer token.** Rejected: the bearer token is the model client's credential, and a Claude Code configuration holds it in a file the model's host can read. Anyone who has it could compute the tag for every code offline. See D3 for the choice.
10. **A new signing secret.** Offered as the alternative to D3's choice (Owner confirmation 2); rejected as the default because it adds an owner step and does not protect against the compromise that matters (see D3).
11. **Allow any notify service for the code, without the allowlist test.** Rejected: 0016 refuses legacy notify services the owner has not listed because a `command_line` notify service runs a shell command. One list of trusted services is simpler to explain and to audit. See D1 and Owner confirmation 4.
12. **Count challenge requests in Home Assistant to limit the number of buzzes.** Rejected: it is state in Home Assistant that the model could read or reset.

## Decision

### D1. The setting and its place in the allowlist

`DELETE_CONFIRMATION_NOTIFY_SERVICE` is a new optional plain Worker variable (not a secret) that names the legacy notify service that delivers codes, written `notify.<name>` or `<name>`, for example `notify.mobile_app_pixel`. `Env` in `src/index.ts` gains the optional member, and the comment in `wrangler.toml` documents it with no value.

It is read by one function that returns the name or the reason there is none:

- Trimmed with Python's `str.strip()` (as the allowlist does), lower-cased, and a leading `notify.` removed. A result that is empty is **absent**. A variable set to an empty text is absent; for this setting empty and absent mean the same, because both refuse.
- A name that is not made only of lower-case letters, digits and underscores is **invalid**.
- `send_message` (an entity service that needs an entity id and takes no per-device name) and `persistent_notification` (see the leak analysis: a persistent notification can be observed by a trigger the capture rule does not examine) are **unsupported**. The server cannot tell a group from a device service by its name, so a notify group that has a `persistent_notification` member is not detected; that is a residual and a README warning (D6).

Every delete call, both steps, first requires a valid name that is on the effective allowlist (D2 of 0016). When it is not, the call is refused before any request to Home Assistant, and the message names the setting and the reason: absent, invalid, unsupported, or "`ALLOWED_NOTIFY_SERVICES` is set and does not list it". Removing the setting is therefore the owner's switch that turns every delete off.

**Deletes need the system-action block on.** When `ALLOW_SYSTEM_ACTIONS` turns the block off (the exact text `true`, and nothing else: `src/policy/settings.ts`, lines 5-7), both calls are refused before any request to Home Assistant, with a message that says deletes need the system-action block on and names `ALLOW_SYSTEM_ACTIONS`. The check comes first, before the notify setting is examined. It calls `systemActionsAllowed` (`src/policy/settings.ts`, lines 5-7), the same function the policy uses, so the policy and the delete check cannot disagree about whether the block is on. The guarantees of this record (the code is not readable through `sql.query`, the capture rule is complete, called configs are examined) are claimed only with the block on, where the full policy of 0016 applies: `sql.query` is a blocked service (`src/policy/lists.ts`, line 32), a templated, non-text or unreadable service name in a written config is an undecidable problem that is refused (`src/policy/resolve.ts`, lines 99-110), a walk that reaches a bound (more than 20 nesting levels or 1000 steps) is a problem that is refused the same way (`src/policy/walker.ts`, lines 410-422), and the scripts, automations and scenes that a written config calls are walked as well. With the block off 0016 skips all of these (0016 D2 switches off D3, D4 and D6 to D9), so the policy cannot judge a config it has not fully walked, and this record does not try to repair that path piece by piece: it declines to confirm deletes there (Owner confirmation 15).

The interaction with `ALLOWED_NOTIFY_SERVICES` changes the function in `src/policy/settings.ts`:

| `ALLOWED_NOTIFY_SERVICES` | `DELETE_CONFIRMATION_NOTIFY_SERVICE` | Allowlist the policy uses | Delete |
|---|---|---|---|
| absent (not a string) | absent, blank, invalid or unsupported | empty | refused, setting named |
| absent | valid name | that one name | allowed to proceed |
| set to a list that includes the name | valid name | the list | allowed to proceed |
| set to a list without the name, or to an empty text | valid name | the list (possibly empty) | refused, allowlist named |
| set to any value | absent, blank, invalid or unsupported | the list | refused, setting named |

Today's test `typeof raw !== "string"` stays: it separates "set, even to an empty text" (the whole list, as 0016 decided) from "absent". What changes is `defaultNotifyServices`, which returns the setting's name when it is valid and `[]` otherwise, so that a typo or an unsupported name is never allowlisted by default and an empty text in the new variable never adds an empty entry. Tests cover each row of the table, which also covers the empty-versus-absent case that could not be tested before this setting existed.

This replaces one sentence of 0016 D2: "The server's own notify call for a delete code is not a model call and is not checked." The server's own call is now checked against the same allowlist, by the same function that checks a model's call. The implementation adds a dated amendment to 0016.

The consequence is stated in the README: the model can call the confirmation service directly (it is on the allowlist by default), so it can send the phone text of its own. That text cannot be a valid code (D3), and the residual is already declared in 0016.

### D2. The two calls

`delete_automation` takes `id` (required), `challenge` (optional text) and `code` (optional text).

**Call 1: `id` only.**

1. Check that the system-action block is on, then the setting (D1). Nothing is sent to Home Assistant on a refusal.
2. Read the config as the delete does today (`GET /api/config/automation/config/<id>`). A 404 is the existing refusal and nothing is sent to the phone. A 401 or 403 is reported as today with its hint and is not repeated.
3. Read the entity registry as the delete does (WebSocket, informational), to learn the automation's entity id for the notification (D4). A failure of the read, or no entry for the id, does not refuse: the notification then says the entity is unavailable. A credential failure is reported as today and stops the call before the notification. Nothing is retried.
4. Compute the digest of the config (D3) and the expiry (now plus 300 s). Draw the code (D3).
5. Send the code: `POST /api/services/notify/<name>` with `{"title": "Confirm automation delete", "message": <text of D4>}` and a 15 s limit. The limit is longer than the push service's own 10 s (`ha:homeassistant/components/mobile_app/notify.py:277`) so that Home Assistant's answer normally arrives first. The answer body is discarded. Nothing is retried.
6. On an answer in the 2xx range, return `{status: "confirmation_required", id, alias, entity_id, challenge, expires_at, expires_in_seconds, note}` (`alias` and `entity_id` are null when there is none). The `note` tells the model what to do (D8). It does not contain the code, and neither does anything else the server returns.
7. On any other outcome, refuse (D5). No challenge is returned.

**Call 2: `id`, `challenge`, `code`.** `challenge` and `code` must be given together. A `code` without a `challenge`, or a `challenge` without a `code`, is refused locally with an explanation and nothing is sent: a mistaken call must not start a second notification.

1. Check that the system-action block is on, then the setting (D1).
2. Read the shape, exactly (D3 gives the challenge format). `challenge` is at most 128 characters and has the four fields of D3, each matching its pattern. `code` is at most 32 characters; after removing ASCII spaces and hyphens only (the notification shows it in two groups of four) it must match `^[0-9]{8}$`, ASCII digits only. Anything else is refused.
3. Expired: if the expiry in the challenge (a whole number of seconds, at most 12 digits, so no overflow) is earlier than now, refuse and say so. The expiry is in the clear, so this reveals nothing.
4. Verify the tag with the supplied id, expiry, digest text and code (D3). Any failure is one message for all causes: the code is wrong, the challenge was altered, or it was issued for another automation. No request to Home Assistant has been made yet.
5. Run the existing delete flow unchanged, with one added step. It reads the config, as today (a 404 is the existing refusal). It then computes the digest of what it read, writes it in base64url and compares that text with the digest text in the challenge, exactly. A mismatch is refused: the automation changed after the code was sent, so the owner did not approve this version. The flow then reads the registry (informational) and sends the DELETE with its 20 s limit, exactly as 0012 D8 describes, and returns `deleted_config`, `lost_registry_metadata`, `warnings` and `note`.

Every check that can refuse comes before the DELETE, and the DELETE follows the checks directly. The step 5 comparison uses the read the delete already makes, so call 2 makes no extra request.

### D3. The code, the challenge and the key

**Code.** Eight decimal digits from `crypto.getRandomValues`: a 32-bit value is drawn, values at or above 4,200,000,000 (42 times 10^8, the largest multiple of 10^8 below 2^32) are discarded and drawn again, and the rest is reduced modulo 10^8 and written with leading zeros. Every code is equally likely. The notification shows it as two groups of four.

**Config digest.** The first 16 bytes of SHA-256 of the config serialised as JSON with the keys of every object sorted. It binds the code to the version of the automation that existed when the code was sent. The digest is carried in the challenge in the clear; it is not secret and is no use for guessing the code.

**Challenge.** One text of four dot-separated fields: `dc1`, the expiry in Unix seconds, the digest in base64url, and the tag in base64url. The id is not in the text: the caller passes it as an argument and the tag covers it. It is read exactly as follows, and any deviation is the one refusal of D2 step 4 or a plain "malformed challenge":

- At most 128 characters (a valid one has at most 83). Split on `.` into exactly four fields.
- Field 1 is `dc1`. Field 2 matches `^\d{1,12}$` (ASCII digits) and is read as a whole number. Field 3 (the digest) matches `^[A-Za-z0-9_-]{22}$`. Field 4 (the tag) matches `^[A-Za-z0-9_-]{43}$`.
- The digest is kept and compared as text: the tag input holds the text of field 3 exactly as given, and D2 step 5 compares it with the recomputed digest's base64url text. The tag is decoded to 32 bytes for `crypto.subtle.verify`, and a tag text that does not re-encode to itself (spare bits set in the last character) is refused.
- `code` is normalised as D2 step 2 says, and the tag input holds the eight digits.

**Tag.** HMAC-SHA256, with the derived key below, over the text `JSON.stringify(["ha-mcp/delete-confirmation/v1", id, expiry, digest, code])`. The array form cannot be confused by concatenation. Verification recomputes the tag from the supplied id, the challenge's expiry text and digest text, and the supplied code, and compares with `crypto.subtle.verify`. Whether `crypto.subtle.verify` compares in constant time in workerd is unverified (no pinned source states it), and the design does not rely on it: the compared tag is the one issued for a code the caller must already know, and a recomputed tag for any other guess is unrelated to it, so a timing difference tells a caller nothing about the code. The tag is keyed over the code, so it gives no way to test a guessed code without the key, and there is no unkeyed hash or other offline-checkable form of the code anywhere in the challenge or the notification.

**Key.** `HMAC-SHA256(HA_TOKEN, "ha-mcp delete confirmation v1")`, computed per request and imported as a signing key. It is derived from the Home Assistant token, a secret the Worker already has and no tool, result or client ever holds, so there is no new owner step. The derivation gives the key its own purpose. Reasons for not using the bearer token are under Options (9). The costs are that rotating the Home Assistant token invalidates open challenges (they live five minutes), and that someone who has the Home Assistant token has no need of this guard: they can call Home Assistant directly. A separate secret would add an owner step (`wrangler secret put`) and protect against nothing more than a leak of the Worker's secrets that already includes the Home Assistant token. An empty `HA_TOKEN` refuses the call; the server never signs with an empty key.

**Lifetime.** 300 seconds. The owner has to look at the phone and reply in the chat, and the model has to make the second call; five minutes is generous for that and keeps the window short.

**Guessing bound.** Verification is stateless, so the number of attempts is not counted. The bound comes from the code space, the lifetime and the request rate, and it must be stated for a holder of the bearer token, who is not limited to what a chat client does. Assumptions:

- A guess has probability 1 in 10^8 of being right, whatever the challenge, because the code is uniform and the tag cannot be tested without the key. A guess against a challenge the server did not issue never verifies.
- Every attempt is one HTTP request, because the Worker edge refuses JSON-RPC batches (D9). A `tools/call` carries one code. Without that refusal one request would carry up to 100 attempts (`fw:src/server/requestBody.ts:5`), and the bound below would be 100 times looser.
- The request rate is the attacker's choice. The table uses 1 per second (a model), 10 per second, and about 333 per second, the rate that spends the free plan's whole daily cap inside one challenge's lifetime (100,000 / 300 s). Whether a Worker sustains 333 per second is not measured.
- Guesses are refused before any request to Home Assistant, so they cost no Home Assistant requests and no failed logins there.

| Bearer holder, one attempt per request | Attempts in one 300 s lifetime | Chance of a right guess per challenge |
|---|---|---|
| 1 request per second | 300 | 3 in 10^6 |
| 10 requests per second | 3,000 | 3 in 10^5 |
| About 333 requests per second | 100,000 | 1 in 1,000 |

Per day, on the **free plan**, at most 100,000 requests are served, so at most 100,000 attempts: the chance of a right guess is at most 1 in 1,000 per day, whatever the number of challenges. One notification is enough to reach it at about 333 requests per second; at 10 per second the same ceiling needs about 34 challenges (100,000 / 3,000), so 34 notifications over the day. A slower attacker needs more notifications for the same chance, and a faster one gains nothing from them, so the number of notifications is not a reliable signal and the attack is not visible as a stream. The ceiling is the plan's request cap and nothing the server does.

On a **paid plan there is no daily request cap**, so there is no bound from the design. Attempts per day are the rate times 86,400, kept going by a live challenge at all times (one notification every five minutes, 288 a day): 10 requests per second is 0.9 percent per day, 100 per second is 8.6 percent. The only bound is the rate and CPU the attacker can use. A stored counter (Owner confirmation 3) is the only remedy that holds on a paid plan.

A six-digit code would give 1 in 10 per day at the free ceiling; that is why the code has eight digits. The attack can be stopped by rotating the bearer token, which removes the caller's access.

**Replay.** A challenge and code that were used can be used again until the expiry. After a successful delete the config read answers 404 and the call deletes nothing. If the automation is then re-created with the same id and a byte-for-byte identical config (for example by `upsert_automation` with `deleted_config`), a replay deletes it again, which the owner has already approved for that id and config. If the re-created automation differs in any way, the digest differs and the replay is refused. That is the case the digest exists for.

**Tampering.** Changing the expiry, the digest, the tag, the id or the code changes the input of the HMAC, so the tag fails. Extending the expiry makes the tag fail, not the call succeed.

### D4. The notification text

Title: `Confirm automation delete`. Message, in one line:

`Claude asked to delete the automation with id <id>, entity <entity_id>, named '<alias>'. Confirmation code: 1234 5678. It expires in 5 minutes. If you did not ask for this, ignore this message and do not share the code.`

The id and the entity id come before the alias, so text inside the alias that imitates an id or an entity id always follows the real ones and cannot precede them.

Three values come from the config and registry the server read, and the alias was written by the model or the owner, so each is made safe before it is placed in the line:

- **Alias.** Characters of Unicode category Cf (format characters, which include the bidirectional controls and isolates) are removed. Characters of category Cc (control characters, line breaks included), category Cs (lone surrogates, which a JSON text from Home Assistant can carry and which the push could fail to encode, so one alias could block the delete of its own automation) and the line and paragraph separators U+2028 and U+2029 become a space. Every double quote, single quote and typographic quotation mark becomes a backtick, so the alias cannot close its own quotation or imitate the rest of the message. Runs of white space collapse to one space and the result is trimmed. It is cut to 60 characters, counted as code points, with `...` appended when cut. A config with no alias, an alias that is not text, or one that is empty after this is shown as `(no alias)`.
- **Id.** The same removal and replacement (Cf removed; Cc, Cs, U+2028 and U+2029 become a space; every quote of any kind becomes a backtick; white space collapsed and trimmed), cut to 64 code points.
- **Entity id.** Shown only when the registry read gave a value that matches `^automation\.[a-z0-9_]+$`; otherwise `entity unavailable`, which is also the text when the registry could not be read or has no entry for the id. A value that does not match is never copied into the text.

The REST route sends the message as plain data, so a `{{` in an alias is not rendered (`ha:homeassistant/components/api/__init__.py:442-457`). The id, the entity id and the alias are there so that the owner sees what would be deleted before reading the code to anyone. The entity id matters because an alias can be changed beforehand by an overwrite, which needs no code: the entity id is the name the owner knows from Home Assistant, and no tool of this server changes it (the registry tool only reads). Making the text useless without a human is not possible: whatever a person can read, a program that captures the text can read. The only protection is that the text never reaches the model, which is the leak analysis below.

### D5. Failure handling

Every refusal says that nothing was deleted, and no message contains the code or the code the caller supplied. A failure of the notify call reports the HTTP status and a fixed explanation, never Home Assistant's own text, which for some notify integrations can repeat the message.

| Situation | Call 1 | Call 2 |
|---|---|---|
| System-action block off | Refused before any request; the message says deletes need the block on | Same |
| Setting absent, invalid or unsupported; service not on the allowlist | Refused before any request; the message names the setting and the reason | Same |
| `HA_TOKEN` empty | Refused | Refused |
| Registry read (call 1): no entry, transport failure | The call goes on; the notification says `entity unavailable` | not applicable (call 2 is as today) |
| Registry read (call 1): credential failure | The existing credentials refusal; nothing sent to the phone | not applicable |
| Config read: 404, 401, 403, other status, timeout | The existing refusal or error (stage `before_delete`); nothing sent to the phone; a 401 carries the credentials hint and is not repeated | Same, after the code check |
| Notify call: 400 (unknown service, invalid data) | Refused: Home Assistant did not accept the request, so a notification may not have been sent (a handler can fail partway); check the setting | not applicable |
| Notify call: 401 or 403 | Refused with the credentials hint (token revoked, user not an administrator, user local-only) or the address-ban message; never repeated | not applicable |
| Notify call: 500 or another status | Refused: a notification may or may not have been sent | not applicable |
| Notify call: timeout or no answer | Refused: a notification may have been sent, because Home Assistant finishes a call whose client left | not applicable |
| Notify answers 2xx but no push arrives (a failed push is only logged by the app's service) | A challenge is returned; the note tells the model to ask the owner and, if nothing arrives within about a minute, to ask again | The code is never typed; the challenge expires |
| Wrong code, altered challenge, or another id | not applicable | One message; nothing deleted; "call again with only the id for a new code" |
| Expired | not applicable | Refused, says so |
| Config changed after the code was sent | not applicable | Refused, says so; only reachable with a valid code |
| Registry read fails | not applicable | As today: a warning and the delete continues; a credential failure stops it with no DELETE |
| DELETE fails | not applicable | The existing branches, unchanged (`deleteFailure`) |

For every refusal of the "may have been sent" kind (the 400 included, which is only "may not have been") the message says that a code may have arrived on the phone, that it cannot be used because no challenge was returned, that nothing was deleted, and that the caller should ask again. The server does not retry (a repeated call is a repeated notification) and does not guess whether the notification was sent.

**Repeated challenge requests.** Each call 1 sends a notification and the server cannot count them. The bound is the free plan's requests per day (a paid plan has none) and the cost per request: each call 1 makes three subrequests. The owner can end it by removing the setting or rotating the bearer token. The tool description tells the model to ask once per delete and to reuse the challenge until it expires. Besides the notifications themselves, the push service's daily quota can run out, after which every notification to that phone fails for the rest of the day, security alerts from Home Assistant included (a failed push is only logged: `ha:homeassistant/components/mobile_app/notify.py:243-261`). This is accepted as a residual (Owner confirmation 6).

**Time budget.** Call 1: config read at most 10 s, registry read at most 10 s, notify at most 15 s, so 35 s in the worst case. Call 2: the code check takes microseconds and makes no request, then the existing delete flow, 10 + 10 + 20 = 40 s in the worst case (0012 D11). Both are below the SDK client's 60 s (`fw:src/shared/protocol.ts:106`). Subrequests: 3 and 3 (the WebSocket counts as one), within the free plan's 50. They are single messages: a batch of call 2 messages, which could have used 3 subrequests each and passed the 50-subrequest limit after sixteen, is refused at the edge (D9), so the limit cannot be reached by one request. Neither call has a step after the irreversible one other than the existing result.

### D6. Leaks of the code to the model

The code leaves the server in one place, the notify call. After that it exists in the Home Assistant event bus (the `call_service` event), in whatever the notify service does with the message, on the push service, and on the phone. The server keeps nothing, returns nothing that holds it, never writes it to a log, and discards the answer of the notify call.

**Through the server's own tools.** `get_entity`, `list_entities`, `get_history`, `list_automations`, `get_automation`, `search_registry`, `get_dashboard`, `list_dashboards`, `list_services` and `check_config` return states, attributes, configs and registry rows. A notify call writes none of them: a legacy notify service sends the message and, for the companion app's service, records a "notification sent" signal for the device's notify entity (`ha:homeassistant/components/mobile_app/notify.py:123-137`, `ha:homeassistant/components/mobile_app/notify.py:225`, `ha:homeassistant/components/mobile_app/notify.py:234`), not the text. The tools have no event, trace, log or logbook reader, and the logbook keeps only the domain and service (`ha:homeassistant/components/logbook/processor.py:340-341`, `ha:homeassistant/components/logbook/processor.py:491-497`). `call_service` can return response data only for services that offer it, and a service can return the code only if something stored it first. Something does: the recorder (next paragraph). With the block on, so that `sql.query` is refused, as that paragraph says, and a plain notify service, the code is not in anything a read tool or a service response returns. This claim relies on the safety policy's accepted open-ended-lists residual (0016: the list of services that return stored data cannot be complete). An example is a service the owner has configured to return stored data: `file.read_file` over `allowlist_external_dirs` (it returns data only for an allowlisted path and a file that parses as JSON or YAML: `ha:homeassistant/components/file/services.py:21-90`), or an email-backed code service with `imap.fetch`. Bound: owner configuration only; the companion app's service mirrors nothing. Remedy: name a phone service, and fix any route found later with a list change.

**Through the recorder and `sql.query`.** The recorder stores every event except the types the owner excluded, and its default exclusion list is empty (`ha:homeassistant/components/recorder/__init__.py:149-154`). The notify call carries no `entity_id`, so its `call_service` event is written with its data, the message included, to the event data table (`ha:homeassistant/components/recorder/core.py:288-300,1044-1083`), within the recorder's commit interval and so inside the 300 s lifetime. `sql.query` runs a caller's SELECT against the recorder database by default and returns the rows as response data (`ha:homeassistant/components/sql/services.py:48-60`), and `call_service` passes `return_response` through (`src/tools/services.ts`, lines 107-140). So a model that can call `sql.query` reads the code and deletes alone. Deletes work only with the system-action block on (D1), and with the block on 0016 refuses `sql.query` by name, in a direct call and wherever the walker meets it in a written config (`src/policy/lists.ts`, line 32). A templated, non-text or unreadable service name in a written action, which Home Assistant would render only when the step runs (`ha:homeassistant/helpers/service.py:280-283`), is recorded as an undecidable problem (`src/policy/walker.ts`, lines 350-369), and with the block on a problem refuses the write (`src/policy/resolve.ts`, lines 99-110), so a template cannot produce `sql.query` either. A config that is too large to walk (more than 20 nesting levels or 1000 steps) is a problem of the same kind and is refused (`src/policy/walker.ts`, lines 410-422), so a call placed after the bound is not written unexamined. The scripts, automations and scenes that a written config calls are walked, so a service name inside them is checked too (0016 D6 to D9). This record adds no rule of its own for `sql.query` or service names: it relies on those, and it refuses deletes where they do not apply.

**With the block off.** Both calls refuse (D1), so no code is sent and nothing here depends on what the model can read. The ways a model could read a code with the block off (`sql.query`, `hassio.addon_stdin` and other services that return stored data, templated names, a call hidden past the walk bounds) do not matter for deletes, because no code exists in that configuration.

**An automation or script written while the block was off, or under an earlier build.** The refusal does not look back. An automation or script the model wrote while the block was off (before this change, while the setting was absent, or while the block was off and deletes were refused), or while a build without this change's rules was deployed (a rollback, or the time before this change was first deployed), stays in Home Assistant. Turning the block on or redeploying this change does not remove it. An earlier build may not have the `mobile_app_notification` prefix rule, and one from before the safety policy has no capture rule or `sql.query` rule at all. The policy checks writes, never configs that already exist, so such an automation is not re-checked and can read later codes: it can call `sql.query` or another service that returns stored data and copy the rows into an entity, listen for `call_service` and copy the event, or listen for `mobile_app_notification*` events. This is declared as a residual (below). Its bound is that such a period existed while the model could write automations. The remedy is the owner's, before relying on delete confirmation after any such period: review every automation created or changed through the server during such a period, including owner automations the server overwrote (an overwrite keeps the owner's id), and the scripts those automations call, for capture triggers (`call_service`, `*`, templated event types, `mobile_app_notification*`), for `sql.query` or any other service the current policy refuses or that returns stored data (for example `file.read_file`), and for templated service names, and delete what the review finds in Home Assistant: turning an automation off is not enough, because a model can turn it back on (`automation.turn_on` is not walked, which is the safety policy's accepted "automations on their own trigger" residual); an optional extra check is to re-save an automation unchanged through `upsert_automation` with the block on, which runs the current policy over it and refuses it if it holds something the policy refuses, or exclude `call_service` from the recorder (`recorder: exclude: event_types: [call_service]`), which stores no copy of the message for `sql.query` to return (a capture trigger needs no recorder, so the review is the remedy for that form). The recorder exclusion has a cost: the logbook loses the "triggered by action" context it reads from those rows (`ha:homeassistant/components/logbook/processor.py:330-341`). The README says this in the human step that sets the variable, in the text for `ALLOW_SYSTEM_ACTIONS` and in the rollback note.

**Owner configs with variable service names.** A script or automation of the owner's that takes its service name from variables (`action: "{{ svc }}"`) and is run with variables the model supplies, through `script.turn_on`, `script.<key>` or `automation.trigger`, could run `sql.query`. With the block off deletes are refused, so this is moot for deletes. With the block on, a script or automation that a written config calls is walked, and its templated name is an undecidable problem that is refused (`src/policy/resolve.ts`, lines 99-110), so it is covered for the call routes. An owner config that runs on its own trigger, with state the model influences, is not reached by that walk; it falls under the safety policy's accepted "automations on their own trigger" residual and is not a separate residual of this record.

**Through an entity that copies notification text.** This is the one route that the server cannot close and that is not in Home Assistant Core. The companion app can publish a "last notification" sensor from the notifications shown on the device. If the owner turns it on, the text of the code notification lands in a state and in history that `get_entity`, `list_entities` and `get_history` return. Whether the app has such a sensor, how it is enabled and whether it filters apps is app behaviour, not in the pinned source, and unverified. The remedy is the owner's: do not enable it, or exclude the Home Assistant app from it. The real-environment run checks it (verification plan). A notify service that mirrors the message into an entity (a custom integration, a notify group that includes one) has the same effect. The setting must name a service that does not.

**Through an automation written with this server (capture).** The code is observable by an automation only through the bus and the integration that sends it. Starting from `ha:homeassistant/core.py:2944-2952` and `ha:homeassistant/core.py:1651-1659`: an automation sees a bus event only through an `event` trigger or a `wait_for_trigger` step of the same kind (`ha:homeassistant/components/homeassistant/triggers/event.py:225-241`), and the `call_service` event reaches one that lists `call_service` or `*`. With the block on, 0016 D10 refuses an automation written through the server whose normalised triggers or `wait_for_trigger` steps, at any depth and inside blueprint expansions, list `call_service`, `*`, a templated type or a non-text type, including a type placed under `options`. A trigger of another event type cannot receive the `call_service` event, but it can receive an event the companion app fires with the notification's own data. This record therefore extends the rule (see "Companion-app notification events" below). No other trigger kind reads the service call: state, template, numeric state, time and the others read states, `mqtt` reads topics, `webhook` reads inbound calls, and `persistent_notification` reads persistent notifications. The last is why `persistent_notification` is refused as the code service in D1: with it, the message would be in `trigger.notification`, which the capture rule does not examine. The same holds for a notify group that has a `persistent_notification` member: the group sends the message to every member (`ha:homeassistant/components/group/notify.py:105-125`), so the message reaches a persistent notification and a model-written `persistent_notification` trigger. The server cannot see a group's members, so the README tells the owner not to name such a group, and it is a residual. For any other service, the rule as extended covers, with the block on, every way the notify call can be observed by an automation the model writes, except events that an integration or app other than the ones named fires itself. The rule examines only what the walk reached, so a written config that is too large to walk (the bounds above) is refused, with the block on, before the capture question arises (`src/policy/resolve.ts`, lines 99-110). With the block off deletes are refused and the rule's reach does not matter for them.

**Residual routes.** Declared in the table below with bounds:

- `mqtt_eventstream` republishes every event, `call_service` included, to an MQTT topic (`ha:homeassistant/components/mqtt_eventstream/__init__.py:83-96`), and an automation written through the server can trigger on that topic. The owner does not configure it.
- The companion app's `fire_event` webhook (`ha:homeassistant/components/mobile_app/webhook.py:306-324`) lets the phone put any event into Home Assistant, and the app does fire `mobile_app_notification_*` events (`ha:homeassistant/components/script/blueprints/confirmable_notification.yaml:75`). The extension below closes the types whose names start with `mobile_app_notification` for automations written through the server. Any other event the app or its platform variants fire with notification text stays open; it is bounded by the owner's check in the verification plan, which lists every event during a call 1.
- An automation of the owner's own that listens for `call_service` and stores its data. The rule examines only automations written through the server.
- A notify integration that fires an event of its own type, or logs an error, with the message in it. The companion app's service does neither with the text (`ha:homeassistant/components/mobile_app/notify.py:252-258` logs a translated error without the message). Other services are unchecked.

**The text itself.** It names the automation so that a human can refuse; it cannot be made useless to a program. It carries no secret beyond the code.

**Companion-app notification events (the capture rule's extension).** The rule's list of event types gains a prefix: an event trigger whose `event_type` starts with `mobile_app_notification` (after the same Python strip and lower-casing the rule applies to `call_service`) is refused. That covers `mobile_app_notification_received`, `mobile_app_notification_cleared` and `mobile_app_notification_action`, and any later type with that prefix. It applies wherever the capture rule applies: the automation's own triggers, `wait_for_trigger` steps at any depth, blueprint-expanded automations, and triggers normalised from `options` or a list. The implementation adds the prefix to `src/policy/lists.ts` next to the capture types and tests it with the same shapes as the existing capture tests. It also adds a dated amendment to 0016's capture rule (D10). Cost: an automation written through this server cannot listen for those events, which includes the common pattern of an actionable-notification button that fires `mobile_app_notification_action`; the owner can write such automations in Home Assistant itself (Owner confirmation 12). The rule does not reach automations written elsewhere.

**Through the owner.** The owner reads the code to the model. A model that asks for a code without saying what it will delete, or an owner who does not read the notification, defeats the human check; the notification names the alias and id, and the tool description tells the model to say which automation it means. Declared below.

### D9. The Worker edge refuses JSON-RPC batches

After the bearer check and before the transport, the Worker parses the request body once and refuses a request whose parsed value is a JSON array. The check is made on the parsed value, not on characters of the text, so it cannot disagree with what the transport would have parsed:

1. The edge reads the body with the SDK's own `readRequestBody` (`fw:src/server/requestBody.ts:44-62`), imported from `@modelcontextprotocol/sdk/server/requestBody.js`, which resolves through the package's `./*` export at 1.32.1 (as the existing import in `src/index.ts` does). It decodes with a default `TextDecoder`, which removes one leading UTF-8 byte order mark (BOM), and it enforces the transport's 4 MiB limit (a declared `Content-Length` over it, or more bytes received than it). A body over the limit gets status 413, `Content-Type: application/json`, and the transport's own JSON-RPC error body (code -32000, message from `requestBodyTooLargeMessage`, `fw:src/server/requestBody.ts:8-10`), as `fw:src/server/webStandardStreamableHttp.ts:751-755` answers. A failure of the body stream (the read itself fails, which `readRequestBody` lets propagate) is caught by the edge and answered 400 with code -32700 and the same parse-error body as step 2, as the transport answers it (`fw:src/server/webStandardStreamableHttp.ts:749-760`); it is never an uncaught exception.
2. The edge calls `JSON.parse` once on the text. A failure (a second BOM, which `JSON.parse` rejects, an empty body and any other malformed text included) gets status 400 with the transport's body: code -32700, message `Parse error: Invalid JSON` (`fw:src/server/webStandardStreamableHttp.ts:756-759`).
3. When `Array.isArray(parsed)` the edge answers with the batch refusal below, whatever the array holds.
4. Otherwise the edge passes the parsed value on with `transport.handleRequest(request, { parsedBody: parsed })` (`fw:src/server/webStandardStreamableHttp.ts:182,746-748`). The transport then does not read or parse the body again, so there is no second decode that could treat a BOM, white space or any other character differently. The request given to the transport is the original one; its body has been consumed by the edge, and the transport does not touch it when `parsedBody` is given.

The existing log line for `initialize` in `src/index.ts` (today it reads `request.clone().json()`) must take the same parsed value as an argument and read nothing itself, so the body is read and parsed exactly once per request. Because the edge parses before the transport, which checks `Accept` (406) and then `Content-Type` (415) before it reads the body (`fw:src/server/webStandardStreamableHttp.ts:719-765`), a request with a wrong `Content-Type` and an unparseable body gets the edge's 400 rather than the transport's 415, and a request with a wrong `Accept` and a body that is unparseable or an array gets the edge's 400 rather than the transport's 406. A request with a wrong `Content-Type` or `Accept` and a parseable non-array body still reaches the transport and gets its 415 or 406. A single message after one BOM is parsed and served as before; after two BOMs it is a parse error, as it was.

- **Answer:** status 400, `Content-Type: application/json`, body `{"jsonrpc":"2.0","error":{"code":-32600,"message":"Invalid Request: JSON-RPC batches are not supported"},"id":null}`. This is the status and code the SDK uses for its own batch-size refusal (`fw:src/server/webStandardStreamableHttp.ts:762-765`), so a client already handles it. The 413 and the -32700 answers are the transport's own, produced by the edge.
- **Order:** path, method, `Origin`, bearer, then the read and this check, then the transport. An unauthenticated request still gets the 401 of the edge contract and learns nothing about batches.
- **Why:** it makes one HTTP request carry one attempt, which the guessing bound of D3 assumes (the transport accepts up to 100 per request and needs no session or earlier `initialize` in this mode: `fw:src/server/webStandardStreamableHttp.ts:762-775`, `fw:src/server/webStandardStreamableHttp.ts:1016-1019`). It also makes the subrequest limit unreachable from one request (D5).
- **Effect on legitimate clients:** none expected. The SDK client sends `JSON.stringify(message)` per POST (`fw:src/client/streamableHttp.ts:513`); its `send` accepts an array (`fw:src/client/streamableHttp.ts:490-491`), but the protocol layer calls it with one message at a time (`fw:src/shared/transport.ts:180`). The SDK's message type for the latest version has no batch member (`fw:src/types.ts:250-255`). Of the five protocol versions the server accepts, batching belongs to at most 2025-03-26, by the protocol's own text, which is not in a pinned source here and is unverified. A client that negotiates that version and sends a batch gets the 400 above and can send its messages one at a time. Whether claude.ai and Claude Code ever batch is unverified; the real-environment run connects both and confirms every tool call works.
- **Implementation:** `src/index.ts` gets the check and tests in `test/mcp.test.ts` (where the initialize-logging test is): an array body with one element, with two, after leading white space, after one BOM and after two BOMs (the last is a parse error, 400 with -32700, which is still no batch), each with a valid bearer, gets a 400 and builds no server (no Home Assistant request is made), the arrays with the batch body above; the same arrays without a bearer get 401; a non-array single message (also after one BOM and after leading white space) is still served; an oversize body gets 413 as the transport answers it; malformed JSON and an empty body get 400 with -32700; a body stream that fails while it is read gets 400 with -32700 and no uncaught exception; a wrong `Accept` with an unparseable or array body gets the edge's 400, and a wrong `Content-Type` with an unparseable body gets 400 rather than 415; a test that spies on the transport shows it receives `parsedBody` and that the body is read once. The implementation adds a dated amendment to 0005 (the check order gains a step, the edge reads and parses the body, and it answers 413 and -32700 itself, and a wrong `Content-Type` or a wrong `Accept` with an unparseable body, or a wrong `Accept` with an array, gets the edge's 400 instead of the transport's 415 or 406) and a row to the README's troubleshooting table: `400 "JSON-RPC batches are not supported"`: the client sent an array; send one message per request.

## Owner confirmations

Each item changes what a user sees or goes beyond what was asked for. Each states its cost and its alternative.

1. **A new setting, `DELETE_CONFIRMATION_NOTIFY_SERVICE`; deletes are refused until it is set.** Cost: no delete works on a fresh deploy until the owner sets a legacy notify service (a human step). Alternative: a default such as the first `mobile_app_` service, which the server cannot discover without reading services and which could be wrong.
2. **The key is derived from the Home Assistant token, with no new secret.** Cost: rotating the token invalidates open challenges. Alternative: a separate secret set with `wrangler secret put`, an extra owner step with no gain against a leak of the Worker's secrets, and one more thing to rotate.
3. **Eight digits, five minutes, no stored state, so no attempt counter.** Cost, for a holder of the bearer token with one attempt per request (D9): 3 in 10^5 per challenge at 10 requests per second; on the free plan at most 1 in 1,000 per day (the 100,000-request daily cap), reachable with a single notification at about 333 requests per second, so the notifications are not a warning; on a paid plan there is no daily cap and so no bound (0.9 percent per day at 10 requests per second, 8.6 percent at 100, with 288 notifications a day). Single use and replay protection are not available either. Alternative: Workers KV or a Durable Object holding the code, a used flag and an attempt counter (for example five wrong attempts kill a challenge), at the price of a binding, a second failure mode and state; or six digits and a shorter life, which loosens the bound (1 in 10 per day at the free ceiling).
4. **The server's own notify call is checked against `ALLOWED_NOTIFY_SERVICES`, so the code service is on the model's allowlist by default.** Cost: the model can message the phone, including a look-alike "Confirm automation delete" message for another automation and, if the app accepts them (unverified), its notification commands such as clearing a notification or silencing alerts, which can hide a real code notification (a denial of service, not a bypass); an owner who narrows the allowlist to stop that stops deletes too. Alternative: send the code unchecked, which 0016 had said, so that the allowlist can be empty while deletes work.
5. **`persistent_notification`, `send_message` and invalid names are refused as the code service.** Cost: the owner cannot use the Home Assistant app's bell for codes, and a notify group with a `persistent_notification` member cannot be detected, so the README forbids naming a group. Alternative: allow `persistent_notification` and declare the persistent-notification trigger as a residual, or extend the capture rule to that trigger kind.
6. **Phone spam from repeated call 1 is accepted.** Cost: notifications, and the push service's daily quota can run out, after which every notification to that phone, security alerts from Home Assistant included, fails silently for the rest of the day. Alternative: a stored rate limit (item 3's alternative).
7. **Residual routes stay declared:** the companion app's last-notification sensor (the owner does not enable it for this app), `mqtt_eventstream`, any app-fired event other than `mobile_app_notification*`, owner automations on `call_service`, notify integrations that mirror the message, a notify group with a mirroring or `persistent_notification` member, and a group or multi-device service slower than the 15 s limit (name one device). Cost: each lets a determined model read the code in a house that has it, or stops deletes. Alternative: examine MQTT triggers and every event trigger, which refuses legitimate automations.
8. **A replay inside five minutes can delete an automation re-created identically.** Cost: none beyond the case. Alternative: a stored used flag (item 3).
9. **The notification shows the alias, the id and the entity id.** Cost: they appear on a locked screen, and the model can still send a look-alike message that steers the owner towards a real code (the real message always names the entity id). Alternative: text with the code only, which removes the owner's check of what is being deleted.
10. **A delete that was a one-call undo of a create now needs the owner's code.** Cost: the model cannot clean up an automation it just made without the owner. Alternative: none; it follows from the decision.
11. **Real-environment acceptance:** the owner confirms the notification arrives, the code works, no read tool returns the code, and no event carries it (see Verification plan). Until then the change counts as built but not accepted.
12. **The capture rule also refuses event triggers whose type starts with `mobile_app_notification`.** Cost: an automation written through this server cannot listen for the companion app's received, cleared or action events, which includes the common actionable-notification button pattern; such automations are written in Home Assistant itself, outside the rule. Alternative: leave the types allowed and rely on the owner's check of the app's events, which cannot see a route that a later app version opens.
13. **The Worker reads and parses every request body once at the edge and refuses every JSON-RPC batch with a 400.** Cost: a client that sends a batch (only protocol version 2025-03-26 has batching, unverified here) must send messages one at a time; the SDK client does not batch. The edge now answers 413 and -32700 itself with the transport's bodies, a bad body with a wrong content type gets 400 instead of 415, and a wrong `Accept` with an unparseable or array body gets 400 instead of 406. Parsing happens once in the edge and the transport receives the parsed value, so the two cannot disagree. Alternative: allow batches and accept the 100-times looser bound of item 3, or count attempts in stored state.
14. **Call 1 also reads the entity registry over the WebSocket.** Cost: one more subrequest and up to 10 more seconds (35 s worst case); a failure only makes the notification say `entity unavailable`. The rename mitigation disappears whenever the WebSocket is down, not only on one failed read: with no WebSocket the owner has the alias alone for every delete. Call 1 also parses the whole registry list, which costs CPU (a large registry is thousands of entries) before the notification; on a plan with a low CPU limit, hitting the limit ends call 1 before the notify, so nothing unsafe follows but deletes stop working (the CPU limit is unverified here). Alternative: no entity id in the notification, which leaves a rename-then-delete trick (an overwrite that gives an important automation a harmless alias) to the owner's reading of the alias alone.
15. **Deletes are refused while the system-action block is off (`ALLOW_SYSTEM_ACTIONS` set to `true`).** Cost: with the block off you cannot delete automations through the server; the owner turns the block on to delete. Alternative: keep deletes with the block off and add rules for `sql.query`, templated service names and the walk bounds on that path, which three design reviews showed keeps leaking, because with the block off the policy does not walk configs fully (0016 D2 switches off D3, D4 and D6 to D9).
16. **An automation or script written while the block was off, or while a build without this change's rules was deployed (a rollback, or before this change was first deployed), persists; redeploying this change or turning the block on does not remove it, and nothing re-checks stored automations. Accepted by the owner on 2026-10-23.** Cost: after any such period (it existed while the model could write automations), a model-written automation could read later codes; the owner must, before relying on delete confirmation, review every automation created or changed through the server during such a period, including owner automations the server overwrote (an overwrite keeps the owner's id), and the scripts those automations call, for capture triggers (event triggers on `call_service`, `*`, templated types, `mobile_app_notification*`), for `sql.query` or any other service the current policy refuses or that returns stored data (for example `file.read_file`), and for templated service names, and delete what the review finds in Home Assistant: turning an automation off is not enough, because a model can turn it back on (`automation.turn_on` is not walked, which is the safety policy's accepted "automations on their own trigger" residual); an optional extra check is to re-save an automation unchanged through `upsert_automation` with the block on, which runs the current policy over it and refuses it if it holds something the policy refuses, or exclude `call_service` from the recorder (the logbook then loses the "triggered by action" context it reads from those rows); the README says so in the human step that sets the variable, in the text for `ALLOW_SYSTEM_ACTIONS` and in the rollback note. A block turned off and on again inside one 300 s challenge lifetime is declared with it; remedy: wait five minutes after turning the block on. Alternative: re-check every existing automation at call 1, which the server cannot do without reading and walking them all.

## Consequences

- A model cannot delete an automation alone. The owner's phone is the second factor, and the two calls make the owner see what is being deleted.
- The server stays stateless: no storage, no new secret and no new binding. The cost is the bound in D3 and the declared residuals above.
- The safety policy's allowlist now has a default, which fixes an open point of 0016 and makes the empty-versus-absent test meaningful. 0016 gets a dated amendment that its D2 sentence about the server's own call no longer holds. 0016's system-action rules are not changed: deletes are refused while the block is off, and the full policy that applies with the block on carries the guarantees.
- Tests that delete in one call change to two. The first deploy after this change refuses every delete until the variable is set.
- The HTTP edge gains a step (batches refused), and 0005 gets a dated amendment; the capture rule gains a prefix, and 0016 gets a dated amendment for it.
- Rolling back to a build from before this change silently restores single-call deletes and empties the default allowlist; nothing is stored on the server, but automations or scripts the model writes under the older build stay after this change is redeployed and are not re-checked, so the owner reviews them and deletes what the review finds (the residual for automations written under an earlier build) and should know this before redeploying an older build.
- Release note: "`delete_automation` now takes two calls. The first sends a one-time code to your phone through the Home Assistant notify service named in `DELETE_CONFIRMATION_NOTIFY_SERVICE` and deletes nothing; the second takes the challenge and the code you read to Claude and deletes. Set the variable, and see the README for what to avoid."
