# 0010. Dashboard tools: how a dashboard save is made safe

Date: 2026-10-22
Status: Accepted

## Context

### Problem

A Home Assistant dashboard is stored as one JSON document. The only way to change it over the API is to send the whole document: `lovelace/config/save` replaces everything, performs no content validation, keeps no history and answers with an empty result. A save that carries a partial config, a config with keys we silently dropped, or a config for a dashboard that cannot be written, damages a live dashboard that the household uses. The next get-modify-save then starts from the damaged version and compounds it.

The server this repository builds is stateless: every tool call runs in a fresh Worker request, it keeps nothing between calls, and it reaches Home Assistant over a WebSocket that it opens for that call (ADR 0003). So whatever protects a save has to happen inside one call, and the only undo that can exist is the previous config handed back in the tool result.

This ADR decides how `save_dashboard` resolves its target, what it refuses, what order it talks to Home Assistant in, what it returns, and what happens at every point where something can fail. It also states what cannot be guaranteed.

### Behaviour of the last release

There is no release. Before this server was built, the repository had no dashboard tool: the original design note (`plan.md` as first written, before its dated correction note) only described one. It said that `save_dashboard` would "require the full config and have Claude do get-then-save" (line 165), that `lovelace/config` "returns `{ views: [...] }`" and that only storage dashboards are writable (line 91), and that the dashboard schema would be "a loose `DashboardConfig` (`views` array of records)" (line 143). It did not say what to do about YAML dashboards other than the note on line 91, a missing target, a strategy-only config, a failure part way, or concurrent edits. So every residual below is marked "no tool existed".

This ADR departs from that note in four ways, each recorded under Decision: `views` is not required when a `strategy` is present; the target is checked against the dashboard list before anything is saved; the tool returns the previous config; and the tool never trusts a read to have a particular shape.

## Options considered

1. **Send what the caller gives, let Home Assistant validate.** Rejected: Home Assistant checks only that the config is a dict or string (`ha:homeassistant/components/lovelace/websocket.py:153`). `{}` or a string would be stored and the dashboard emptied, with no undo.
2. **Validate the full dashboard structure (card types, entity ids) before saving.** Rejected: card types include custom cards that only the frontend knows, and a strict schema would either strip keys (permanent loss) or refuse valid dashboards. The refusal rule below is deliberately the minimum that separates "a dashboard" from "not a dashboard".
3. **Use a fixed list of messages built before connecting, with the caller's `url_path` and no checks.** Rejected: nothing would stop a save into a YAML dashboard from being sent, or a save to a path that does not exist.
4. **Open a connection per step (list, read, save, read).** Rejected for the reasons in ADR 0003: four logins instead of one and no way to make a later step depend on an earlier result.
5. **Rewrite the later commands' `url_path` to the resolved path before sending.** Rejected: it depends on the helper reading the message at send time, which is an implementation detail, and it adds nothing while the dashboard list is unchanged, because Home Assistant resolves a null path the same way (`ha:homeassistant/components/lovelace/websocket.py:44-54`); the case where the list changes during the call is walked in S21 and S25.
6. **Optimistic concurrency: an optional argument carrying the config the caller last read, refused if the stored config differs.** Rejected for now: Home Assistant offers no compare-and-set, so the tool would still be doing read-then-write with a window, and it adds an argument to a tool whose contract is "full config in, previous and current out". It is the recommended follow-up if concurrent edits turn out to matter; see the residual risks.
7. **A second connection after a failed save to find out what state the dashboard is in.** Rejected: another login, and the tool's contract is never to repeat a Home Assistant call automatically. The error tells the caller to read the dashboard instead.
8. **Cap the config size in the tool.** Rejected: the SDK's 4 MiB request cap already bounds it, the cap is not to be raised, and a second limit based on an unverified value would be a guess.

## Decision

Rules for `save_dashboard`, in the order they act. `get_dashboard` and `list_dashboards` are covered by D12.

**D1. Resolve the target the way Home Assistant does, from the dashboard list.**
The first command is `lovelace/dashboards/list`. Its `check` callback resolves the target:
- `url_path` null or omitted: the listed item whose `url_path` is `lovelace`, if there is one; otherwise the storage default, which is never listed (`ha:homeassistant/components/lovelace/websocket.py:44-54`, `ha:homeassistant/components/lovelace/dashboard.py:330-344`). A null path with no `lovelace` item is allowed and is the normal case for a default that has never been customised.
- `url_path` a string (including the empty string): it must equal the `url_path` of a listed item. Otherwise the save is refused as an unknown dashboard, and the message lists the paths that are available and says that the default dashboard is addressed by omitting `url_path`.
- If the list result is not an array of objects, the save is refused (fail closed).

The later commands carry the caller's `url_path` unchanged (omitted when null). While the dashboard list does not change during the call, Home Assistant resolves it exactly as the check did. A dashboard added or removed during the call can make it differ (S21, S25). For a string path the previous-read `check` closes that gap: if the read comes back `config_not_found` with the message "Unknown config specified" (`ha:homeassistant/components/lovelace/websocket.py:56-60`), the save is refused as an unknown dashboard before it is sent, instead of relying on Home Assistant to refuse it. That message is Home Assistant's own text; if it changes, the save itself still fails with `config_not_found` and nothing is stored.

**D2. Refuse anything that is not a storage dashboard, before any save is sent.**
When D1 selects a listed item, its `mode` must be exactly `storage`. `yaml`, and any other or missing value, is refused with a message saying that the dashboard is defined in a file and must be edited there. This includes a null path that resolves to the legacy YAML `lovelace` item. The refusal is raised from the `check` callback, so the sequence stops with the read and the save unsent. The storage default has no item to check and is always storage (`ha:homeassistant/components/lovelace/__init__.py:155`, `ha:homeassistant/components/lovelace/dashboard.py:113-117`).

**D3. Refuse an empty or partial config, before connecting.**
The `config` argument must be an object with a `views` array (each element an object), or a `strategy` object, or both. A key that is present must have the right type, whatever the other key holds: `views` that is null or not an array of objects, and `strategy` that is null, a string or an array, are refused even when the other key is valid (so `{"views": [...], "strategy": null}` is refused). `{}`, a config with neither key, a string and an array are refused too. Every refusal is a tool error naming the requirement. The type rules are enforced by the input schema (a plain-object, array or string config, a `views` that is not an array of objects and a `strategy` that is not an object are rejected there), and the SDK turns that rejection into a tool error too; the rule that one of the two keys must be present is enforced in the handler. Both run before a WebSocket is opened, so no connection and no login is spent on a refusal. `views: []` is accepted: it is a valid, if empty, dashboard, and D6 gives the way back. A string config, which Home Assistant would accept (`ha:homeassistant/components/lovelace/websocket.py:153`), is never sent. The rule is deliberately minimal: a config that has a `views` array but lacks views or cards the caller meant to keep is accepted. D3 separates "a dashboard" from "not a dashboard"; it does not detect a lossy edit. The previous config in the result is the protection against that.

**D4. Schemas are loose at every depth.**
The input schema is a loose object (`z.looseObject`) with `views` declared as an optional array of loose objects and `strategy` as an optional record; everything inside a view, a card or a strategy is `unknown` and passes through unchanged. No plain `z.object` appears anywhere on the path from the tool argument to the WebSocket message, because the SDK passes parsed output to the handler (`fw:src/server/mcp.ts:330-338`, `fw:src/server/zod-compat.ts:63-71`) and Home Assistant replaces the whole stored object. The returned `previous_config` and `config` are the values Home Assistant sent, not rebuilt objects. The one JSON round trip through the Worker is unavoidable and is listed under residual risks.

**D5. One connection, strictly ordered: list, resolve and check, read previous, save, re-read.**
All four commands run in one `haWsCommands` call, so there is one login (ADR 0003). The helper sends each only after the previous result has arrived, so:
1. `lovelace/dashboards/list` (check: D1, D2).
2. `lovelace/config` with `allowErrorCodes: ["config_not_found"]`. Its `check` records the previous config, or "none stored" when that code came back.
3. `lovelace/config/save` with the caller's config. Its `check` records that the save was acknowledged.
4. `lovelace/config` again. Its result is the `config` returned.

The save is the only irreversible command and is sent only after the target is resolved, the mode is checked and the previous config is in hand. Nothing in the tool retries any command, and after `auth_invalid` or an HTTP 401 nothing is sent again (ADR 0003).

**D6. What is returned.**
On success the tool returns JSON text with:
- `previous_config`: the config stored immediately before the save, as Home Assistant returned it, or `null` when none was stored.
- `config`: the config read back after the save.
- `notes`: present only when non-empty. When `previous_config` is `null` it says that Home Assistant reported no stored config: either the dashboard was never saved (auto-generated), or its stored file was missing or was set aside by Home Assistant as corrupt (the original is then in a `.corrupt.` file in Home Assistant's storage folder, and Home Assistant logs an error). In every case no tool restores the earlier state, and the dashboard is now fixed to the saved config. When the read-back `config` differs from the config that was sent, it says so and that another change may have landed between the save and the read. The comparison is a string comparison of two compact serialisations (see D13), not a deep walk.

`previous_config` is also the undo: calling `save_dashboard` again with it restores the earlier version (S19). The result is compact JSON with `previous_config` first, and is about twice the size of the dashboard in compact form. The size and where it can be lost are covered by D13.

**D7. Know how far the call got, and report it, on every failure the tool can observe.**
Because the helper discards earlier results when it rejects, `save_dashboard` keeps its own progress in variables set by the `check` callbacks, with one of these stages: `before_save` (nothing mutating has been sent), `save_in_flight` (set when the previous-read check passes; the save is next on the wire and may or may not have reached Home Assistant), `saved` (the save was acknowledged). The tool turns any rejection into a tool error that says which stage was reached and includes the previous config whenever it was read:

| Failure | Stage | What the error says |
|---|---|---|
| Refusal (D1, D2), `auth_invalid`, upgrade failure, list failed (including `unknown_command`), timeout or close before the previous read | `before_save` | Nothing was changed. |
| Home Assistant error answer to the save (`code` set): `unauthorized` (not an administrator), `config_not_found` for a dashboard that no longer exists, any other code | `save_in_flight` with an answer | Home Assistant refused the save. For `unauthorized` (raised before the handler runs) and for an unknown dashboard nothing changed. For any other code the outcome is not known: read the dashboard with `get_dashboard`. The previous config is included. A failed file write does not belong in this row: Home Assistant logs it and answers success (see the disk write residual and S23). |
| Timeout, close or a send that throws (no `code`) after the previous read and before the save was acknowledged | `save_in_flight` without an answer | Whether the save was applied is unknown. A save that reached Home Assistant is not cancelled by our disconnect (`ha:homeassistant/components/websocket_api/decorators.py:44-50`, `ha:homeassistant/components/websocket_api/connection.py:258-272`). Read the dashboard with `get_dashboard`. The previous config is included. |
| Any failure of the re-read, or timeout or close after the save was acknowledged | `saved` | The save was acknowledged and the dashboard probably holds the new config. Only the confirmation failed. The previous config is included. |

If sending a command throws inside the helper, the helper rejects at once with an `HaWsError` that has no `code` (src/ha/ws.ts, lines 139-152, and 0003), whichever command it was, and closes the socket. The stage reported is whatever was set before the throwing send: a throw on the save send reports the conservative "unknown whether applied" even though nothing may have been sent, with the previous config included; a throw on the previous-read send reports `before_save`; a throw on the re-read send reports `saved`. Each is on the safe side. The save case is covered by a unit test that makes the save command's send throw and asserts a prompt `save_in_flight` report; the helper's three send paths (the `auth` message, the first command, a later command from the result handler) have a test each in the helper's own tests. Before this was fixed the helper turned a throw from the result handler into an unhandled rejection that nothing settled, so the call waited for the 10 s timeout.

The tool does not open a second connection to find out. These reports exist only while the Worker runs to the end of the call; D13 covers the cases where it does not. Messages for `auth_invalid` and `unauthorized` keep the causes from ADR 0003 (token revoked, user not an administrator, user local-only).

**D8. Concurrency with a person editing in the Home Assistant UI: last write wins, and the tool says what it can.**
Home Assistant offers no version, lock or compare-and-set on a dashboard save (`ha:homeassistant/components/lovelace/websocket.py:150-155`). The tool therefore does not claim to prevent a lost update. What it does guarantee:
- `previous_config` is what was stored when the previous read ran, one WebSocket round trip before the save, so an edit made after the caller's own earlier `get_dashboard` is in `previous_config` and can be recovered by merging.
- A change landing between the save and the re-read shows up as a `config` that differs from what was sent, with a note.
What it cannot guarantee: an edit landing in the window between the previous read and the save is overwritten and is in no result (S15b); and an editor left open in a browser can save its own copy later and overwrite ours.

**D9. Undo when there was no previous config.**
If the previous read returned `config_not_found`, `previous_config` is `null` and the note in D6 is added (which does not assume the dashboard was auto-generated). No `save_dashboard` call can return to the auto-generated state. Only Home Assistant's own `lovelace/config/delete` does (`ha:homeassistant/components/lovelace/websocket.py:169-185`), equivalent to removing the stored file (`ha:homeassistant/helpers/storage.py:624-631`), and the server exposes no tool for it. The save is still allowed, because the first save to a never-customised dashboard is the normal way to create one.

**D10. Size limits are documented, not raised.**
A tool call body over 4 MiB is answered 413 by the transport before any tool runs (`fw:src/server/webStandardStreamableHttp.ts:165-171`, `fw:src/server/webStandardStreamableHttp.ts:749-754`); this limit is not raised. The WebSocket message to Home Assistant is the same JSON plus about 50 bytes, so it is bounded by the same cap; Home Assistant's inbound cap is the aiohttp default (`ha:homeassistant/components/websocket_api/http.py:98`, value unverified). If a message is too large Home Assistant ends the connection, the tool sees a close with no `code`, and D7 applies (`save_in_flight`). The tool adds no limit of its own. The tool description says that a dashboard near these sizes should be split across dashboards or edited in the UI.

**D11. Annotations and logging.**
`save_dashboard` is registered with `destructiveHint: true`; `get_dashboard` and `list_dashboards` with `readOnlyHint: true`. The tool never logs config contents or the access token.

**D12. The read tools.**
`list_dashboards` returns the list items as they are, with a note that the default dashboard appears only once it has a stored config (`ha:homeassistant/components/lovelace/dashboard.py:330-344`). `get_dashboard` sends one `lovelace/config` and returns the stored config as it is, including strategy-only configs. A `config_not_found` answer becomes a message naming its possible causes: the dashboard path does not exist; it has no stored config (never saved, so auto-generated); its YAML file is missing; its stored file was set aside by Home Assistant as corrupt; or Home Assistant is in recovery mode (`ha:homeassistant/components/lovelace/websocket.py:56-60`, `ha:homeassistant/components/lovelace/websocket.py:65-66`, `ha:homeassistant/components/lovelace/dashboard.py:134-135`, `ha:homeassistant/components/lovelace/dashboard.py:142-143`, `ha:homeassistant/components/lovelace/dashboard.py:260-261`, `ha:homeassistant/helpers/storage.py:370-381`). Any other error is returned with Home Assistant's code and message.

**D13. Protect the undo from the Worker and from the client.**
The previous config is the only undo, and two things can destroy it after a save has been applied: the Worker can be stopped before it returns (on a free plan the CPU limit is small, and most of the call's CPU is spent after the save: parsing the re-read, serialising the result, and the SDK serialising its response; the memory limit of the isolate is the second way, because after the save the re-read message, its parsed copy and text, the result and the SDK's escaped response are alive at once), and the client can cut off a result about twice the size of the dashboard. The tool cannot report either, because in neither case does it get to run. Within the `{previous_config, config}` contract it therefore:
- serialises compact JSON, with no indentation anywhere;
- puts `previous_config` first in the result, so a result cut off at the end loses `config` before it loses the undo;
- serialises `previous_config` as text in the previous-read `check`, which is before the save, so that cost is not paid afterwards;
- does not deep-compare configs. The sent config is serialised once by the tool before the save, to give the text it compares with later. The WebSocket helper serialises the whole save message again when it sends it; that second copy is also made before the save, so it does not add work after it. After the save the read-back config is serialised once, which the result needs anyway, and compared as text with the sent one. That is linear and cheap, and both sides go through the same JSON round trip, so the comparison is as exact as a deep one for any config the tool can send;
- says in the tool description that the caller must keep its own earlier `get_dashboard` copy until the save is confirmed, must never rebuild a config from a read that looks truncated (a truncated copy that still has a `views` array passes D3 and would drop views), and should treat a missing result after a `save_dashboard` call as "possibly applied".
This lowers the risk; it does not remove it. The dashboard size at which it matters, for CPU time and for Worker memory alike, is not known and is measured in the real-environment run. Beyond it the remedies are Home Assistant's own backups and the caller's earlier copy.

## Consequences

- A dashboard save is not sent into a YAML dashboard, to a dashboard that is unknown when the tool looks, or with a config that has neither a `views` array nor a `strategy` object, and nothing is stripped on the way. If a dashboard is deleted between the tool's read and its save, the save is still sent and Home Assistant refuses it. A config that has a `views` array but lacks views the caller meant to keep is accepted; the returned previous config is the protection against that.
- A successful save hands back the version it replaced, and a failure the tool can observe says how far the call got and includes the previous version. If the Worker is stopped or the client cuts the result off after the save, the previous version is not delivered (D13, declared residual).
- A disk write failure inside Home Assistant is reported as success and the change reverts at the next restart; the tool cannot see it.
- Cost: one connection and four commands per save instead of one; the result carries two copies of the dashboard; `save_dashboard` refuses a config that has neither `views` nor `strategy`.
- Behaviour that callers must know and the tool text says: last write wins, no tool restores an auto-generated dashboard, and an unknown outcome is resolved by calling `get_dashboard`.
- Release note: "Dashboards can be listed, read and saved. A save replaces the whole dashboard; the result includes the previous config so a change can be undone. YAML dashboards and unknown dashboards are refused."

## Verification plan

Unit tests, using a fake WebSocket server driven through the helper and recording every message it receives. Each test fails against a plain object schema or a naive fixed-sequence implementation.

- D1: null path with a listed `lovelace` storage item goes to `lovelace`; null path with no `lovelace` item saves to the default; a string path not in the list is refused with the available paths and no read or save is sent; the empty string is refused.
- D2: a YAML named dashboard, a legacy YAML `lovelace` item reached by null, and an item with an unexpected or missing `mode` are all refused, and the recorded messages end with the list.
- D3: `{}`, `{"title": "x"}`, `{"views": "a"}`, `{"views": [1]}`, `{"strategy": null}`, a string, an array, `{"views": [...], "strategy": null}` and `{"views": null, "strategy": {...}}` are refused with no connection opened; a views-only config, a strategy-only config and a config with both are accepted.
- D4 and the tool schema: the `tools/list` input schema leaves `additionalProperties` open (not `false`) at every level of `config`, because the SDK builds it with the input side of the schema (`fw:src/server/zod-json-schema-compat.ts:33-36`); and a config with unknown keys at the top level, in a view, in a card, nested inside a card and in a strategy, sent through the whole MCP request path, arrives in the save message deeply equal; the same holds for `previous_config` and `config` in the result.
- D5: the recorded order is list, read, save, read with ids 1 to 4; the save is not sent until the previous read's result arrives; a `config_not_found` on the previous read does not stop the sequence; a `config_not_found` on the save does.
- D6 and D13: result shape on success, as compact JSON with `previous_config` as the first key; `notes` absent when `previous_config` exists and the re-read equals the sent config; a note when `previous_config` is null (with the softened wording); a note when the re-read differs; the tool description contains the keep-your-copy and never-rebuild-from-a-truncated-read text.
- D7, one test per row of the failure table: refusal, `auth_invalid`, list failure with `unknown_command`, timeout during the previous read, an error answer to the save (`unauthorized` and a generic one), timeout and close after the previous read, and a failed re-read. Each asserts the stage text, whether the previous config is included, and that exactly the expected commands were sent and that nothing is sent twice. Peak Worker memory against dashboard size is a real-environment measurement, not a test. The save-error test models an error answer from Home Assistant (`unauthorized`), not a write failure, which Home Assistant never reports. A further test makes the fake server answer success to a save and return the sent config, as it does after a failed write, and asserts the tool reports plain success: the limit is documented, not detected. The timeout cases use the real 10 s timer, because fake timers do not reach the Worker's request context. The case where the save command's send throws is unit-tested (see D7 and the amendment below): it asserts a prompt `save_in_flight` report with the previous config, not a wait for the 10 s timeout. The string-path read check is tested with an "Unknown config specified" answer: no save is sent. The same check is tested with a string path whose previous read answers "No config found." (a storage dashboard created and never saved): the save is sent and succeeds. The refusal matches the message by its prefix, because Home Assistant appends the path, and never on the code alone.
- D9 and D12: the null-previous note text, and the `config_not_found` message naming every cause.
- D10: a config just under the 4 MiB cap saves through the request path; one over it gets a 413 with no tool run.
- D11: tool annotations as registered. D12: `list_dashboards` returns the items and the default-dashboard note; `get_dashboard` returns a strategy-only config verbatim and maps `config_not_found` to the five-cause message; each of the three tools has one Home Assistant error-path test.
- S19: two saves in a row in the fake server, the second sending the first one's `previous_config`, ending with the original config stored.

Only a run against the real environment can show:
- that a Worker can open the WebSocket to Home Assistant through the Nabu Casa address and complete the four-command sequence on one connection (the local test runtime is not production Workers and is not proof);
- the value and behaviour of Home Assistant's inbound WebSocket message cap (aiohttp's default is unverified here), and any size limit imposed on WebSocket messages by Workers or by the Nabu Casa proxy, in both directions;
- whether Home Assistant completes a save when our socket closes right after sending it (the code shows no cancellation; the effect through the proxy is unproven);
- how the Home Assistant frontend treats a stored config with `views: []` or a minimal strategy, and what an open editor does when the dashboard is updated underneath it (frontend code is outside the pinned source);
- CPU time, peak Worker memory and result size versus dashboard size on a free-plan Worker, and the client's tool-result limit, to find the size above which the previous config can be lost (D13);
- that every existing dashboard can be read with `get_dashboard` and saved back unchanged once with `save_dashboard`, to confirm that configs written by the frontend (outside the pinned source) pass D3 and that the result's `config` equals `previous_config` apart from the key-order and number effects listed under residual risks;
- the restart migration of a default saved with a null path (S22), which needs a Home Assistant restart.
